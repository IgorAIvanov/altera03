# @altera/mcp — MCP-обгортка над базою Altera

Дає готовому агенту (Claude Desktop, Claude Code, будь-якому MCP-хосту) працювати
з обліковою базою **від імені реального користувача**: його правами, під його
токеном, із його слідом в аудиті.

Шість інструментів, а не дзеркало команд:

| інструмент | що робить |
|---|---|
| `altera_models` | каталог моделей: імена, назви, синоніми, перелік команд — без схем |
| `altera_describe` | схеми payload-ів названих моделей (можна кілька одним викликом) |
| `altera_call` | виконати команду моделі |
| `altera_attach` | прикріпити файл із диска до збереженого запису |
| `altera_fetch` | забрати вкладення запису на диск |
| `altera_print` | забрати друковану форму запису (PDF) на диск |

Причина не в лаконічності: опис інструментів у MCP лежить у контексті **завжди**,
з першого повідомлення. Дзеркало на сотню моделей — це 400–600 інструментів і
близько 200 КБ у кожній розмові; тут агент читає каталог (~130 байтів на модель),
а схему бере тоді, коли справді збирається викликати.

Кількість росте від КАНАЛІВ бази, а не від моделей, і каналів рівно два: команди
возять JSON, байти ходять окремо (`/api/blob`), бо картинка потрібна браузеру
звичайним GET-URL без заголовка авторизації. Тому файл через `altera_call` не
передати в принципі — скільки б команд не додали в модель. Канал байтів при цьому
ДВОСТОРОННІЙ, і кожен напрямок має свій інструмент: покласти файл, забрати файл,
забрати те, чого в базі ще немає, — бланк, який сервер малює на вимогу.

## Вкладення: `altera_attach`

```json
{ "path": "C:/scan/накладна.pdf", "model": "goods_receipt", "id": "1032" }
```

**Файл називається шляхом, а не вмістом.** Аргументи інструмента їдуть у JSON-RPC
і лишаються в контексті агента: накладна на 420 КБ у base64 — це 560 КБ у
розмові, за які платять щоразу, коли до неї повертаються. Обгортка працює на тій
самій машині, що й хост, тож шлях коштує сорок байтів, а файл читає вона сама.

Ціна цього рішення названа чесно: **обгортка читає будь-який файл, доступний
користувачу, і відправляє його в базу.** `--allow-read` у конфізі — саме те, на
що схоже. Якщо це не влаштовує, звужуй дозвіл до каталогу
(`--allow-read=C:/scan`), а не сподівайся на обгортку.

**Власник обов'язковий** (`model` + `id`). Вкладення без власника — «сирота», і
його за добу прибирає `attachment_gc`: у браузері власника проставляє збереження
форми, а агенту тієї форми нема де зберігати. Тому запис має існувати ДО
прикріплення: спершу `altera_call save`, потім `attach` до отриманого `id`.

Ім'я в базі — з шляху (`name` перекриває), тип — за розширенням; незнайоме
розширення їде `application/octet-stream`. Розмір обмежує база
(`BLOB_MAX_SIZE_MB`), і відмову вона називає словами.

**Показати вкладення людині — окрема робота застосунку.** Байти ляжуть у
`app.attachment` із правильним власником, але на формі їх видно лише там, де
стоїть `<ui-attachments>`. Еталон — `app/document/invoice`.

## Забрати файли: `altera_fetch`

```json
{ "model": "invoice", "id": "42" }          // всі вкладення запису
{ "attachment": "77" }                       // одне за його id
```

У відповідь ідуть **шляхи**, а не вміст: імена, типи, розміри й місце на диску.
Причина та сама, що й у `altera_attach`, лише дзеркальна — скан на 400 КБ у
base64 коштував би 560 КБ у КОЖНІЙ розмові, де до нього повернулися.

**Зображення додатково показуються мініатюрою** (до чотирьох на виклик, ~10–50
КБ кожна). Це навмисний виняток: шлях каже, ДЕ файл, і не каже, ЩО це, а серед
вкладень накладної буває і скан акта, і фотографія пломби. Вимкнути —
`"preview": false`. PDF мініатюри не має: рендерити його довелося б окремим
рендерером, а він живе в сервері й працює в інший бік.

Подивитися перелік вкладень, нічого не забираючи, можна звичайною командою —
`altera_call attachment list {"ownerModel": "invoice", "ownerId": "42"}`. Для
цього користувачу потрібне право **`attachment:view`**; без нього агент бачить
документ і не бачить жодного прикріпленого файлу.

## Друкована форма: `altera_print`

```json
{ "model": "invoice", "id": "42" }
{ "model": "invoice", "id": "42", "templateCode": "invoice_act" }
```

Той самий бланк, який дає кнопка друку у формі: сервер малює PDF за активним
шаблоном моделі, обгортка кладе його у файл і віддає шлях. Без `templateCode`
береться активний шаблон.

Друк **читає**, а не пише, тож він доступний і токену «тільки для читання».
Модель має бути з непорожнім блоком `prints` — інакше активного шаблону немає, і
база скаже це словами.

Те саме через `altera_call invoice printPdf` формально працює, але байти звідти
**зрізані**: там вони лягли б у контекст сотнею кілобайтів base64, які агент не
може ні відкрити, ні зберегти.

## Куди лягають файли

```json
"env": { "ALTERA_DOWNLOAD_DIR": "C:/altera-files" },
"args": ["run", "--allow-net", "--allow-env", "--allow-read", "--allow-write=C:/altera-files", "jsr:@altera/mcp@^0.3.0"]
```

**Каталог називає людина в конфізі, а не агент у виклику.** Аргумента «куди
покласти» немає свідомо: дозвіл `--allow-write` виданий один на процес і вибором
в інструменті вже не звужується, зате файли розповзлися б по диску, а шукати їх
потім людині.

Не задано — `altera_fetch` і `altera_print` чесно відмовляють і кажуть, що
дописати; у базу за файлом при цьому навіть не ходять. Наявні файли не
затираються (другий бланк ляже як `накладна (2).pdf`) і **не прибираються** —
каталог належить людині, і чистити чуже обгортка не має права.

## Налаштування

Потрібні дві змінні оточення й **персональний токен**:

| змінна | | |
|---|---|---|
| `ALTERA_URL` | обов'язково | `https://buh.example.com` або `http://localhost:3000` |
| `ALTERA_TOKEN` | обов'язково | персональний токен доступу |
| `ALTERA_DOWNLOAD_DIR` | для файлів | каталог, куди лягають `altera_fetch` і `altera_print`; без нього вони відмовляють |
| `ALTERA_TIMEOUT_MS` | ні | умовчання 60000; звіт по великому регістру рахується довго |

Запис у конфізі хоста (Claude Desktop — `claude_desktop_config.json`):

```json
{
  "mcpServers": {
    "altera-buh": {
      "command": "deno",
      "args": ["run", "--allow-net", "--allow-env", "--allow-read",
               "--allow-write=C:/altera-files", "jsr:@altera/mcp@^0.3.0"],
      "env": {
        "ALTERA_URL": "https://buh.example.com",
        "ALTERA_TOKEN": "…",
        "ALTERA_DOWNLOAD_DIR": "C:/altera-files"
      }
    }
  }
}
```

**Токен — тільки через `env`, ніколи аргументом командного рядка**: аргументи
видно в списку процесів будь-якому користувачу машини.

### Звідки взяти токен

Видає його `POST /api/auth/tokens`, і **тільки по сесії** — тобто з браузера:
агент, який тримає токен, не має карбувати собі нові. Окремого екрана «Мої
токени» в застосунку ще немає, тож поки що зручніше з репозиторію застосунку:

```bash
deno task token claude-code          # тільки читання (умовчання)
deno task token нічна-звірка --write # з правом запису
```

Значення показується **один раз** — у базі лежить лише хеш. Токен належить базі,
у якій виданий: у сусідній він не працює за побудовою.

## Кілька баз

**Один процес — одна база.** Кілька баз означає кілька записів у конфізі хоста
(`altera-buh`, `altera-test`, `altera-acme`). Це не обмеження реалізації, а
рішення: параметр «до якої бази» в інструменті зручніший у конфізі, але промах у
ньому пише **не в ту базу**, а в обліку така помилка помітна не одразу й
прибирається руками. Тут інструмент фізично не вміє звернутися до сусідньої бази,
а хост підписує кожен виклик іменем сервера.

```json
{
  "mcpServers": {
    "altera-dev":  { "command": "deno", "args": ["run","--allow-net","--allow-env","--allow-read","jsr:@altera/mcp@^0.1.0"],
      "env": { "ALTERA_URL": "http://localhost:3000", "ALTERA_TOKEN": "${ALTERA_TOKEN}" } },
    "altera-test": { "command": "deno", "args": ["run","--allow-net","--allow-env","--allow-read","jsr:@altera/mcp@^0.1.0"],
      "env": { "ALTERA_URL": "http://localhost:3001", "ALTERA_TOKEN": "${ALTERA_TOKEN_TEST}" } },
    "altera-buh":  { "command": "deno", "args": ["run","--allow-net","--allow-env","--allow-read","jsr:@altera/mcp@^0.1.0"],
      "env": { "ALTERA_URL": "https://buh.example.com", "ALTERA_TOKEN": "${ALTERA_TOKEN_BUH}" } }
  }
}
```

Три речі, які видно лише на другій базі:

- **порт — частина `ALTERA_URL`.** Дві локальні установки на одній машині
  розрізняються саме ним (у них і `PORT`, і база, і cookie різні);
- **токен свій у кожної.** `app.access_token` живе В БАЗІ, тож токен із «buh» у
  «test» не працює за побудовою — і змінні оточення мусять бути різні, інакше
  всі записи візьмуть один і той самий;
- **ім'я запису — це те, чим бази розрізняє агент.** Хост показує інструменти з
  префіксом сервера, і воно ж стоїть у вікні підтвердження перед людиною. Тому
  «altera-buh» проти «altera-test», а не «altera-1» і «altera-2».

Робота з двома базами в одній розмові при цьому не втрачається: хост тримає
кілька серверів одночасно.

## Бойова база — токен «тільки читання»

Для продуктиву видавай токен із прапорцем **«тільки читання»**, а запис — окремим
токеном під конкретну задачу. Заборона діє на сервері (не в обгортці), тож
переплутати базу й дописати щось у бойову не вийде навіть помилково.

Ще два запобіжники, які працюють самі:

- **зміна стану вимагає підтвердження.** `delete`, `undelete`, `post`, `unpost`
  проходять лише з `"confirm": true` у payload — провести документ «щоб
  подивитися» не можна;
- **права рахуються на кожній команді.** Агент успадковує рівно права свого
  користувача; токен їх не додає;
- **«тільки читання» стосується і вкладень** — з `@altera/server@0.23.1`.
  Доти прапорець перевіряв лише рантайм моделей, а `altera_attach` ходить іншим
  каналом: на старішій базі такий токен файл завантажить.

## Вимоги

- база на `@altera/server@0.19.0` або новішому. На старіших `GET /api/agent/tools`
  віддає плаский перелік схем замість каталогу — обгортка це впізнає й скаже
  прямо, а не віддасть агенту порожнечу;
- **для `altera_fetch` і `altera_print` — `@altera/server@0.25.3`** і
  перегенерований застосунком реєстр (`deno task sql:registry`, `@altera/tools@0.14.9`).
  Доти модель `attachment` не входила в перелік агента, а `printPdf` не був
  оголошений жодній моделі — обидва інструменти дістануть відмову диспетчера;
- Deno на машині, де живе хост. Окремий виконуваний файл (`deno compile`)
  з'явиться, коли знадобиться комусь, кому Deno ставити не можна.

### Свіжий реліз недоступний перші 24 години

Deno не бере пакет, опублікований менш ніж добу тому, — це захист від
компрометації реєстру, і діє він **за датою публікації**, тож точна версія
замість діапазону не рятує:

```
error: Could not find version of '@altera/mcp' that matches '^0.1.0'
A newer matching version was found, but it was newer than the specified
minimum dependency date …
```

Це не поламка й не помилка в конфізі. Варіанти: зачекати добу; або, якщо треба
негайно, дописати в `args` обгортки `--minimum-dependency-age=0`. Другий шлях
знімає захист для ВСЬОГО, що резолвить той запуск (включно з npm-залежністю
SDK), тому в постійному конфізі йому не місце — краще на цей час лишити шлях до
файла обгортки, а на `jsr:` перейти назавтра.

## Перевірка

```bash
deno task mcp:test
```

Проба піднімає підроблену базу на ефемерному порту, запускає обгортку
**підпроцесом** і розмовляє з нею справжнім JSON-RPC: рукостискання, `tools/list`,
виклики, поведінка на відмовах і на старішій базі. Половина того, що тут може
зламатися, живе не в наших функціях — зайвий `console.log` ламає потік
повідомлень, а помилку в `annotations` видно лише тоді, коли хост покаже людині
не те вікно.
