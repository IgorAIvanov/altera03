# @altera/mcp — MCP-обгортка над базою Altera

Дає готовому агенту (Claude Desktop, Claude Code, будь-якому MCP-хосту) працювати
з обліковою базою **від імені реального користувача**: його правами, під його
токеном, із його слідом в аудиті.

Три інструменти, а не дзеркало команд:

| інструмент | що робить |
|---|---|
| `altera_models` | каталог моделей: імена, назви, синоніми, перелік команд — без схем |
| `altera_describe` | схеми payload-ів названих моделей (можна кілька одним викликом) |
| `altera_call` | виконати команду моделі |

Причина не в лаконічності: опис інструментів у MCP лежить у контексті **завжди**,
з першого повідомлення. Дзеркало на сотню моделей — це 400–600 інструментів і
близько 200 КБ у кожній розмові; тут агент читає каталог (~130 байтів на модель),
а схему бере тоді, коли справді збирається викликати.

## Налаштування

Потрібні дві змінні оточення й **персональний токен**:

| змінна | | |
|---|---|---|
| `ALTERA_URL` | обов'язково | `https://buh.example.com` або `http://localhost:3000` |
| `ALTERA_TOKEN` | обов'язково | персональний токен доступу |
| `ALTERA_TIMEOUT_MS` | ні | умовчання 60000; звіт по великому регістру рахується довго |

Запис у конфізі хоста (Claude Desktop — `claude_desktop_config.json`):

```json
{
  "mcpServers": {
    "altera-buh": {
      "command": "deno",
      "args": ["run", "--allow-net", "--allow-env", "--allow-read", "jsr:@altera/mcp@^0.1.0"],
      "env": {
        "ALTERA_URL": "https://buh.example.com",
        "ALTERA_TOKEN": "…"
      }
    }
  }
}
```

**Токен — тільки через `env`, ніколи аргументом командного рядка**: аргументи
видно в списку процесів будь-якому користувачу машини.

### Звідки взяти токен

Видає його `POST /api/auth/tokens`, і **тільки по сесії** — тобто з браузера:
агент, який тримає токен, не має карбувати собі нові. Окремого екрана «Мої
токени» в застосунку ще немає, тож поки що зручніше з репозиторію застосунку:

```bash
deno task token claude-code          # тільки читання (умовчання)
deno task token нічна-звірка --write # з правом запису
```

Значення показується **один раз** — у базі лежить лише хеш. Токен належить базі,
у якій виданий: у сусідній він не працює за побудовою.

## Кілька баз

**Один процес — одна база.** Кілька баз означає кілька записів у конфізі хоста
(`altera-buh`, `altera-test`, `altera-acme`). Це не обмеження реалізації, а
рішення: параметр «до якої бази» в інструменті зручніший у конфізі, але промах у
ньому пише **не в ту базу**, а в обліку така помилка помітна не одразу й
прибирається руками. Тут інструмент фізично не вміє звернутися до сусідньої бази,
а хост підписує кожен виклик іменем сервера.

```json
{
  "mcpServers": {
    "altera-dev":  { "command": "deno", "args": ["run","--allow-net","--allow-env","--allow-read","jsr:@altera/mcp@^0.1.0"],
      "env": { "ALTERA_URL": "http://localhost:3000", "ALTERA_TOKEN": "${ALTERA_TOKEN}" } },
    "altera-test": { "command": "deno", "args": ["run","--allow-net","--allow-env","--allow-read","jsr:@altera/mcp@^0.1.0"],
      "env": { "ALTERA_URL": "http://localhost:3001", "ALTERA_TOKEN": "${ALTERA_TOKEN_TEST}" } },
    "altera-buh":  { "command": "deno", "args": ["run","--allow-net","--allow-env","--allow-read","jsr:@altera/mcp@^0.1.0"],
      "env": { "ALTERA_URL": "https://buh.example.com", "ALTERA_TOKEN": "${ALTERA_TOKEN_BUH}" } }
  }
}
```

Три речі, які видно лише на другій базі:

- **порт — частина `ALTERA_URL`.** Дві локальні установки на одній машині
  розрізняються саме ним (у них і `PORT`, і база, і cookie різні);
- **токен свій у кожної.** `app.access_token` живе В БАЗІ, тож токен із «buh» у
  «test» не працює за побудовою — і змінні оточення мусять бути різні, інакше
  всі записи візьмуть один і той самий;
- **ім'я запису — це те, чим бази розрізняє агент.** Хост показує інструменти з
  префіксом сервера, і воно ж стоїть у вікні підтвердження перед людиною. Тому
  «altera-buh» проти «altera-test», а не «altera-1» і «altera-2».

Робота з двома базами в одній розмові при цьому не втрачається: хост тримає
кілька серверів одночасно.

## Бойова база — токен «тільки читання»

Для продуктиву видавай токен із прапорцем **«тільки читання»**, а запис — окремим
токеном під конкретну задачу. Заборона діє на сервері (не в обгортці), тож
переплутати базу й дописати щось у бойову не вийде навіть помилково.

Ще два запобіжники, які працюють самі:

- **зміна стану вимагає підтвердження.** `delete`, `undelete`, `post`, `unpost`
  проходять лише з `"confirm": true` у payload — провести документ «щоб
  подивитися» не можна;
- **права рахуються на кожній команді.** Агент успадковує рівно права свого
  користувача; токен їх не додає.

## Вимоги

- база на `@altera/server@0.19.0` або новішому. На старіших `GET /api/agent/tools`
  віддає плаский перелік схем замість каталогу — обгортка це впізнає й скаже
  прямо, а не віддасть агенту порожнечу;
- Deno на машині, де живе хост. Окремий виконуваний файл (`deno compile`)
  з'явиться, коли знадобиться комусь, кому Deno ставити не можна.

## Перевірка

```bash
deno task mcp:test
```

Проба піднімає підроблену базу на ефемерному порту, запускає обгортку
**підпроцесом** і розмовляє з нею справжнім JSON-RPC: рукостискання, `tools/list`,
виклики, поведінка на відмовах і на старішій базі. Половина того, що тут може
зламатися, живе не в наших функціях — зайвий `console.log` ламає потік
повідомлень, а помилку в `annotations` видно лише тоді, коли хост покаже людині
не те вікно.
