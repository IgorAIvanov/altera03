# Документообіг: гіпотези, рішення, план

Живий документ. Мета — обмін первинними документами з контрагентами:
отримати документ → перевірити підписи → зареєструвати в обліку (з допомогою
AI-розпізнавання); і зворотно — сформувати документ → підписати → передати.

**Статус:** проєктування. Код ще не писався.
**Оновлено:** 2026-07-22.

Як користуватися: гіпотези мають статус (`не перевірено` / `підтверджено` /
`спростовано`) і критерій перевірки. Після кожної перевірки статус
оновлюється тут, а не в чаті — інакше знання загубиться між сесіями.

---

## 1. Що вже встановлено фактами

Розібрано реальний пакет із Вчасно (акт, ТОВ «ГАРНЕТ КИЇВ» ↔ фізособа):

| факт | звідки |
|---|---|
| Підпис **detached CAdES, рівень T**: `signingCertificateV2` + `signingTime` + `signatureTimeStampToken` | розбір `.p7s` |
| Алгоритми **ДСТУ 4145-2002** + геш ДСТУ ГОСТ 34.311/7564 | OID-и `1.2.804.*` у контейнерах |
| На один документ — **три підписи**: підпис директора, **печатка** організації, підпис контрагента | три `.p7s` у пакеті |
| Сертифікат містить **ЄДРПОУ** (`NTRUA-…`), **РНОКПП** (`TINUA-…`), назву юрособи, ПІБ підписанта | рядки сертифікатів |
| Пакет — ZIP: оригінал + `.p7s` + квитанція + інструкція | вміст архіву |
| **Оригінал ≠ те, що завантажується кнопкою «PDF»**: 1 сторінка / 121 800 Б проти 2 сторінок / 211 753 Б | порівняння файлів |
| У самому PDF **немає** `/ByteRange`, `/Sig`, `/AcroForm` — підпис зовні | розбір структури PDF |

Останній рядок — ключовий: «підпис усередині файлу», який видно в інтерфейсах,
у цьому випадку є візуалізацією над detached-підписом. Переслати «людський» PDF
разом із `.p7s` не можна — хеші не збігаються.

Про бібліотеку підпису (за документацією, не перевірено на практиці):

- бібліотека ІІТ підтримує CAdES / PAdES / XAdES / ASiC за ДСТУ 4145;
- існують **дві генерації**: стара web-бібліотека (розширення браузера +
  нативний модуль `EUSignWebInstall`) і нова `euscp.js` + `euscp.worker.js`
  (без встановлення);
- в описі API `euscp.js` є `SignHash` і `SignDataEx` із параметром формату;
- звернення до серверів АЦСК із браузера потребує крос-доменного проксі.

## 2. Гіпотези

| # | Гіпотеза | Як перевіряємо | Якщо спростовано | Статус |
|---|---|---|---|---|
| **H1** | `euscp.js` працює у браузері без розширення й нативного модуля | спайк: сторінка + тестовий ключ | інструкція встановлення для користувачів або перехід на хмарний підпис раніше | не перевірено |
| **H2** | Бібліотека при перевірці detached-підпису віддає дані підписанта (ЄДРПОУ, РНОКПП, ПІБ) програмно | спайк: перевірка пакета з Вчасно | парсимо сертифікат самі (ASN.1) або серверна перевірка через провайдера | не перевірено |
| **H3** | Web-збірка вміє накладати **PAdES** | спайк: підписати тестовий PDF | `SignHash` + власний placeholder/ByteRange, або лише CAdES | не перевірено |
| **H4** | Перевірка **мітки часу** (рівень T) доступна тією ж бібліотекою | спайк на реальному `.p7s` | серверна перевірка або статус «мітку не перевірено» | не перевірено |
| **H5** | Крос-доменний доступ до АЦСК вирішується проксі на нашому боці | спайк | узгодження з АЦСК / серверна перевірка | не перевірено |
| **H6** | AI-розпізнавання дає ≥90% полів шапки без правок на 20 реальних документах одного типу | вимір на вибірці | звужуємо тип документа, додаємо підказки полів, ручний ввід лишається основним | не перевірено |
| **H7** | Наявних TypeBox-схем моделей достатньо, щоб згенерувати JSON Schema для structured output LLM | прототип розпізнавання на `invoice` | додаємо вісь `x-extract` (синоніми полів у бланках) | не перевірено |
| **H8** | Контрагент однозначно визначається за ЄДРПОУ із сертифіката | на вибірці вхідних пакетів | ручний вибір контрагента у формі звірки | не перевірено |
| **H9** | Зберігання документів у `bytea` витримує реальні обсяги (десятки тисяч документів) | навантажувальний тест на етапі 1 | винесення байтів у об'єктне сховище; `attachment` уже має поле під зовнішнє ім'я | не перевірено |

## 3. Прийняті рішення

| # | Рішення | Чому |
|---|---|---|
| **D1** | Основа — **CAdES detached + ASiC/ZIP**. PAdES — другим кроком, як опція для вихідних | це те, що реально їздить між контрагентами; без нього немає сумісності |
| **D2** | Підписаний оригінал і візуалізація — **два різні файли**, оригінал незмінний | інакше хеш розходиться з підписом; так само робить ринок |
| **D3** | Приватний ключ **ніколи** не потрапляє на сервер | вимога до КЕП; підпис накладається на клієнті або в хмарі провайдера |
| **D4** | Своєї криптографії не пишемо — жодного рядка | ДСТУ 4145 не підтримується стандартними бібліотеками; ризик неприйнятний |
| **D5** | AI **ніколи** не створює проведений документ автоматично — лише чернетку + екран звірки | тиха помилка в обліку дорожча за ручну звірку |
| **D6** | Контрагент береться **з сертифіката підпису**, якщо підпис є; розпізнавання — лише для решти полів | точні дані замість імовірнісних |
| **D7** | Друк отримує окрему команду «зафіксувати друковану форму як файл» (freeze), окремо від `printPdf` | `printPdf` щоразу рендерить наново — для обміну потрібні незмінні байти |
| **D8** | `SignatureProvider` як інтерфейс із першого дня; реалізації — локальна браузерна, потім хмарна | обидва способи зводяться до одного примітиву; різниця має лишитися локальною |

## 4. Модель даних (ескіз)

Доповнення до наявної `app.attachment`:

```
app.attachment
  + replaces_id  bigint   -- попередня ревізія файлу (ланцюжок версій)
  + kind         varchar  -- 'original' | 'visualization' | 'signature' | 'receipt'
```

Нові таблиці:

```
app.doc_signature
  attachment_id            -- що підписано (оригінал)
  signature_attachment_id  -- сам .p7s (для PAdES — null, підпис усередині)
  format                   -- 'cades_detached' | 'pades_embedded'
  role                     -- 'signature' | 'seal'
  signer_name, signer_edrpou, signer_tin
  cert_serial, cert_issuer, cert_valid_from, cert_valid_to
  signed_at, timestamp_at
  verify_status            -- 'unknown' | 'valid' | 'invalid'
  verify_result jsonb, verified_at

app.doc_exchange
  document_id, direction ('in' | 'out'), counterparty_id
  package_attachment_id    -- ZIP/ASiC як прийшов або як відправляємо
  state                    -- draft → signed → sent → delivered → countersigned → done | rejected
  channel, sent_at, delivered_at

app.doc_recognition
  attachment_id, target_model
  raw_json jsonb           -- сира відповідь LLM (аудит: «звідки взялася сума»)
  confidence jsonb
  status                   -- 'new' | 'confirmed' | 'rejected'
  created_document_id
```

Дедуплікація вхідних — за наявним `attachment.sha256`: той самий файл, залитий
двічі, ловиться до реєстрації.

## 5. Потоки

**Вхідний**

```
ZIP/PDF/скан → attachment (dedup за sha256)
  → якщо є .p7s: зіставити з оригіналом, перевірити, витягти підписантів
  → контрагент за ЄДРПОУ з сертифіката (D6)
  → AI-розпізнавання решти полів → чернетка + довіра по полях
  → екран звірки (PDF ліворуч, форма праворуч)
  → підтвердження → звичайний save цільової моделі
```

Окремо ловимо типову помилку: користувач залив візуалізацію замість оригіналу →
повідомлення «цей PDF не є підписаним оригіналом», а не «підпис недійсний».

**Вихідний**

```
документ проведено → freeze друкованої форми (D7) → незмінний оригінал
  → підпис (клієнт, ключ не залишає машину)
  → .p7s поруч + запис у doc_signature
  → пакет ZIP/ASiC → вивантаження файлу (далі — email/EDI)
```

**Розпізнавання — це «друк навпаки»**, і в цьому репозиторії лягає симетрично:

| друк | розпізнавання |
|---|---|
| модель → `prints` + шаблон → PDF | PDF → `recognition` у manifest.json → `item` моделі |
| `runtime.printPdf` | `runtime.recognizeDocument` |

JSON Schema для structured output будується з наявної `<model>.schema.ts`
(див. H7) — нова модель отримує розпізнавання так само, як зараз отримує CRUD.

## 6. План

| етап | зміст | готово, коли |
|---|---|---|
| **0. Спайк підпису** | окрема сторінка, тестовий ключ: зчитати ключ → перевірити пакет із Вчасно → підписати тестовий PDF | H1–H5 мають статус; жодного рядка в систему не додано |
| **1. Файл документа** | версійність `attachment`, freeze друкованої форми, журнал вхідних, імпорт ZIP-пакета, дедуп | вхідний документ можна зареєструвати вручну, файл зберігається незмінним |
| **2. Перегляд і перевірка підписів** | панель підписантів (ПІБ, роль, час, статус), розбір `.p7s`, перевірка | видно те саме, що показує Вчасно |
| **3. Накладання підпису** | `SignatureProvider` (локальна реалізація), підпис вихідного документа, пакет на вивантаження | наш документ приймає перевірка на ЦЗО |
| **4. AI-розпізнавання** | `runtime.recognizeDocument`, екран звірки, журнал розпізнавань | H6 виміряно на реальній вибірці |
| **5. Обмін** | хмарний підпис, канал відправки (email → EDI) | документ доходить до контрагента без ручного експорту |

Етапи 1–2 не залежать від результату спайка й можуть іти паралельно з ним.
Етап 4 не залежить від 2–3 — розпізнавання й підпис незалежні.

## 7. Відкриті питання

1. **Канал обміну:** файли напряму чи інтеграція з EDI (Вчасно, M.E.Doc, Paperless)?
   Контрагенти вже сидять у провайдерах — «свій канал» вони можуть не прийняти.
2. **Типи документів першими** для розпізнавання: акт, видаткова накладна, рахунок, ТТН?
   Розпізнавання проєктується під конкретний бланк.
3. **LLM:** лишаємось на OpenAI (ключ і код уже є в `agent-llm.service.ts`) чи
   додаємо Claude для vision-витягу? Для сканованих бланків рекомендую Claude.
4. **Архівність:** чи потрібен рівень LT/LTA (вбудовані OCSP/CRL), щоб документи
   пережили строк дії сертифіката?
5. **Печатка організації:** чи використовуємо (у прикладі з Вчасно вона є)?
