# Вход через внешнего провайдера (redirect-поток)

Как подключить OAuth 2.0 / OIDC-провайдера, что при этом делает фреймворк, а что
остаётся приложению, и почему поток устроен именно так.

Про **права** это документ не рассказывает — вход отвечает только на вопрос «кто
это». Что человеку можно делать дальше, решает [`access-control.md`](access-control.md).

---

## Где проходит граница

| Кто | Что делает |
|---|---|
| Фреймворк (`server/modules/auth/`) | маршруты `authorize`/`callback`, одноразовый `state`, связка внешней личности с пользователем, сессия и cookie |
| Приложение (метод входа) | собственно разговор с провайдером: куда отправить браузер и как обменять код на личность |

В ядре нет ни discovery, ни JWKS, ни одного имени провайдера — это знание
принадлежит приложению. Ядру достаточно двух методов.

---

## Контракт

Метод входа кладётся в `auth.methods` конфигурации `bootstrap()`. Их два вида:

```ts
// Обмен на месте — так работает встроенный пароль.
interface AuthDirectMethod {
  key: string;
  label: string;
  authenticate(payload): Promise<AuthUserDto | null>;
}

// Поход в браузер — OAuth/OIDC.
interface AuthRedirectMethod {
  key: string;
  label: string;
  authorizeUrl({ state, redirectUri }): string | Promise<string>;
  exchange({ code, state, redirectUri, params }): Promise<AuthExternalIdentity | null>;
}
```

`AuthMethod` — объединение этих двух. Не один интерфейс с необязательными
полями: у redirect-метода нет осмысленного `authenticate`, и наоборот. Поэтому
`implements AuthMethod` не сработает — реализуйте конкретный вид.

`exchange` возвращает **личность**, а не пользователя:

```ts
interface AuthExternalIdentity {
  externalId: string;   // стабильный идентификатор у провайдера (OIDC `sub`)
  email?: string;       // справочно; на решения не влияет
  displayName?: string; // справочно
}
```

`externalId` — именно `sub`, а не e-mail. E-mail меняют, и связка тихо переехала
бы на другого человека.

Подключение:

```ts
const env = configFromEnv();
await bootstrap({
  ...env,
  auth: { ...env.auth, methods: [new GoogleAuthMethod({ clientId, clientSecret })] },
  // …
});
```

Метод сразу попадает в `GET /api/auth/methods` (с `kind: "redirect"`), и экран
входа рисует для него кнопку.

## Как идёт поток

```
браузер                          сервер                        провайдер
   │  GET /api/auth/authorize/google?redirect=/
   │─────────────────────────────►│
   │                              │  создаёт state в app.auth_login_state
   │                              │  зовёт method.authorizeUrl({state, redirectUri})
   │  302 на провайдера           │
   │◄─────────────────────────────│
   │──────────────────────────────────────────────────────────►│
   │                        пользователь подтверждает вход      │
   │◄──────────────────────────────────────────────────────────│
   │  GET /api/auth/callback/google?code=…&state=…
   │─────────────────────────────►│
   │                              │  гасит state (одним UPDATE … RETURNING)
   │                              │  зовёт method.exchange({code, …})
   │                              │  ищет app.user_identity по (provider, sub)
   │                              │  создаёт сессию, ставит httpOnly-cookie
   │  200 HTML + Set-Cookie       │
   │◄─────────────────────────────│
   │  страница делает location.replace('/')
```

`?redirect=` принимается только как путь от корня (`safeRedirectPath`).
Абсолютный URL там превратил бы вход в открытый редирект — причём срабатывающий
уже **после** создания сессии.

---

## Две ловушки, ради которых поток выглядит именно так

### 1. Callback отвечает документом, а не редиректом

Cookie сессии — `SameSite=Strict`. Поставить её в ответе на кросс-сайтовый
переход можно. А вот если ответить `302` на `/`, браузер считает весь
редирект-ланцюжок кросс-сайтовым и Strict-cookie с запросом к `/` **не
отправит**: приложение откроется неавторизованным, и выглядит это как «вход не
сработал», хотя сессия уже создана.

Поэтому callback возвращает обычный документ с нашего же origin, а переход на
`/` делает уже он (`location.replace`). Эта навигация инициирована нашей
страницей, она same-site, и cookie идёт как надо.

Ослаблять cookie до `SameSite=Lax` ради редиректа — плохой размен: Strict это
один из двух барьеров против CSRF (второй — заголовок `X-Requested-With`).

Код и подробности — `server/modules/auth/auth-redirect-page.ts`.

### 2. `state` лежит в базе, а не в памяти процесса

`dev:server` ходит с `--watch`. Состояние в памяти умирало бы при каждом
перезапуске ровно посреди отладки редиректа — и выглядело бы как «поток
сломан». Плюс так поток переживает несколько инстансов сервера.

Гашение и чтение — один `UPDATE … RETURNING`: два запроса оставляли бы окно, в
которое один и тот же callback проходит дважды.

## Политика связки: только заведённая вручную

Провайдер подтверждает, что человек тот самый, но **не** то, что ему здесь
что-то можно. Поэтому вход пускает только при наличии строки в
`app.user_identity`:

```sql
app.user_identity (user_id, provider, external_id, email, display_name, last_login_at)
unique (provider, external_id)
```

Заводится она на экране пользователя (`app/admin/user` → «Зовнішні входи»), а
хранится и переписывается через `user_get` / `user_save` — полным состоянием,
как и членство в группах. Поле `identities` в `user_save` **необязательное**:
его отсутствие означает «не трогать», иначе любая форма, которая о связках не
знает, молча отвязывала бы человека от провайдера при обычном сохранении имени.

**Исключение одно и оно одноразовое: пустая база.** Тогда внешний вход заводит
первого администратора — иначе после развёртывания без пароля некому завести
вообще никого. Условие то же, что и у остальных bootstrap-путей: `app.users`
пуста. После первого пользователя ветка недостижима навсегда.

У такого администратора пустой хеш пароля, то есть войти паролем он не может.
Это осознанно, но имеет последствие: **если провайдер станет недоступен, войти
будет нечем.** Поставьте себе пароль сразу после первого входа —
`deno task passwd <логин>` или экран пользователя.

Отказы приходят на экран входа параметром `?authError=`; текст общий
(«не пов'язаний з жодним користувачем»), подробности провайдера остаются в логе.

## Проверка без живого провайдера

В разработке живого OAuth нет, поэтому в приложении лежит заглушка —
`app/login/dev-redirect-auth.method.ts`. Она проходит весь путь фреймворка
(`state`, callback, обмен, связка, cookie) и не делает единственного —
кросс-доменного перехода: `authorizeUrl` сразу возвращает адрес нашего же
callback с кодом.

```bash
DEV_AUTH_REDIRECT=1
DEV_AUTH_REDIRECT_SUBJECT=dev-subject
```

В продуктивном окружении заглушка **валит старт сервера** — тот же
предохранитель, что у `DEV_AUTH_BYPASS`.

Чтобы войти ею: заведите пользователя, добавьте связку `dev` / `dev-subject`,
нажмите на экране входа «Тестовий провайдер (dev)».

Автоматически поток проверяют пробы в `scripts/smoke_test.ts` (`deno task smoke`):
список методов и `kind`, редирект со `state`, отказ на чужом `state`, отказ
непривязанной личности, полный цикл со временной связкой и повторное погашение
`state`.

## Что ещё не сделано

- **PKCE.** Контракт его не мешает (метод сам кладёт `code_challenge` в
  `authorizeUrl` и `code_verifier` в `exchange`), но хранить verifier между
  двумя запросами методу пока негде: в `app.auth_login_state` для него нет поля.
  Для confidential-клиента, которым является сервер, это не блокер.
- **Готового OIDC-провайдера в ядре нет** — только контракт. Google/Microsoft
  приложение пишет само; когда таких реализаций накопится две-три и станет
  видно общее, generic-провайдер имеет смысл вынести в `server/`.
- **Отвязка при удалении провайдера** — строки в `app.user_identity` остаются;
  чистить их пока только руками через экран пользователя.
