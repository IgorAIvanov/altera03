# Підсистема друку

Друк — частина **ядра**. Застосунок про рендер нічого не знає: у `app/` живе лише
опис друкованої форми в `manifest.json` та сам файл шаблону.

Клієнт теж нічого не рендерить. Він викликає команду моделі, а сервер бере дані,
бере шаблон, малює PDF і повертає готовий файл.

## Розкладка по файлах

| Де | Що |
| --- | --- |
| [`server/modules/print/print-template.ts`](../server/modules/print/print-template.ts) | формат шаблону: типи блоків, нормалізація «сирого» JSON, резолвінг шляхів |
| [`server/modules/print/print-render-plan.ts`](../server/modules/print/print-render-plan.ts) | шаблон + дані → плаский план блоків із підставленими значеннями |
| [`server/modules/print/print-pdf.renderer.ts`](../server/modules/print/print-pdf.renderer.ts) | малювання плану в PDF (pdf-lib). Чистий рендер: без БД і без знання про моделі |
| [`server/modules/print/barcode/`](../server/modules/print/barcode) | символіки штрих-кодів: Code 128 і EAN-13 своїми силами, QR — обгортка над `qrcode-generator`. Віддають модулі, не малюють |
| [`server/modules/print/print.handlers.ts`](../server/modules/print/print.handlers.ts) | рантайм-команди `runtime.printPdf` і `runtime.printPreview` |
| [`server/sql/print_template/db/`](../server/sql/print_template/db) | таблиця `app.print_template` + `print_template_resolve` — те, без чого ядро не працює |
| `app/<family>/<model>/manifest.json` | опис друкованої форми моделі |
| `app/<family>/<model>/prints/*.template.json` | файл шаблону |
| [`app/admin/print_template/`](../app/admin/print_template) | звичайна admin-модель: CRUD-SQL, список і редактор шаблонів |

## Як модель отримує друк

```json
{
  "prints": {
    "invoice_default": {
      "templateFile": "./prints/invoice_default.template.json",
      "dataCommand": "printData"
    }
  },
  "commands": {
    "sql": { "printData": "invoice_print_data" }
  }
}
```

Команду `printPdf` оголошувати не треба: непорожній блок `prints` уже сказав, що
модель друкується, і генератор реєстру виводить із нього прив'язку до хендлера
ядра `runtime.printPdf`. Явне оголошення в `commands.ts` лишається як
перекриття — для моделі, якій потрібен власний обробник друку замість ядрового.

`handlerKey` — ключ готового хендлера ядра. Застосунок не знає шляхів усередині
`server/`: ключ резолвиться реєстром
([`model-registry.ts`](../server/modules/model-runtime/model-registry.ts)).

А от `commands.sql.printData` потрібен: `printData` не входить до стандартної
п'ятірки, тож рантайм не виводить ім'я функції за конвенцією і не вгадує його.

Далі — SQL-команда даних (`app.<model>_print_data`), файл шаблону в `prints/`,
`deno task sql:registry && deno task sql:assemble && deno task sql:publish`.

У формі редагування кнопка друку викликає команду `printPdf` з `{ id }`, бере
`data.extra.pdfBase64` і відкриває blob у новій вкладці. Еталон — `printPdf()`
у [`invoiceEdit.ts`](../app/document/invoice/invoiceEdit.ts).

## Контракт даних

Рендерер читає **один корінь** — `data.item` відповіді команди, названої в
шаблоні полем `dataCommand`. Прив'язки — крапкові шляхи від цього кореня:

- скалярне поле (`field-list`): повний шлях, напр. `document.counterpartyName`;
- текстовий рядок (`text`): так само повний шлях;
- картинка (`image`): повний шлях; за ним очікується `data:`-URI рядком;
- `source` таблиці: повний шлях до масиву, напр. `document.lines`;
- `path` колонки: шлях **усередині одного рядка** масиву, напр. `name`
  (а не `document.lines.name`).

**Статичне значення перекриває прив'язку** — і в `text`, і в `image`, і в комірці
таблиці, і в штрих-коді. Правило одне на весь формат навмисно: інакше довелося б
пам'ятати, де саме пріоритет інший.

## Шрифти: який гліф звідки

Бланк малюють три шрифти: вбудовані субсети **Roboto** (кирилиця та `№`) і
**PT Sans** (знак гривні), плюс стандартна **Helvetica** з pdf-lib. Символ
дістає шрифт **за наявністю гліфа**, а не за межею коду:

1. ASCII — завжди Helvetica (так метрики збігаються з очікуваннями pdf-lib);
2. далі перший вбудований субсет, що покриває символ: Roboto, потім PT Sans;
3. далі Helvetica, якщо код є у WinAnsiEncoding — сюди потрапляють `«»“”„—–’…`;
4. інакше вбудований шрифт — порожня рамка на папері.

Останній пункт — не «правильний шрифт», а свідома відмова падати: pdf-lib кидає
виняток, коли просиш стандартний шрифт намалювати символ поза його кодуванням, і
без цього рядка один незнайомий символ валив би весь друк.

> **Тут був живий дефект.** Шрифт вибирався за `код <= 0x7F`, тобто все вище
> йшло в Roboto — а лапки-ялинки `«` (U+00AB) у кирилічному субсеті немає, і
> `ТОВ «Демо»` друкувалося сміттям. У КОЖНОМУ бланку, бо лапки має назва
> будь-якої української юрособи. Іронія в тому, що Helvetica ці символи має —
> питання просто ставилося не те.

**Знак гривні `₴` малює друга гарнітура — і це єдине, заради чого вона є.**
U+20B4 немає ні у WinAnsi, ні в жодному з 162 файлів `@fontsource/roboto`
(перевірено скануванням), тож без PT Sans сума зі знаком гривні друкувалася б
порожньою рамкою. З трьох гарнітур, у яких гліф знайшовся (Inter, Noto Sans,
PT Sans), узята найдешевша — 10.8 КБ проти 13.0 і 28.0.

Ціна чесна: `₴` намальований іншою гарнітурою, ніж цифри поруч. Для знака
валюти це непомітно, а альтернатива — міняти гарнітуру ВСІХ бланків, під яку
вже підібрані ширини колонок. Жодна українська літера в PT Sans не
провалюється: Roboto покриває і `Ґґ`, і `ЄІЇєії`.

Покриття субсетів — не здогадка: `deno task print:fonts` читає woff через
fontkit і кладе діапазони кодів поруч із байтами в `fonts.generated.ts`. Тому
правило «чи є гліф» — це дані, а не припущення, і воно під пробою
(`printFontIndexFor`).

## Ширини колонок: намір замість числа

Колонка може не називати ширину, а називати **намір** — і тоді число рахує ядро,
пройшовши по даних до того, як почне малювати:

```json
"columns": [
  { "key": "num",  "width": "fit" },
  { "key": "name", "width": "auto", "minPt": "60" },
  { "key": "vat",  "width": "8%" }
]
```

- **`fit`** — рівно стільки, щоб значення не переносилося (числа, коди, дати);
- **`auto`** — забирає лишок (найменування, опис);
- **відсоток** — фіксована частка ширини блока, як було завжди;
- **`minPt`** — нижня межа в пунктах для `auto`/`fit`; порожньо — немає.

**Стара форма (`widthPercent`) лишається чинною й нікуди не дінеться.** Розвилка
в рендері стоїть на «чи оголосив хоч ХТОСЬ намір»: доки всі колонки на
відсотках, розкладка та сама, до пункта. Рахунок по даних дає інші числа за
визначенням — він на те й потрібен, — тож вмикати його всім означало б
переверстати всі наявні бланки мовчки. Непорожній `width` перекриває
`widthPercent` у тій самій колонці.

### Як воно ділить

Три кроки, і кожен працює з тим, що лишив попередній:

1. **відсотки** забирають свою частку (не влазять — стискаються пропорційно);
2. якщо решті вистачає на «не переноситися» — кожен дістає рівно стільки, а
   **лишок іде колонкам `auto`** (немає жодної — ділиться між усіма гнучкими:
   таблиця мусить заповнити відведене місце);
3. якщо не вистачає — кожен дістає свій мінімум (найдовше **слово**), а
   надлишок роздається за **правилом висоти**: крок іде колонці, чия висота
   зараз найбільша.

Правило висоти прислали прикладники, і воно взяте як є. Ціна його відсутності
вимірна: на бланку з дев'ятнадцяти колонок сума «потрібного» склала 970.5 pt при
альбомному аркуші 761.9 — і без перерозподілу шапка розганялася на 11 рядків
замість 6. Тобто місця вистачало з самого початку, бракувало **розподілу**.

Вибір колонки тут без перебору («кому вигідніше дати») навмисно: пошук коштував
би на кожному кроці обходу всіх колонок по всіх рядках, а таблиця на 500 записів
це тисячі комірок.

### Що рахівник знає такого, чого не знає застосунок

- **об'єднані комірки.** Комірка з `colSpan` каже про СУМУ своїх колонок, а не
  про кожну окремо: спершу вимогу ставлять одиночні комірки, а об'єднана лише
  добирає різницю, і добирає порівну. Позиційна прикидка на боці застосунку саме
  тут і брехала — на тризначній шапці з `rowSpan` показувала чужі числа;
- **повернутий текст** (`textOrientation: "90"`) росте вгору, тож ширини йому
  треба на один рядок, і давати більше — марно віднімати в сусідів;
- **явний розрив** у підписі зменшує потрібну ширину, а не лише вигляд;
- **усі рядки, а не сама шапка.** Порахувати по шапці спокусливо (її мало), але
  тоді колонка з числами на 12 знаків отримає ширину слова «Сума».

### Межа, названа явно

Буває, що не влазять навіть найдовші слова — дев'ятнадцять підписів
регламентованої форми дають суму мінімумів, більшу за альбомний аркуш. Жодна
розкладка цього не виправить: ядро стискає пропорційно, а слово ріже сам
перенос (див. нижче). Розрив некрасивий, але він **у межах комірки**, а вихід за
межі не має жодного правильного прочитання.

## Перенос тексту: явний розрив і довге слово

Правило переносу одне на весь друк (`wrapPrintText` у метриці), і читачів у
нього два — рендерер, який малює, і рахівник ширин. Дві копії розійшлися б
мовчки: ширина рахувалася б за одним переносом, а на папір ліг би інший.

**Явний `\n` у тексті комірки поважається.** У затверджених формах підписи довгі
(«сільськогосподарська»), і той, хто малює бланк, часто знає краще за алгоритм,
де рядок має розірватися. Доти єдиним способом було вставити пробіли з дефісами
прямо в текст («сіль- сько- госпо- дарська») — тобто зіпсувати дані заради
верстки.

**Слово, ширше за комірку, розривається.** Доти воно не переносилося взагалі й
вилазило на сусідню колонку: сітка намальована, текст поверх неї, бланк
зіпсований мовчки.

## Чи влізе значення в колонку: `@altera/server/print/metrics`

Бланк псується мовчки. Число, ширше за комірку, ламається на два рядки; а
заголовок, чиє **слово** ширше за колонку, не переноситься взагалі й лізе на
сусідню — перенос іде по словах. Ані `sql:publish`, ані валідність шаблону, ані
правильні дані цього не показують: видно лише з готового PDF.

Рендерер усе потрібне рахує й так, тож метрика винесена окремим вузьким входом:

```ts
import {
  createPrintTextMeasurer,
  PRINT_CELL_PADDING,
  printContentWidth,
} from "@altera/server/print/metrics";

const measure = await createPrintTextMeasurer();
const usable = printContentWidth() * 0.10 - PRINT_CELL_PADDING * 2;   // колонка 10 %

measure("1 234 567.89", 9) <= usable;                       // значення влізе?
caption.split(/\s+/).every((w) => measure(w, 9, true) <= usable);  // а кожне СЛОВО заголовка?
```

**Заголовок міряють по найдовшому слову, а не по рядку.** Рядок із двох
коротких слів розкладеться на два — це нормально; одне довге не розкладеться
ніяк, і саме воно псує сусідню колонку.

Вимірювач асинхронний, бо шрифт треба вбудувати в документ pdf-lib; сам
документ викидається. Створюй його **один раз на прогін** — вбудовування
коштує помітно більше, ніж усі вимірювання разом.

Ширину не порахувати «приблизно»: Roboto пропорційний, а рядок ще й розпадається
на відрізки різними шрифтами (кирилиця Roboto, латиниця Helvetica), тож
відповідь дає лише сума їхніх ширин. Тим самим кодом міряє й рендерер —
`embedPrintFonts` один на обох, і розійтися їм нема де.

> **Чому окремий вхід, а не `@altera/server/print`.** Метрика тягне pdf-lib, а
> `./print` імпортує ЕКРАН редактора шаблонів — pdf-lib поїхав би в бандл
> фронтенду. Та сама причина, з якої `./print` свого часу відділили від бареля.

### Зібрати бланк у пробі: `@altera/server/print/render`

Метрика відповідає «чи влізе», але не «як воно виглядає» — а перевірити бланк,
не заходячи в застосунок, потрібно саме цілим. Рендерер тому теж вузький вхід:

```ts
import { normalizePrintTemplateSchema } from "@altera/server/print";
import { renderPrintPdf } from "@altera/server/print/render";

const schema = normalizePrintTemplateSchema(JSON.parse(await Deno.readTextFile(file)));
if (!schema) throw new Error("не schemaVersion 2 або порожній шаблон");

const bytes = await renderPrintPdf(
  { code, name, targetModel, dataCommand, orientation: "portrait", schema },
  printData,                                  // те саме `data.item`, що віддає команда даних
);
```

**Шаблон із диска треба нормалізувати** — рівно ця пастка описана вище в розділі
про секції таблиці: файл у `prints/` не проходив через `normalizePrintTemplateSchema`,
і план рендеру зустрічав напівописану таблицю.

Доти проба верстки в застосунку збирала PDF імпортом із `vendor/` і запускалася
з `--no-config` (при `"vendor": true` Deno такий імпорт забороняє) — тобто
трималася на імені файлу в чужому пакеті. Вхід прибирає і те, і те.

## Умовна видимість: `visibleWhen`

Регламентований бланк рідко буває один. Колонка знижки, рядок «У т.ч. ПДВ»,
блок зворотної тари, підвал із факсиміле — усе це є або немає **залежно від
документа**. Без умовності лишалося два виходи, і обидва погані: звузити бланк
до спільного знаменника (виглядає закінченим, доки не з'явиться перше з
пропущеного) або завести шаблон на кожну комбінацію — знижки × ПДВ × тара ×
три підвали це 24 шаблони одного рахунку, і всі 24 редаговані.

Поле одне й лежить **на всіх рівнях**:

```json
{ "type": "field-list", "visibleWhen": "invoice.hasVat", "items": [ … ] }
{ "key": "c_vat",  "widthPercent": "10", "visibleWhen": "invoice.hasVat" }
{ "key": "r_note", "cells": [ … ],       "visibleWhen": "note" }
{ "key": "vat",    "label": "У т.ч. ПДВ", "path": "vat", "visibleWhen": "hasVat" }
```

- **блок будь-якого типу**, включно з лініями, картинкою й штрих-кодом. Саме
  «включно»: підвал із факсиміле — це картинка ПЛЮС риска, і сховати з них
  частину означало б лишити на бланку висячу лінію;
- **колонка таблиці** — від кореня даних: колонка або є на весь бланк, або її
  немає;
- **рядок секції** — з того самого кореня, що й шляхи його комірок: у
  `header`/`footer` це дані друку («Разом ПДВ»), у `row` — конкретний запис
  (додатковий рядок під позицією);
- **рядок списку полів**.

**Умова — це ШЛЯХ, а не вираз.** Шаблон редагує бухгалтер, і `amount > 0 &&
hasVat` — це мова всередині форми, яку доведеться і розбирати, і пояснювати.
Рішення лишається в SQL: команда даних рахує `hasVat`, `hasDiscount`,
`hasPackaging`, а бланк лише показує, чим воно керує. Дані від цього не стають
поданням — прапорець це факт про документ, а не про розкладку.

Хибою вважаються `false`, `0`, порожній рядок, порожній масив, `null`, відсутнє
поле — **і текстові написання `"false"` / `"0"`**. Останнє не поступка, а
fail-closed: команда даних, що віддає все рядками (`(total > 0)::text`), інакше
показувала б блок завжди, і побачити це можна було б лише на папері.

Порожня умова означає «видно завжди», тож наявні шаблони чинні без міграції.

### Що з цього випливає для таблиці

**Схована колонка віддає ширину сусідам сама.** Окремої арифметики немає:
рендерер ділить таблицю за вагами тих колонок, що прийшли, тож менша сума ваг
розтягує решту пропорційно.

**Комірка, об'єднана через сховану колонку, звужується, а не зникає** —
`colSpan: 3` над трьома колонками стає `colSpan: 2`, коли середню сховали.
Комірка, від якої не лишилося жодної видимої колонки, зникає разом із ними, а
рядок, від якого не лишилося комірок, не друкується: інакше в таблиці була б
порожня смуга — слід від колонки, якої на бланку немає.

Прив'язати комірки до колонок можна лише обходом сітки (`colSpan`/`rowSpan`
зсувають усе, що правіше й нижче), і цей обхід **один на два місця** —
`layoutPrintTemplateGrid` у `print-template.ts`. Ним користується і план
рендеру, коли викидає комірки, і PDF-рендерер, коли їх розставляє. Дві копії
розійшлися б на першому ж `rowSpan`, і розходження виглядало б як з'їхала
таблиця, а не як помилка в коді.

**Таблиця без жодної видимої колонки не друкується зовсім** — це не порожня
таблиця, а таблиця, якої на цьому бланку немає.

### У редакторі

Рядок «Показувати, коли» стоїть поруч із прив'язкою — у властивостях блока, у
рядку списку полів, у списку колонок і в переліку рядків секції.

Полотно **нічого не прибирає**: сітку, яку редагують, треба лишити чим рухати й
куди клікати. Блок, чия умова на демо-даних не виконується, блідне й дістає
штрихування (`.frame-hidden`); умовні колонки й рядки лишаються як є, а їхню
умову видно в панелі властивостей. Результат показує вкладка PDF — вона
малюється тим самим рендерером, що й друк.

### Логотип, печатка, факсимільний підпис

Це не прикраса й не властивість бланка: вони належать **організації**, від імені
якої друкують, а організацій у базі кілька. Статичний `src` означав би одну
печатку на всі — тобто не спрощений документ, а неправильний. Тому картинка
береться прив'язкою, як усе інше:

```json
{ "key": "stamp", "type": "image", "path": "invoice.sellerStamp", "alt": "Печатка" }
```

Команда даних віддає `data:`-URI рядком (вкладення й так лежать у базі —
[`blob-subsystem.md`](blob-subsystem.md)). Нічим іншим воно й не могло б
приїхати: блок читає дані друку, а не файлову систему сервера.

Порожня прив'язка дає **порожній** `src`, а не «-»: прочерк тут став би зламаною
картинкою замість відсутньої. Те саме рішення, що в штрих-коді.

### Рядок значень без підпису

Заголовок бланка («Рахунок на оплату № 12 від 02.02.2026 р.»), підсумок
(«Всього найменувань 2, на суму 12 000,00 грн.»), реквізити сторони — це
ЗНАЧЕННЯ без підпису, і робиться це двома способами:

```json
{ "type": "text", "path": "document.title" }
{ "type": "field-list", "items": [{ "key": "org", "label": "", "path": "org.name" }] }
```

Порожній `label` у списку полів означає «друкувати саме значення» — без нього
рядок починався б із двокрапки. Обидві дірки були одночасно, і разом вони
робили динамічний рядок без підпису недосяжним: текст умів лише статику, а
список полів завжди клеїв «підпис: значення».

Тихий бік цього був гірший за саму відсутність. Шаблони писали `path` у
текстовий блок, наче він працює; нормалізація його викидала мовчки, і на бланку
лишався «-» — тобто відсутність механізму виглядала як **заповнений бланк**.
Помітно це лише поглядом на папір, і тільки якщо прочерк опинився там, куди
дивляться.

Команда даних має повертати вже денормалізований payload: назви замість id,
пораховані суми, дати й гроші — рядками. Еталон — `app.invoice_print_data`
у [`invoice.custom.sql`](../app/document/invoice/db/invoice.custom.sql).

### Формат значення: сума прописом

З правила «рендерер не форматує» є рівно один виняток, і зроблений він свідомо.
Поле `field-list` і комірка таблиці приймають `format: "amountInWords"`, а мова
й валюта беруться з кореня шаблону:

```json
{ "schemaVersion": 2, "locale": "uk", "currency": "UAH", "blocks": [
  { "type": "field-list", "items": [
    { "key": "sum", "label": "Сума словами", "path": "document.total", "format": "amountInWords" }
  ]}
]}
```

**Чому в шаблоні, а не в команді даних.** Правило написання суми словами
належить МОВІ, а не застосунку, і кожен пише його однаково неправильно: рід
належить розряду («дві тисячі», але «два мільйони»), форма назви вибирається за
двома останніми цифрами (111 — «гривень»), порожній розряд усе одно називається
(1000 — «одна тисяча гривень»). Жодної з цих помилок не видно на 1234,56.
Шаблон при цьому вже знає мову — регламентована форма заводиться окремим
шаблоном на кожну, — а команда даних лишається без подання: те саме число
друкується і цифрами, і словами, не знаючи про це.

Умовчання — `uk` / `UAH`, тож шаблони, зроблені до появи формату, лишаються
чинними без міграції. Мови: `uk`, `ru`, `en`; валюта з неоголошеними формами
**відхиляється**, і — як помилкове значення штрих-кода — друкується числом, а не
валить документ. Тобто перевіряти треба надрукований результат, а не факт того,
що команда відпрацювала.

Перелік форматів закритий навмисно: «дата прописом» і «кількість прописом» сюди
не додаються. Реалізація — [`money-in-words.ts`](../server/modules/print/money/money-in-words.ts),
таблиця випадків поруч у пробах; звірено з `n2words` на 2011 числах, розбіжності
лише там, де грошова фраза вимагає жіночого роду одиниці.

## Таблиця: сітка й три секції

Таблиця — це **сітка колонок** плюс три секції, у кожній довільна кількість
рядків із комірок:

| Секція | Коли друкується | Корінь для шляхів |
| --- | --- | --- |
| `header` | на кожній сторінці | усі дані друку |
| `row` | по разу на кожен запис `source` | один запис |
| `footer` | один раз, після останнього запису | усі дані друку |

Секції необов'язкові: таблиця може бути без шапки або без підвалу.

Колонка несе тільки ключ і ширину — заголовки живуть у комірках, бо над однією
колонкою може стояти кілька рівнів заголовків. Комірка задає `colSpan`/`rowSpan`
(як у HTML), статичний `text` **або** прив'язку `path`; заповнений текст
перекриває прив'язку.

Класичний приклад — широка «Номенклатура», що на другому рядку ділиться на «Код»
і «Найменування»:

```json
"columns": [
  { "key": "num", "widthPercent": "8" },
  { "key": "id", "widthPercent": "14" },
  { "key": "name", "widthPercent": "30" },
  { "key": "sum", "widthPercent": "18" }
],
"sections": {
  "header": { "rows": [
    { "cells": [
      { "text": "№", "rowSpan": 2 },
      { "text": "Номенклатура", "colSpan": 2 },
      { "text": "Сума", "rowSpan": 2 }
    ] },
    { "cells": [{ "text": "Код" }, { "text": "Найменування" }] }
  ] },
  "row": { "rows": [
    { "cells": [{ "path": "index" }, { "path": "id" }, { "path": "name" }, { "path": "amount" }] }
  ] },
  "footer": { "rows": [
    { "cells": [
      { "text": "Разом", "colSpan": 3, "align": "right" },
      { "path": "document.total", "align": "right" }
    ] }
  ] }
}
```

Підсумки беруться **готовими з даних** (`document.total`): суму рахує SQL — там,
де вся інша арифметика документа, тож округлення гарантовано збігається.

Секція `row` може мати кілька рядків — тоді кожен запис друкується кількома
рядками, і при розриві сторінки запис не розсікається.

Шаблони, збережені до появи секцій (колонки з `title`/`path`), працюють без
міграції: нормалізатор підіймає їх у секції — рядок шапки із заголовків і рядок
даних із прив'язок.

## Регламентована форма: клітинки й повернутий текст

Дві речі, без яких український затверджений бланк надрукувати нема чим. Обидві —
властивості РЕНДЕРЕРА: обійти їх із боку застосунку не виходить ані полем, ані
таблицею, а спрощений бланк — це не спрощений документ, а неправильний.

### Поле по клітинках

Блок `char-cells`: одне значення, розрізане по символах, кожен у своїй рамці.
Так друкуються ІПН і ЄДРПОУ, РНОКПП, дата складання, порядковий номер
декларації — у затвердженій формі це рамка з квадратиків, у яку податкова
вписує цифри від руки.

```json
{
  "key": "seller_tax",
  "type": "char-cells",
  "path": "doc.sellerTaxNumber",
  "count": "12",
  "borderColor": "#262626",
  "lineWidth": "1",
  "placement": { "mode": "absolute", "xPercent": "22", "yPercent": "14", "widthPercent": "30.3", "heightPercent": "0" }
}
```

**Кількість клітинок береться із затвердженої форми, а не з довжини значення**
(ІПН — 12, РНОКПП — 10, дата — 8): порожні клітинки на бланку лишаються
порожніми, і це його нормальний вигляд. Значення береться за загальним правилом
формату — статичний `value` перекриває `path`.

**Ріже рендерер, форматує команда даних.** `22.06.2026` у восьми клітинках дасть
`2 2 . 0 6 . 2 0` — крапки теж символи. Дату під клітинки команда даних віддає
окремим полем (`to_char(d, 'DDMMYYYY')`), як і все інше в друку. Правило
«рендерер не форматує» тут не має винятку, і саме цим ця дірка небезпечна:
бланк виглядає заповненим.

Геометрія — з рамки блока, як у решти блоків: ширина клітинки це ширина рамки,
поділена на `count`. Окремого «розміру клітинки в міліметрах» немає навмисно —
він завів би другу систему координат поруч із розкладкою, і полотно редактора
почало б показувати не те, що піде на папір.

**Порожня висота означає КВАДРАТ** — клітинку заввишки в саму себе завширшки.
Це не зручність, а єдиний спосіб дістати квадрат не рахуючи: відсотки по двох
осях беруться від різних сторін аркуша, тож той самий квадратик записується
двома різними числами (клітинка 13 pt — це 2.52 % завширшки й 1.71 % заввишки).
Рамку розміряють від клітинки: `widthPercent = count × розмір ÷ 5.1528`, звідки
12 клітинок по 13 pt — 30.3 %. Задана висота сильніша за квадрат: клітинка
затвердженої форми буває й видовженою.

**Вирівнювання каже, ДЕ в рамці сидить коротке значення**, а не як символ
виглядає у клітинці (у своїй клітинці він завжди центрований — так надруковані
всі затверджені форми). Воно ж вирішує, який кінець задовгого значення
лишиться: при `left` — початок, при `right` — хвіст. Розтягнути рамку рендерер
не має права, кількість клітинок задана формою.

### Вертикальний текст

`"textOrientation": "90"` — текст читається знизу вгору. Стоїть у двох місцях:
у блоці `text` і в комірці таблиці. Умовчання `"0"`, тож наявні шаблони чинні
без міграції; приймається і `"90"`, і `90`.

```json
{ "type": "text", "value": "Звіт про використання коштів…", "textOrientation": "90" }
{ "text": "Ставка ПДВ", "fontWeight": "bold", "textOrientation": "90" }
```

Кут рівно один, і це не спрощення: серед 1590 макетів джерела (BAS Бухгалтерія
УКР) поворот стоїть у 27, і скрізь це 90°. Довільний кут дав би поле, яким ніхто
не користується, і арифметику розкладки, яку нічим перевірити.

Дві речі, що з повороту випливають:

- **У повернутого текстового блока висота рамки починає ДІЯТИ НА ДРУК.** Ролі
  сторін міняються місцями: рядок переноситься по висоті, а наступні рядки
  лягають праворуч. Висота не задана — текст іде одним рядком на всю свою
  довжину (саме так стоїть заголовок авансового звіту вздовж краю аркуша).
- **Повернута комірка не переноситься по словах**: її текст іде одним рядком, а
  висоту рядка таблиці задає ДОВЖИНА цього тексту. Інакше вийшла б рекурсія —
  щоб перенести, треба знати висоту, а висота залежить від переносу. Заради
  цього поворот у таблиці й потрібен: у колонці шириною 6 % горизонтальний
  заголовок або лізе на сусідню, або розсипається на стовпчик літер.

Вирівнювання в обох випадках діє вздовж напрямку читання — знизу вгору: `left`
притискає напис до низу, `right` — до верху.

## Багатосторінковий друк

Рядок таблиці, який не влазить до нижнього поля, починає нову сторінку —
**шапка колонок повторюється** на кожній. Це не «обрізання»: жоден рядок не
втрачається.

Решта блоків розділена за вертикаллю відносно першої таблиці:

- блоки **вище** таблиці (заголовок, реквізити) друкуються лише на першій
  сторінці;
- блоки **нижче** (разом, підписи) — на останній, одразу під кінцем таблиці.
  Якщо таблиця до них не дотягнулась, вони лишаються на своєму місці; якщо під
  них не лишилось місця — переносяться на нову сторінку цілком, зберігаючи
  взаємну розкладку.

Полотно редактора показує **першу** сторінку: воно не моделює переноси. Скільки
вийшло сторінок і як ліг підвал — видно на вкладці PDF.

Типи блоків: `text`, `field-list`, `table`, `image`, `barcode`, `char-cells`,
`horizontal-line`, `vertical-line`.

Розкладка абсолютна: `placement` задає `xPercent`/`yPercent`/`widthPercent`/
`heightPercent` у відсотках від області друку (A4 мінус поля 40pt). Числа
зберігаються рядками — щоб поле форми не «стрибало» під час набору; у числа їх
перетворює `resolvePrintTemplateBlockPlacement`.

**`yPercent` — це ВЕРХ блока, і однаково для всіх типів.** Вміст стоїть під цією
межею: рамка з клітинок висить під нею, картинка й таблиця починаються з неї,
текст відсунутий від неї вниз на висоту літери. Два блоки, які мусять стояти
поруч, несуть ОДНАКОВУ `yPercent` — поправки на тип блока не потрібно. До
server 0.23.0 текст був винятком (`y` означала базову лінію першого рядка, тобто
літери стирчали над рамкою), і бланки тих часів несуть підгонки, які тепер
зайві.

### Потоком, а не координатою

Координата правильна для ШАПКИ: вона відповідає затвердженій формі до
міліметра. Нижче шапки бланк складається з блоків, чия висота відома лише
після рендера — скільки рядків забрала шапка таблиці на дев'ятнадцять колонок,
на скільки рядків розсипався опис товару, де скінчилася перша таблиця. Записати
там координату означає ПЕРЕДБАЧИТИ те, що ядро порахує пізніше, а перевірити
передбачення можна лише готовим PDF.

Тому блок може стати `placement.mode: "flow"` — під попереднім блоком СПИСКУ,
хай де той скінчився:

```json
{ "key": "section_b_caption", "type": "text",  "value": "Розділ Б",
  "placement": { "mode": "flow", "gapPt": "10", "xPercent": "0", "widthPercent": "100" } }
{ "key": "section_b", "type": "table",
  "placement": { "mode": "flow", "gapPt": "4", "xPercent": "0", "widthPercent": "100" } }
```

П'ять речей, які варто знати наперед:

- **порядок беруть зі СПИСКУ блоків**, а не з координат: «попередній» — це
  попередній елемент `blocks`. Абсолютний блок теж рухає курсор, тож стос
  законно починається під шапкою;
- **`yPercent` у потоці лишається** й нічого не вирішує на папері — це місце
  рамки на полотні редактора. Поле там так і підписане;
- **блок, який не влазить, іде на наступну сторінку цілим**; `keepTogether`
  («не відривати від наступного») тримає на одній сторінці цілу групу — саме
  так виражається «підпис не відривати від твердження». Таблиця цього не слухає:
  вона розривається сама, по записах;
- **розрив сторінки оголошується, а не вгадується** — `pageBreakBefore: true`
  на блоці:

  ```json
  { "key": "back_title", "type": "text", "value": "Зворотний бік акта",
    "pageBreakBefore": true,
    "placement": { "mode": "flow", "gapPt": "0", "xPercent": "0", "widthPercent": "100" } }
  ```

  Це НАМІР, і його не замінює ніщо з переліченого вище: потік переносить те, що
  не влізло, `keepTogether` тримає групу вкупі, евристика підвалу дивиться на
  залишок місця. Затверджена двобічна форма (НА-1, НА-3, М-2, інвентаризаційний
  опис із розпискою на звороті) вимагає протилежного: зворотний бік починається
  з нового аркуша ЗАВЖДИ, хоч би лицьовий зайняв півсторінки. Читається лише в
  режимі `flow`, як і `keepTogether`; на ПЕРШОМУ блоці бланка не діє — порожній
  перший аркуш це не розрив, а зламаний друк;
- **досить одного блока з `flow`, щоб евристика підвалу вимкнулась на всьому
  бланку** (див. нижче). Це навмисно: два механізми вертикалі в одному бланку —
  це той самий здогад, від якого потік і рятує.

### Шапка з переліку граф — коротка форма

Затверджена форма майже завжди має дворівневу шапку: «Номери» над трьома
графами, «Дорогоцінні метали» над трьома, а решта граф займає обидва рівні. У
секціях це `colSpan`/`rowSpan` — на двадцяти чотирьох графах (ОЗ-6) двадцять
чотири числа, кожне з яких помиляється ТИХО: сітка з'їде на графу, шаблон
лишиться валідним, а розбіжність побачить той, хто звірятиме папір із бланком.

Колонка може назвати саму графу:

```json
"columns": [
  { "key": "c_inv",    "width": "4%",   "header": "Номери", "headerSub": "інвентарний" },
  { "key": "c_serial", "width": "5.5%", "header": "Номери", "headerSub": "заводський" },
  { "key": "c_year",   "width": "3%",   "header": "Рік випуску (побудови)" }
]
```

Об'єднання не задають — воно **виводиться**: сусідні графи з однаковою `header`
склеюються в комірку верхнього рівня, графа без `headerSub` займає обидва рівні,
а перелік без жодного `headerSub` дає однорядкову шапку. Той самий крок, що
зроблено з ширинами: шаблон називає намір, геометрію рахує ядро.

Три межі:

- **склеюються лише СУСІДНІ графи** — порядок колонок це порядок граф у формі,
  тож «Номери» на початку бланка й «Номери» в кінці лишаються двома
  об'єднаннями;
- **написана руками шапка сильніша**: коротка форма діє, лише поки
  `sections.header` порожня. Три рівні, шапка з прив'язкою до даних, порожні
  комірки-роздільники — усе це й далі пишеться секціями;
- **комірки виходять по центру й напівжирними** — об'єднана комірка над трьома
  графами, притиснута ліворуч, не схожа на жоден затверджений бланк. Колонка,
  якій треба інакше, каже `headerAlign` / `headerFontWeight`.

Схована колонка (`visibleWhen`) виведеній шапці не шкодить: `colSpan` план
рендеру перераховує сам, як і для написаної руками.

### Евристика підвалу — для бланків без потоку

Доти вертикаль тримало одне правило: усе, що нижче ПЕРШОЇ таблиці, вважається
підвалом і малюється зсунутим під ОСТАННЮ. Воно працює на бланку з однією
таблицею й ламається на двох: підпис між ними зараховується до підвалу і їде на
другий аркуш разом із підписами, хоча місця на першому вистачало. Правило
лишається чинним рівно для шаблонів без жодного `flow` — щоб наявні бланки не
поїхали.

### Куди що стало: звіт про розкладку

`renderPrintPdfWithLayout(template, data)` віддає байти РАЗОМ із переліком
блоків: ключ, тип, сторінка початку й кінця, `topPt`/`bottomPt` (координати
PDF — вісь y росте вгору) і `overflow`. Це те, що ядро й так знає в момент
малювання; доти воно це викидало, і застосунок з'ясовував своє місце
розпакуванням потоку готового PDF.

```ts
const { bytes, layout } = await renderPrintPdfWithLayout(template, data);
layout.filter((block) => block.overflow);           // що не влізло
layout.find((block) => block.key === "section_b");  // де саме стала таблиця
```

`renderPrintPdf` лишився як був — віддає самі байти.

## Штрих-коди

Блок `barcode` — три символіки:

| `symbology` | Для чого | Що приймає |
| --- | --- | --- |
| `code128` | документи: номер накладної, код замовлення | будь-який ASCII 32–126 |
| `ean13` | номенклатура, цінники | 12 або 13 цифр |
| `qr` | посилання, платіжні рядки, службові дані | довільний текст, зокрема кирилицю |

```json
{
  "key": "number_barcode",
  "type": "barcode",
  "symbology": "code128",
  "path": "document.number",
  "value": "",
  "showText": true,
  "placement": { "mode": "absolute", "xPercent": "72", "yPercent": "0", "widthPercent": "28", "heightPercent": "6" }
}
```

Значення береться так само, як у комірці таблиці: **статичний `value` перекриває
прив'язку `path`**. Одне правило на весь формат.

**Висота діє на друк** (як у зображень і ліній). Не задана — 40pt ≈ 14 мм: нижче
ручні сканери починають вимагати точного прицілювання. QR квадратний і бере
меншу зі сторін рамки, тож ширину для нього зазвичай зменшують.

**Кольору в блока немає навмисно.** Штрих-код мусить бути чорним на білому,
інакше сканер його не візьме; поле кольору було б способом зіпсувати документ,
який на екрані виглядає нормально. Налаштування `text` стосуються лише підпису
під кодом — вирівнювання й насиченості там теж немає, підпис завжди центрований.

**Тихі зони входять у код.** Порожні поля з боків — частина символіки, а не
відступ розкладки; якби вони лишалися рендереру, код, поставлений впритул до
краю рамки, перестав би зчитуватися. Тому Code 128 отримує по 10 модулів з
кожного боку, EAN-13 — 11 зліва й 7 справа, QR — 4, і все це масштабується
разом із кодом.

**Помилкове значення друкується текстом** на місці коду, а не пропускається:
порожнє місце в накладній ніхто не помітить, і партія товару поїде без коду.
Так само поводиться EAN-13 із невірною контрольною цифрою — вона не
виправляється мовчки, бо розбіжність означає помилку в довіднику.

Code 128 автоматично переходить у Code C на довгих цифрових ділянках — номер
документа виходить удвічі коротшим за той самий номер, набраний посимвольно.

### Чому QR — залежність, а решта ні

Code 128 і EAN-13 — це таблиця шаблонів і контрольна сума: десятки рядків, які
перевіряються інваріантами (сума модулів, унікальність шаблонів, охоронні
послідовності). QR — це коди Ріда — Соломона, вибір версії й вісім масок;
написане з голови без еталонного декодера воно з високою ймовірністю дало б код,
який виглядає правильним і не читається. Тому матрицю дає `qrcode-generator`
(без власних залежностей), а прямокутники з неї малюємо самі — у браузер вона
не потрапляє взагалі.

Перевіряються символіки юніт-пробами: `deno task test:unit`. Це той рідкісний
випадок, коли помилку не видно ні на екрані, ні в PDF — вона виявляється аж
сканером на складі, тому тести стережуть саме таблиці, а не «щось намалювалося».

## Джерело правди шаблону в рантаймі

Рантайм читає шаблони **тільки з `app.print_template`** — жодних файлів шаблонів
на диску. Файли в `prints/` — це вихідний код системних шаблонів; `sql:assemble`
перетворює їх на `insert ... on conflict (code) do nothing`, тож відредагований
користувачем шаблон публікацією не затирається.

Виняток — `"republishOnPublish": true` у файлі шаблону: для таких `sql:publish`
виконує окремий `on conflict (code) do update` і **перезаписує** рядок у базі
разом із правками користувача. Ставте прапорець свідомо; щоб просто оновити
системний шаблон разово, простіше видалити рядок і опублікувати наново.

Підбір шаблону — `app.print_template_resolve`: явно вказаний `templateCode`,
інакше шаблон із `is_default`, інакше найсвіжіший активний.

## Редактор

`admin/print_template/edit` — звичайна admin-форма: реквізити шаблону, список
блоків, панель властивостей вибраного блока і дві вкладки перегляду.

**PDF** малює **ядро**: редактор шле чернетку шаблону разом із даними в команду
`preview` (`runtime.printPreview`) і показує повернутий PDF в `<iframe>`. Тому
прев'ю не може розійтися з друком — це той самий рендерер. Перемальовується
через 0,7 с після останньої правки або кнопкою «Оновити».

**Розкладка** — полотно для миші: аркуш A4 з тими самими полями (40pt), що й у
рендерера, і рамки блоків поверх нього. Тягати рамки прямо по PDF не можна:
вбудований переглядач додає власні поля й масштаб, і рамки з ним не збіглися б.

У рамках — **схематичний** вміст: текст, «підпис: значення», шапка й перші рядки
таблиці зі справжніх даних прев'ю. Розміри шрифтів переведені в `cqw`
(1cqw = 1 % ширини аркуша), тому пункти лягають на екран у масштабі. Але це
навмисно НЕ рендер друку: перенесення рядків, розриви сторінок і точні метрики
шрифтів тут не відтворюються — контракт вигляду показує вкладка PDF.

На полотні: перетягування блока, зміна розміру кутовою ручкою, прилипання до
країв, центру аркуша та меж сусідніх блоків із помаранчевими напрямними,
стрілки — зсув на 1 % (з Shift — 5 %), Alt+стрілки — розмір, Escape — зняти
виділення. У схему зміна потрапляє на відпускання кнопки, тож прев'ю не
смикається під час жесту.

Висоту можна міняти в будь-якого блока, але **на друк вона впливає лише для
зображень, ліній, штрих-кода й поля по клітинках** — там її читає рендерер (у
поля по клітинках порожня висота означає квадратну клітинку). Для
тексту, списку полів і таблиці вміст ллється від верху рамки, а висота лишається
розміткою: місцем, яке блок займає на аркуші, щоб було видно, що на що не
налазить. У панелі властивостей таке поле підписане «Висота, % (розмітка)».
Виняток — **повернутий** текстовий блок: у нього висота задає довжину рядка, і
підпис поля це чесно каже.

Таблиця редагується сіткою секцій просто в панелі властивостей: клік вибирає
комірку, Shift+клік — прямокутний діапазон, кнопки «Об'єднати» / «Розбити»
працюють як в Excel. Виділення, що зачепило половину вже об'єднаної комірки,
розширюється до її цілих меж — розсікти комірку навпіл неможливо.

Щоб з'явилися шляхи для прив'язки полів, у панелі «Дані прев'ю» вкажіть payload
(напр. `{ "id": "1" }`) і натисніть «Завантажити дані» — редактор виконає ту саму
команду, що потім виконає рантайм друку, і побудує список шляхів із відповіді.
