# Оновлення фреймворку і прикладного рішення

Записано 2026-08-06.

Раніше цей док починався з двох сценаріїв, які **обирала людина**: «рішення не
змінювали» і «рішення змінювали». Тепер це не вибір, а **стан, який система про
установку знає** — див. розділ 1. Дії від нього й залежать.

---

## 0. Що взагалі оновлюється, і хто називає версію

Оновлюються дві різні речі, і в різний спосіб:

- **фреймворк** — пакети `@altera/*` з JSR (у контейнерній розкладці — образ);
- **рішення** — каталог `app/` цілком, приїжджає пакетом `.tar.gz`.

**Версію фреймворку називає рішення, а не навпаки.** Манифест пакета несе піни,
під якими рішення зібране; завантаження звіряє їх із приймачем і **зупиняється**,
якщо приймач старіший або мажорно інший. Звідси головне правило: патчі фреймворку
можна тягнути будь-коли, мінори — лише разом із рішенням, зібраним під них.
Приклад, чому це не теорія: `@altera/tools` 0.4 → 0.5 розділив згенерований
реєстр на два файли, і `app/server.ts` мусив змінити імпорт.

### Де живуть піни

У `deno.json` застосунку пінів десять, у **двох різних місцях**: в `imports`
(їх бачить `deno outdated`) і в рядках задач `sql:registry`, `sql:gen`,
`solution:*`, `skills:sync` — це просто текст, його править тільки рука.
Пін = `^` + та сама версія скрізь; `@altera/client` рухається разом із мажором
`vite` і версією `@altera/skills`.

### Спільне для всіх випадків

- **Перед оновленням — дамп бази.** Схема накочується вперед ідемпотентно;
  **назад міграції не ходять** — відкат схеми це відновлення дампа.
- **`deno.lock` має бути в дереві.** Без нього Deno резолвить версії наново при
  кожному запуску й на щойно опублікованій версії фреймворку впирається в
  політику мінімального віку залежності — причому в рантаймі, де це схоже на
  зламаний застосунок. Створює його `deno install`.
- Після оновлення `@altera/client` — `deno task skills:sync`.
- `vendor/` не редагується ніколи: наступний `deno install` затре.

## 1. Підтримка: стан, а не вибір

**Установка знає, чи чіпали `app/` після поставки.** Манифест поставки
(`app/.solution.json`, кладе його завантаження) несе SHA-256 кожного файлу;
звірка з диском дає відповідь.

```bash
deno task solution:status
```

Три стани, і третій плутати з першими двома не можна:

| Стан | Що означає | Що робить оновлення |
|---|---|---|
| **на підтримці** | дерево збігається з поставкою | заміняє `app/` цілком, **автоматично** |
| **знято з підтримки** | хоч один файл змінено/додано/видалено | `app/` **не чіпає**, кладе пакет у `app.incoming/` і друкує, чого торкнулися обидві сторони |
| **невідомо** | манифесту немає (рішення розклали руками або старим інструментом) | нічого не робить без `--force`: звірити нема з чим |

Головне в цьому — **оголошувати нічого не треба**. На відміну від 1С, зняття з
підтримки не є дією: правка одного файлу переводить установку в ручний режим
сама, і цим захищає саму себе від наступного автоматичного оновлення. Забути це
неможливо, збрехати теж.

`--force` лишається як «знаю, затри мої правки».

Застосунок той самий стан показує на стартовій вкладці — але тільки показує:
установку він не робить (розділ 2).

## 2. Оновлення: окрема команда

```bash
deno task solution:update -- ./erp-1.2.0.tar.gz --check   # подивитися
deno task solution:update -- ./erp-1.2.0.tar.gz           # застосувати
```

Один прохід: перевірка підтримки → `deno install` → розпакування →
`sql:registry` → `sql:deploy --yes` → `build:front`. На знятому з підтримки
ланцюжок **не запускається** — `app/` не змінився, перебудовувати нема чого.

**`deno install` іде першим, до розпакування, і це не косметика.** Свіжа
установка залежностей ще не має, а `sql:registry` без них не падає — він
мовчки випускає порожні схеми інструментів агента (`agent-tools.generated.ts`
у двадцять разів менший), і застосунок лишається з агентом, який не бачить
жодної команди. До розпакування — щоб невдала установка залежностей лишила
рішення ЦІЛИМ: піни живуть у `deno.json` каркаса, з пакета тут не ставиться
нічого.

Один випадок, коли цей крок відмовляє на щойно розгорнутій установці: `deno.lock`
ще немає, піни резолвляться з реєстру, а щойно опублікований реліз фреймворку
молодший за добу — спрацьовує політика мінімального віку залежності. Інструмент
називає це прямо й пропонує `deno install --min-dep-age=0`; знімати політику за
адміністратора він не буде.

Наприкінці треба **перезапустити застосунок**: реєстр моделей імпортується
статично, тож працюючий процес далі віддає попередні екрани.

### 2.1 Звідки береться пакет

Аргумент — не обов'язково файл на диску. Форм три, і вид джерела виводиться з
вигляду рядка, а не з прапорця:

```bash
deno task solution:update -- ./erp-1.2.0.tar.gz              # файл
deno task solution:update -- https://…/erp-1.2.0.tar.gz      # прямий URL
deno task solution:update -- IgorAIvanov/altera-buh@1.2.0    # реліз GitHub
deno task solution:update -- IgorAIvanov/altera-buh@latest   # останній реліз
```

`@latest` — не «найсвіжіший тег», а останній **реліз**: чернетки й передрелізи
GitHub сюди не віддає.

**Приватний репозиторій — випадок звичайний**, і потрібен токен із правом
читання: `GITHUB_TOKEN` (або `GH_TOKEN`) у `.env` установки. Обидві задачі
читають його через `--env-file`. Без токена GitHub відповідає **404, а не 403** —
приватний репозиторій він не показує навіть фактом існування, тож «релізу не
знайдено» на відомий тег означає саме брак токена, і команда так і каже.

Завантажений пакет лягає в тимчасовий файл і після роботи прибирається: тримати
його ні до чого, бо повернутися до попередньої версії тепер означає **назвати**
її (`owner/repo@1.1.0`), а не шукати архів на диску.

Якщо в релізі кілька `.tar.gz`, інструмент не вибирає сам — перелічує їх і
вимагає `--asset <ім'я>`. Архіви «Source code», які GitHub чіпляє до релізу
завжди, поставкою не є: у них немає `solution.json`.

Та сама форма приймається і в `solution:import`. Вона переживе GitHub: коли
поставки переїдуть в окремий каталог застосунків, зміниться те, у що резолвиться
`власник/рішення@версія`, а не рядок, який набирає адміністратор.

**Частковий пакет** (набір моделей, `solution:export --models`) ця команда не
бере: оновлення установки означає поставку, а набір моделей нею не є — він не
описує рішення цілком, тож і «оновити до нього» нема куди. Такі пакети додає
`solution:import`, і це інструмент розробки, а не експлуатації —
[`solution-transfer-plan.md`](solution-transfer-plan.md), розділ 5.

**Чому окремою командою, а не кнопкою в застосунку.** Той, кого заміняють, не
має заміняти себе сам: кнопка всередині сервера могла переписати власний `app/`,
а перезапуститися після цього — ні. Заразом серверу доводилося давати
`--allow-write` і `--allow-run`, тобто право переписати свій код і запустити
будь-що. Тепер ці дозволи потрібні разово оновлювачу, а обслуговуючий процес
назавжди лишається з `--allow-net --allow-read --allow-env`.

## 3. Приватний сервер

### 3.1 Без контейнера

```bash
pg_dump > backup-$(date +%Y%m%d).sql
deno task solution:update -- ./erp-1.2.0.tar.gz --check
```

`--check` скаже й про стан підтримки, і про те, чи новому рішенню потрібен
новіший фреймворк. Якщо потрібен — спершу підняти піни (обидва місця, розділ 0)
і `deno install`. Далі те саме без `--check` і перезапуск сервісу.

Оновлення **лише фреймворку** (патч, виправлення безпеки): `deno outdated
--update && deno install`, потім обов'язково `deno task sql:assemble &&
deno task sql:deploy --yes` (ядро могло привезти міграції) і `build:front`.
Мінор фреймворку без нового рішення не тягнути.

### 3.2 У контейнері — рекомендований вигляд

Образ несе **фреймворк**, рішення живе на томі:

```
образ:  Deno, deno.json із пінами, vendor/, node_modules/, scripts/, vite.config.ts
том:    app/ (разом із .solution.json і _sqlpackage/) і dist/
```

```bash
docker compose --profile prod build
cp ./erp-1.2.0.tar.gz ./packages/
docker compose --profile prod run --rm update /srv/packages/erp-1.2.0.tar.gz
docker compose --profile prod restart app
```

Звідси два **незалежні** шляхи оновлення — саме заради цього розкладка й
потрібна:

- **нове рішення** → розпакувати на том і зібрати; образ той самий;
- **новий фреймворк** → замінити образ; том той самий.

**Заміна образу вимагає перезбірки**, і це головне правило цієї розкладки. На
томі лишаються `dist/` і `app/_sqlpackage/`, зібрані попередньою версією
фреймворку: у першому вбитий його клієнтський код, у другому — SQL ядра.
Піднявши новий образ без перезбірки, дістанете сервер однієї версії з бандлом і
схемою від іншої. Помітно це не одразу. Розбіжність показує
`deno task solution:status`: манифест поставки несе піни, якими артефакти
зібрані.

Що дає контейнер понад зручність: **незмінність рішення перестає бути
домовленістю**. Обслуговуючий контейнер монтує `app/` і `dist/` лише на читання,
писати може тільки разова служба `update`.

Чотири пастки, знайдені складанням і запуском (усе нижче — не передбачення):

- **`deno install` треба повторити після копіювання `app/`**, і саме
  `--entrypoint ./app/server.ts`: карта імпортів не знає про прямі
  специфікатори в коді (`jsr:@std/http@…`), і без цього кроку контейнер на
  кожному старті йде в мережу, а в закритому контурі не піднімається;
- **`DENO_DIR` треба перенести в рантайм-шар**, інакше старт іде в
  `registry.npmjs.org` по метадані пакетів;
- **`PGPORT` і `PORT` перекриваються в compose обов'язково**: у `.env` лежать
  порти, **опубліковані на хост**, а в мережі compose база слухає 5432 і
  застосунку нема сенсу слухати щось крім 3000;
- **`PGSSLMODE: disable` для бази в мережі compose**: TLS виводиться з хоста, і
  `db` під локальні не підпадає — з'єднання рветься на рукостисканні. Для
  **зовнішньої** бази рядок прибрати, там запобіжник має спрацювати.

Ще дві дрібниці, які видно лише в цій розкладці:

- **пакет рішення кладуть у `./packages`** — цей каталог змонтований у службу
  `update`; шлях, який видно з хоста, зсередини контейнера не існує;
- **`./app.incoming` теж змонтований**, і це не дрібниця: без тому каталог, у
  який лягає поставка при знятті з підтримки, створювався б в ефемерному шарі
  контейнера й зникав разом із ним. Гілка «не чіпати `app/`, покласти поруч»
  спрацьовувала б, а класти було б нікуди — причому мовчки;
- **перша установка в свіжий scaffold вимагає `--force`**: демо-застосунок
  шаблону манифесту поставки не має, тобто стан «невідомо», а мовчки затирати
  невідоме інструмент не буде.

Свіжий реліз фреймворку: `--build-arg DENO_INSTALL_FLAGS=--min-dep-age=0`.

**Контейнерна розкладка й Git складаються без зусиль** (перевірено). Контейнер
пише в змонтований каталог, тобто просто в робоче дерево на хості: після
`update` звичайний `git status` показує оновлення рішення нормальними змінами —
змінені, видалені, додані файли. Сам `.git` усередину не монтується, і не
треба: git-операції робить людина на хості. Тому сценарій із гілкою `vendor`
(розділ 4) працює й тут — контейнер лише розкладає файли.

Дві дрібниці, які з цього випливають і вже враховані в шаблоні: `packages/` і
`app.incoming/` у `.gitignore` (інакше тарболи й проміжний каталог засмічували б
`git status`), а `app/.solution.json` навпаки відстежується — у дифі видно, яка
поставка встановлена. І одне попередження для Linux: там Docker пише від root,
тож файли в робочому дереві дістануться root — на Docker Desktop (Windows/macOS)
власником лишається користувач.

## 4. Змінене рішення й Git

Коли `app/` правлять, стан підтримки сам стає «знято» — і оновлення перестає
бути автоматичним. Пакет лягає в `app.incoming/` разом зі списком того, чого
торкнулися обидві сторони. Але зводити правки краще не каталогами, а Git: **те,
що в 1С робить порівняння конфігурацій, тут уже вміє `git merge`.**

### 4.1 Разова підготовка: гілка `vendor`

```bash
git branch vendor <коміт, де рішення ще незмінне>
```

У неї не комітиться нічого, крім поставок. Завести її треба **до першої власної
правки**: базою злиття має бути незмінене дерево, і заднім числом воно не
відновлюється.

### 4.2 Кожна поставка

```bash
git switch vendor
deno task solution:import -- ./erp-1.2.0.tar.gz . --force
git commit -am "vendor: erp@1.2.0"

git switch master
git merge vendor
```

Заміна цілком у гілці `vendor` — не грубість, а точність: гілка і є знімком
стану постачальника. Конфлікти — не збій, а **список місць, які треба
адаптувати свідомо**; природне місце для агента, бо він бачить обидва наміри.

Далі в тому ж PR: підняти піни, якщо `--check` про них казав; `deno install`;
`sql:registry`, `deno check`, `build:front`, свої проби; рев'ю, зелений CI.

### 4.3 Прод

Тільки з Git, штатною публікацією. **Кнопки установки більше немає взагалі**, а
`solution:update` на проді в цьому режимі запускати не можна: він замінить `app/`
повз Git, і наступна публікація мовчки відкотить рішення.

## 5. Deno Deploy

**Git обов'язковий**: розкат іде з GitHub-репозиторію, файлова система лише для
читання — ні контейнерна розкладка, ні `solution:update` там не працюють.

Незмінене рішення оновлюється без гілки `vendor`:

```bash
deno task solution:import -- ./erp-1.2.0.tar.gz . --check
deno task solution:import -- ./erp-1.2.0.tar.gz .
git commit -am "solution: erp@1.2.0" && git push
```

Далі все робить платформа: `build` збирає SQL-пакет і фронтенд, `predeploy`
накочує схему тими самими змінними, що бачить застосунок. Ревізія і є
перезапуск.

## 6. Підсумок

| | Приватний сервер | Контейнер | Deno Deploy |
|---|---|---|---|
| Оновити рішення | `solution:update` | `run --rm update` | `import` → commit → push |
| Оновити фреймворк | піни + `deno install` | замінити образ **+ перезбірка** | піни + push |
| Незмінність рішення | домовленість | властивість (том `:ro`) | Git |
| Стан підтримки | `solution:status` | те саме, з образу | `solution:status` локально |
| Відкат рішення | попередній пакет | попередній тег образу | `git revert` |
| Відкат схеми | дамп | дамп | дамп |
