# Нумерація: коди довідників і номери документів

**Статус:** план виконано цілком 2026-08-09 — кроки 1–5 (ядро, обгортка
`doc_next_number`, сід із манифестів, генератор CRUD, схеми й форми), потім
рефакторинг за наслідками архітектурного огляду (розділ нижче), потім 6
(`bank.code` → МФО) і 7 (admin-екран нумераторів); 8 вийшов частиною кроку 3.
Замінює пункт 5.2 [`development-plan.md`](development-plan.md).

## Що є сьогодні

**Документи** нумеруються — `app.doc_next_number(type_code, org_id)` у
[`server/sql/document_core/db/document_core.sql`](../server/sql/document_core/db/document_core.sql):
номер = `organization.prefix` + `document_type.prefix` + `lpad(N, 6)`. Правило зашите в
тіло функції, налаштовуються лише два префікси. Три вади:

- лічильник **наскрізний за весь час** — розходження з українською практикою, де
  нумерація починається спочатку щороку;
- `max(substring(number from '[0-9]+$'))+1` — повне сканування документів типу і
  **гонка**: два одночасні записи беруть той самий максимум, один падає на
  `uq_document_number`;
- номер видаленого останнього документа **перевикористовується** — два різні документи
  в різний час отримують один номер.

**Довідники** кодів не видають узагалі: `code` скрізь `not null unique` і вводиться руками.
Але «код» у них — три різні речі, і однакового рішення в них бути не може:

| Модель | Що таке `code` | Рішення |
|---|---|---|
| `currency` | ISO 4217 (`USD`) | зовнішні дані — лишається ручним |
| `chart_of_account` | ключ плану рахунків, на нього посилаються проводки | природний ключ — лишається ручним |
| `bank` | `varchar(9)` поряд із `mfo varchar(6)` — дубль | `code` прибрати, кодом банку стає МФО |
| `counterparty`, `nomenclature`, `organization` | сурогат, поза системою сенсу не несе | нумератор |

## Чому не «показувати id замість коду»

`id` не можна ні зарезервувати, ні дати йому префікс, ні зберегти при перенесенні
рішення (`solution:import` заливає `app/`, а ідентифікатори в базі приймача свої). Код
диктують по телефону і пишуть на папері. Тож розвилка насправді інша: **авто-код або
коду немає взагалі** — показувати технічний ключ під іменем «Код» гірше за обидва
варіанти. Для `counterparty`/`nomenclature`/`organization` обрано авто-код.

## Рішення: один нумератор на застосунок

Не два механізми (документи окремо, довідники окремо), а одна таблиця. Оголошення —
у `manifest.json` моделі, живе правило й лічильник — у базі, екран — в `app/admin/numerator/`.

Це рівно той шлях, яким уже їдуть шаблони друку: манифест сіє рядок, далі його
редагують на екрані, деплой правку не затирає (`on conflict do nothing` у
[`assemble-sql-package.ts:310`](../tools/assemble-sql-package.ts:310)).

### Оголошення в манифесті

```json
"numbering": { "field": "code",   "template": "{NNNNNN}" }                               // довідник
"numbering": { "field": "number", "template": "{ORG}{TYPE}-{NNNNNN}", "period": "year" } // документ
```

`strategy` в манифесті необов'язкова — умовчання `counter` (див. нижче). Оголошувати її
варто лише там, де свідомо обрано `sequence`.

Плейсхолдерів п'ять, шаблонізатора немає свідомо:

| | |
|---|---|
| `{ORG}` | `organization.prefix` |
| `{TYPE}` | `document_type.prefix` |
| `{YYYY}` / `{YY}` | рік дати документа |
| `{MM}` | місяць |
| `{NNN…}` | лічильник, ширина = довжина плейсхолдера |

Усі п'ять — про **вигляд** номера. Період лічильника вони не задають: `{YY}` у
шаблоні означає лише «рік надруковано», а обнуляє лічильник `period` (див. нижче).

### Таблиці (ядро, новий пакет `server/sql/numerator/`)

```sql
create table if not exists app.numerator (
  model       varchar(100) primary key,        -- ключ моделі з manifest.json
  name        varchar(255) not null,
  template    varchar(50)  not null,
  period      varchar(10)  not null default 'none'
              check (period in ('none', 'year', 'month')),
  strategy    varchar(20)  not null default 'counter'
              check (strategy in ('counter', 'sequence')),
  is_editable boolean      not null default true,
  updated_at  timestamptz  not null default now()
);

create table if not exists app.numerator_state (
  model      varchar(100) not null references app.numerator (model) on delete cascade,
  scope_key  varchar(100) not null,            -- '' коли область глобальна
  last_value bigint       not null default 0,
  constraint pk_numerator_state primary key (model, scope_key)
);
```

### Період лічильника — окреме поле, а не наслідок шаблона

Перший варіант цього плану виводив період із шаблона: є `{YY}` — обнуляється щороку.
Виглядало елегантно й **виявилося хибним по суті**: нумерація в межах року потрібна
майже всім, а рік у самому номері друкують далеко не всі. Виведення з шаблона
змушувало б їх вибирати між форматом номера й обліковим правилом — тобто формат
диктував би облік.

Тому шаблон задає **вигляд** номера, а `period` (`none` | `year` | `month`) — **коли
лічильник починається спочатку**. Одне з одного не виводиться.

Тоді чому це безпечно, адже саме проти мовчазного розходження й був той інваріант?
Бо унікальність тримає не форма номера, а **індекс по даті документа**:

```sql
create unique index uq_document_number on app.document
  (document_type_id, organization_id, number, date_trunc('year', doc_date));
```

Окремого стовпчика з періодом при цьому немає — дата в документі вже є, а копія
поруч із нею була б другим місцем для того самого факту. Звідси єдина межа: рік у
виразі **зашитий**, бо індекс один на таблицю, а `period` — рядок конфігурації.
`none` лягає без натяжки (при наскрізному лічильнику номери й так не повторюються),
а `month` вимагає `{MM}` у шаблоні — інакше січневий і лютневий №1 зіткнулися б у
річному ключі. Це і є єдине правило, що зв'язує період із шаблоном, і в нього тепер
справжня причина; перевіряє його `app.numerator_validate`.

Період береться з **дати документа**, тож довідник лишається на `none`: дати в нього
немає, а підставити `now()` не можна — код, виданий у січні, потрапив би в інший
період, ніж грудневий.

Попередження про порожні префікси показує екран нумераторів (крок 7): якщо
шаблон містить `{ORG}`, а префікси організацій порожні, індекс номери пропустить
(організація в ключі окремо), але людина їх не розрізнить — тому попередження,
а не відмова.

### Видача номера

```sql
app.numerator_next(p_model varchar, p_scope jsonb) returns varchar
```

`p_scope` несе факти, відомі на момент запису: `{"orgId": 3, "date": "2026-08-09"}`.
Функція будує `scope_key` з цих **фактів** (організація відома — вона в ключі,
плюс ключ періоду з дати) і бере наступне значення способом, який оголошено в
`strategy`.

**Із шаблона область не виводиться** — той самий принцип, що й у `period`.
Перша версія ділила лічильник по організаціях лише коли `{ORG}` надруковано в
номері: прибрати префікс із номера означало б мовчки злити лічильники всіх
організацій. А розходження тут типове, не екзотичне: кожна юрособа нумерує
свої документи незалежно, але префікс організації в номері друкують далеко не
всі. Область із фактів ще й збігається за побудовою зі складом
`uq_document_number`, куди `organization_id` входить незалежно від шаблона.

### Дві стратегії лічильника

Це справжня розвилка, і вона не про «розриви або ні», як здається спершу, а про
**пропускну здатність проти суцільної нумерації**. Обидві налаштовуються на екрані
нумератора, обидві дають однаковий номер — різниця лише в тому, що відбувається при
відкаті транзакції та при одночасному записі.

**`counter` — умовчання, суцільна нумерація.** Лічильник — рядок звичайної таблиці:

```sql
insert into app.numerator_state (model, scope_key, last_value)
values (p_model, v_scope_key, 1)
on conflict (model, scope_key) do update
  set last_value = app.numerator_state.last_value + 1
returning last_value into v_next;
```

Це звичайний DML, тому при відкаті транзакції **лічильник відкочується разом із нею** —
номер повертається, дірки не лишається. Одночасні записи в одну область серіалізуються:
блокування рядка лічильника тримається до кінця транзакції. Блокується саме рядок
лічильника, а не таблиця документів, і лише в межах своєї області — сусідня організація
чи наступний рік не чекають.

**`sequence` — швидка, з розривами.** Окрема послідовність на кожну область,
`nextval()`. Послідовності навмисно нетранзакційні: вони не блокують паралельних
писарів і не відкочуються, тобто відкат лишає дірку в нумерації назавжди. Це вибір для
потокового введення, де важлива пропускна здатність, а не суцільність.

Ціна `sequence`, яку варто знати до вибору: послідовність доводиться створювати
динамічним DDL при першій потребі (`create sequence if not exists`), ім'я виводиться
хешем від `model` + `scope_key` (обмеження в 63 символи), і вони накопичуються — по
одній на кожну пару «організація + рік». Прибирати їх нема потреби, але в `pg_class`
їх видно.

**Розриви тут не з'являються навіть від видалення** — і це не властивість нумератора, а
наслідок того, що `delete` у системі лише **позначає** запис. Виданий номер назавжди
лишається за видимим рядком, тож при `counter` нумерація суцільна по-справжньому, а не
«суцільна, доки нічого не видалили». Через це не знадобилася й третя стратегія — видача
номера при проведенні: вона потрібна там, де чернетка може зникнути безслідно.

### Ще одне, що мовчки вирішиться неправильно

**Рік береться з `doc_date`, а не з `now()`.** Документ, введений заднім числом у грудень,
мусить отримати торішній лічильник. Зворотний бік: зміна дати вже записаного документа
номер **не** змінює — інакше нумерація перекладалася б заднім числом.

**Номер береться якомога пізніше в транзакції.** При `counter` блокування живе до
коміту, тож рання видача номера змусила б сусідів чекати всю повільну частину запису.
З тієї ж причини TS-команда, що записує два документи одразу, мусить брати номери в
сталому порядку — інакше два таких виклики назустріч дадуть взаємне блокування.

### Виданий номер редагується

Автоматичний код — це умовчання, а не заборона. Поле лишається доступним, форма
підставляє наступний вільний, користувач може виправити. Наслідки:

- ручне значення лічильник **не** піднімає — але якщо воно більше за поточне і
  відповідає шаблону, лічильник підтягується до нього. Без цього наступний авто-номер
  через кілька записів упреться в уже зайнятий, і виглядатиме це як поламана нумерація;
- зіткнення ловить унікальний індекс, і повідомлення саме сідає на поле: рантайм
  переводить ім'я обмеження в ім'я поля (`uq_bank_code` → `code`), механізм уже є.

## Рефакторинг 2026-08-09: що виявилося хибним у першій версії

Перегляд архітектури після кроків 1–5 знайшов чотири місця, де реалізація
суперечила власним принципам підсистеми. Усі чотири виправлені.

1. **Область лічильника виводилася з шаблона** (`{ORG}` є — лічильник на
   організацію) — та сама пастка «формат диктує облікове правило», яку вже
   свідомо усунули для `period`, лише з іншого боку. Тепер область збирається
   з фактів запису (див. «Видача номера»). Для наявних шаблонів (усі з
   `{ORG}`) ключі областей не змінилися, пересів не потрібен.
2. **Оголошений засіб пересіву не працював у бік `sequence`.** Коментарі
   веліли після зміни стратегії кликати `numerator_seed_from_existing`, але
   вона писала лише в `numerator_state`, а послідовність засівалася тільки при
   **створенні** — уже наявна лишалася позаду й видавала б зайняті номери.
   Тепер пересів підтягує обидва місця; рецепт імені послідовності винесено в
   `numerator_sequence_name`, щоб пересів і створення не розійшлися.
3. **Правила перевірки ділилися між SQL і збирачем.** «Довідник не може мати
   період» жило в TypeScript, а решта правил — у `numerator_validate`; заразом
   довідник міг оголосити шаблон із `{ORG}`/`{TYPE}` (падало на першому save)
   або `{YYYY}`/`{MM}` (гірше: підставляється `now()`, тож розбір торішнього
   коду перестає його впізнавати, і bump із пересівом мовчки відстають).
   Тепер `numerator_validate(template, period, p_document)` тримає всі
   правила, а збирач передає тип моделі аргументом.
4. **Документ без дати діставав внутрішню помилку нумератора**, а коментар у
   `doc_next_number` стверджував, що `null` «дає поточний рік» — неправда для
   періодного нумератора. Генерований save тепер перевіряє `docDate` до
   видачі номера (`using column`, відмова сідає на поле форми); закріплено
   smoke-пробою.

3. ✅ **Збирач** — `_generated/numerators.data.sql`: `numerator_validate` → `insert …
   on conflict do nothing` → `numerator_seed_from_existing`. Строго після
   `document-types.data.sql`: сід документа відбирає свої номери за `app.document_type`.
4. ✅ **Генератор CRUD.** Довідник із `numbering`: поле виключене з обов'язкових,
   порожнє значення бере `numerator_next`, непорожнє — `numerator_bump_to`. Документ
   передає в `doc_next_number` дату шапки.
5. ✅ **Схеми й форми.** `code` → `Type.Optional` у `counterparty`, `nomenclature`,
   `organization`; у формах підказка `common.codeAuto` («авто»).
6. ✅ **`bank`.** `code` прибрано, кодом став `mfo`: `uq_bank_mfo`, міграція
   переносить значення (`mfo ← code`, де порожньо) і скидає колонку; схема,
   `bankList`/`bankEdit` без поля code, smoke-проба унікальності — на МФО.
   Дубль МФО на живій базі впаде при створенні індексу — свідомо: його треба
   розібрати руками, а не сховати.
7. ✅ **Екран нумераторів** — `app/admin/numerator/` (список + форма). Шаблон,
   період, стратегія, «дозволити ручний номер», стан лічильників по областях
   (для `sequence` — фактичне значення з самої послідовності), попередження
   про порожні префікси при `{ORG}`. Три рішення поверх плану:
   - **пересів робить сам `save`, і після будь-якої правки**, не лише зміни
     стратегії: шаблон і період входять у ключ області, тож будь-яка правка
     може лишити лічильник під старим ключем. Пересів ідемпотентний, тому
     зайвий виклик безпечний, а «згадати про пересів» перестало бути обов'язком
     людини;
   - для цього **джерело пересіву зберігається в самому рядку нумератора**
     (`source_table/column/org/date/filter`): це структурні факти моделі, їх
     пише деплой з манифеста й оновлює при кожній публікації (`on conflict do
     update` лише цих полів), тоді як налаштування після сіяння належать
     адміністратору. Екран знає лише ключ моделі — і цього досить
     (`app.numerator_reseed`);
   - **`is_editable` став серверною забороною**, а не мертвим перемикачем:
     генеровані `save` (довідник і документ) відхиляють ручний або змінений
     номер із прив'язкою до поля. Незмінений номер наявного запису ручним не
     рахується. Закріплено smoke-пробою.
   Створення й видалення нумераторів з екрана немає навмисно: їх заводить
   деплой із манифестів, а видалений рядок зламав би видачу номерів моделі.
8. ✅ **Міграція існуючих даних** — вийшла частиною кроку 3:
   `app.numerator_seed_from_existing` читає вже видані номери, розбирає їх тим самим
   шаблоном і піднімає лічильник через `greatest`. Ідемпотентна, тож повторний
   `sql:publish` на живій базі нічого не псує.

Попутно з кроком 7 виправлено бічну ваду генератора: **перенумерація наявного
документа не підтягувала лічильник** (`bump` викликався лише для нового), тож
авто-номер згодом упирався в зайнятий. Тепер bump іде для будь-якого зміненого
номера, а незмінений не чіпає лічильник зовсім (раніше довідник смикав його на
кожному save).

## Перевірено

Проба `нумератор: авто-код, ручний код, відкат` у `scripts/smoke_test.ts` — авто-код
із доповненням нулями, послідовність, ручний код підтягує лічильник, код не за
шаблоном його не чіпає, а **відкат номер повертає**. Проба витрачає лічильник, тому
повертає `numerator_state` на місце у `finally` — інакше вона назавжди зсувала б коди
реальних записів у базі розробника.

Друга проба — `нумератор: період року при номері без року`: лічильник починається
спочатку щороку, номер лишається тим самим рядком (`РНК-000001` і за 2026, і за
2025), а в межах свого року він зайнятий і повторно не проходить. Це те місце, де
конструкцію найлегше зірвати назад у «період видно з номера», тож воно закріплене
пробою, а не домовленістю.

Руками на живій базі перевірено те, чого проби не покривають: окремий лічильник у
кожної організації (`ННК-000001` поруч із `РНК-000002`) і поведінка `sequence` —
відкат лишає дірку (16 втрачено, далі 17), а нова послідовність засівається з
`numerator_state`, а не з одиниці.

Лишилося непокритим: **гонка** — два одночасні `save` в одну область. Перевірити це
в пробі, що піднімає застосунок у своєму процесі, нічим: потрібні два справжні
з'єднання й керування транзакціями.
