# Зауваження з хмарної установки: конфігурація і порядок обробки

Як агент на машині розробника працює з потоком зауважень, що народжується в
установці для перевірки. Доповнення до [`review-remarks-plan.md`](review-remarks-plan.md)
— там рішення й причини, тут порядок дій.

**Статус:** написано за побудованим механізмом; на живій хмарній установці ще не
проходило. Місця, які треба перевірити першим проходом, позначені.

---

## 1. Що з чим з'єднується

```
[браузер перевіряльника] ──→ Deno Deploy: застосунок ──→ managed PostgreSQL
                                      ↑
                                      │ HTTPS, Authorization: Bearer
                            [машина розробника]
                              MCP-обгортка @altera/mcp
                                      │
                                      ↓
                            ../altera-feedback/gaps/*.md
```

Дві сторони дивляться в **одну** базу. Це не зручність, а умова: зауваження несе
маршрут і id запису (`document/invoice/edit/412`), і в чужій базі це посилання не
означає нічого.

## 2. Токен

Токен видається **з браузера, по сесії** — агент, який його тримає, не має
карбувати собі нові. У застосунку для цього є діалог: меню користувача в шапці →
«Токени доступу».

1. Увійти в хмарну установку тим користувачем, від імені якого працюватиме агент.
2. Видати токен із **правом запису** — без нього агент не відповість.
3. Скопіювати значення: воно показується **один раз**, у базі лежить лише хеш.

**`deno task token` тут не годиться.** Ця задача ходить у базу напряму й стоїть
під запобіжником оточення: нелокальний хост вона відмовиться чіпати. Так і
задумано — консольний інструмент для дев-бази, браузер для всього іншого.

Токен належить тій базі, у якій виданий, і успадковує **права свого
користувача** — окремих прав у нього немає. Тому користувач агента має бути тим,
кому справді дозволено правити зауваження, і не більше.

## 3. Запис у конфізі MCP-хоста

Одна база — один запис. Параметра «до якої бази» в інструментах немає навмисно:
промах у ньому пише не в ту базу, а в обліку таку помилку помічають не одразу.

```json
{
  "mcpServers": {
    "altera-review": {
      "command": "deno",
      "args": ["run", "--allow-net", "--allow-env", "--allow-read", "jsr:@altera/mcp@^0.1.0"],
      "env": {
        "ALTERA_URL": "https://<проєкт>.deno.dev",
        "ALTERA_TOKEN": "${ALTERA_TOKEN_REVIEW}"
      }
    }
  }
}
```

Токен — **тільки через `env`**, ніколи аргументом командного рядка: аргументи
видно в переліку процесів будь-якому користувачу машини.

## 4. Що агент бачить

Три інструменти обгортки: `altera_models` (каталог), `altera_describe` (схеми
названих моделей), `altera_call` (виклик команди). Для зауважень манифест
відкриває рівно три команди:

```jsonc
"agent": { "allowCommands": ["list", "get", "answer"] }
```

`save` і `verify` не відкриті свідомо: писати зауваження — робота людини,
закривати — теж її.

## 5. Порядок обробки

**Крок 1. Забрати потік.** Один виклик на сесію:

```jsonc
altera_call remark list { "filters": { "openOnly": "1" }, "pageSize": 50 }
```

`openOnly` — це не перелік станів, а порожній `verifiedAt`: доки людина не
підтвердила, запис відкритий, хай навіть відповідь уже написана.

**Крок 2. Прочитати запис.** `remark get { "id": "42" }` віддає текст, контекст
(`ctxRoute`, `ctxModel`, `ctxRecordId`, версії рішення й фреймворку) і вже
написану відповідь, якщо вона є.

**Крок 3. Відтворити випадок.** З `ctxRoute` беруться модель і id — і той самий
запис читається звичайною командою:

```jsonc
altera_call invoice get { "id": "412" }
```

Саме заради цього кроку обидві сторони й дивляться в одну базу.

**Крок 4. Подивитися знімки.** Кадри лежать звичайними вкладеннями:

```jsonc
altera_call attachment list { "ownerModel": "remark", "ownerId": "42" }
```

Рядок несе `token`; байти віддає `GET /api/blob/<id>?token=…`, тобто звичайний
HTTPS-запит повз MCP. Завантажити у файл і відкрити як картинку.
**Перевірити першим проходом:** токен вкладення видається рантаймом під поточну
сесію, і чи приймається він на виклику з `Bearer`, на живій установці ще не
міряно. Якщо ні — знімки лишаються людині, а агент працює з текстом і контекстом.

**Крок 5. Розібрати.** Головне питання — **область**: `solution` (правити
рішення) чи `framework` (бракує самого фреймворку). Перевіряльник цього не знає
й не мусить; це робота агента.

**Крок 6. Відповісти.**

```jsonc
altera_call remark answer {
  "id": "42",
  "status": "fixed",
  "area": "framework",
  "answer": "Прогалина ядра: субконто не читалося з плану рахунків при проведенні. Виправлено.",
  "fixedVersion": "server 0.19.1",
  "feedbackRef": "gaps/2026-08-14-doc-analytic-set.md"
}
```

**Крок 7. Прогалина ядра — окремим каналом.** Якщо `area = framework`, випадок
записується файлом у `../altera-feedback/gaps/`, а ім'я файлу повертається в
`feedbackRef`. Два канали лишаються різними: у них різні сторони й різні терміни
життя.

## 6. Чого агент не робить

| Дія | Чому |
|---|---|
| `verify` — закрити запис | закриває людина, і лише вона; команди немає в `allowCommands` |
| `save` — правити текст зауваження | це чужі слова; `answer` до них і не дотягується |
| `order` → `in_work` | обсяг нової роботи називає власник рішення. Ядро відмовить: заяву `ownerDecision` шле форма, а не агент |
| опитувати потік по колу | див. нижче |

## 7. Ритм і його ціна

**Один прохід на сесію, а не опитування.** Кожен виклик будить ізолят на Deno
Deploy, і платять там за процесорний час: опит раз на п'ять хвилин — це три
сотні пробуджень на добу за нічого. Потік зауважень людський: він росте
годинами, а не секундами.

Розумний ритм — забрати відкриті на початку роботи, обробити пачкою, відповісти.
Якщо потрібне сповіщення «прийшло нове», його має слати установка, а не питати
агент; такого механізму ще немає (див. розділ «Свідомо відкладено» в плані).

## 8. Що піде не так у першу чергу

- **Токен видано без `--write`** — читання йде, `answer` відмовляє. Видно
  одразу, лікується новим токеном.
- **Права користувача агента вужчі за очікувані** — `answer` вимагає `edit` на
  моделі `remark`; токен своїх прав не має.
- **Установка спить** — перший виклик після простою чекає холодного старту.
  Це не помилка, це платформа.
- **Знімки недоступні** — див. крок 4, перевіряється першим проходом.
