# Обов'язковість полів і перевірка форми

Правила полів оголошуються **у формі**, а не тільки в схемі: обов'язковість
часто залежить від інших полів («ЄДРПОУ потрібен юрособі, РНОКПП — підприємцю»),
і схема такого сказати не вміє.

Механіка — у `BaseUI` (`client/ui-kit/base/base-ui.ts`), тож працює в будь-якій
формі редагування без додаткового коду. Еталон — `app/catalog/organization/organizationEdit.ts`.

## Коротко

```ts
import { BaseUI, type FieldRules } from "@client/ui-kit/base/base-ui.ts";

protected override fieldRules(): FieldRules {
  const item = this.$root.item;
  const entrepreneur = item.legalPersonKind === "individual_entrepreneur";
  return {
    // умовна обов'язковість — коротка форма
    mfo: item.kind === "bank",

    // зняти обов'язковість, яку дає схема
    prefix: false,

    // обов'язковість + власна перевірка
    edrpou: {
      required: true,
      check: (v) => /^\d{8}$/.test(String(v)) ? null : this.t("organization.edrpouFormat"),
    },
  };
}
```

Далі нічого підключати не треба: зірочка, підсвітка, текст помилки під полем,
блокування збереження і перехід до першого невалідного поля вмикаються самі.

## Що звідки береться

`fieldRules()` — **метод**, а не константа: він викликається на кожен рендер і
перед збереженням, тому умова вільно читає `$root`. Ключ — ім'я поля основної
сутності (`primaryKey`, зазвичай `item`).

Обов'язковість поля визначається за таким порядком:

| Джерело | Приклад |
|---|---|
| прапорець прямо в розмітці | `renderField(…, { field: "mfo", required: expr })` |
| правило форми | `fieldRules() → { mfo: expr }` |
| схема TypeBox | усе, що не загорнуте в `Type.Optional` |

Схема лишається дефолтом навмисно: форми, яким умовна логіка не потрібна,
працюють як і раніше, без жодного рядка.

## Що саме перевіряється

Перевіряється **об'єднання двох множин**:

- поля, оголошені у `fieldRules()` — хай як їх малює форма;
- поля, віддані в `renderField(…, { field })` — вони беруть обов'язковість зі схеми.

Решта схеми не перевіряється свідомо. `id` за TypeBox обов'язковий
(`Union([String, Null])` — не `Optional`), але в новому записі він порожній:
суцільна перевірка схеми блокувала б збереження завжди.

Поле, якого форма в поточному рендері не намалювала (схована гілка розмітки,
згорнута вкладка), не перевіряється — підсвітити його все одно нікуди. Реєстр
відмальованих полів збирається під час `render()` і очищується перед кожним
наступним.

**Порожнім** вважається `null`, `undefined`, рядок із самих пробілів і порожній
масив. `false` і `0` — заповнені: інакше checkbox «ні» і сума «0» валили б
перевірку.

`check` порожнього значення **не бачить**: «формат» незаповненого поля
перевіряти нічого, а «має бути заповнене» — це `required`. Тому необов'язкове
поле, яке лишили порожнім, власну перевірку проходить.

## Коли спрацьовує

Перевірка запускається `trySave()` — через нього проходять усі три кнопки
підвалу і публічний `save()` (ним же користується оболонка в діалозі закриття
брудної вкладки).

Перевірка **зовні** `saveItem()` навмисно: `saveItem` — це «як саме
відправити», форми його перевизначають і не всі кличуть `super`. Своя кнопка
збереження вішається на `this.save` або `this.trySave`, **не** на `this.saveItem`.

Форма може покликати `validate()` сама, якщо власна дія теж вимагає заповнених
полів:

```ts
private async post() {
  if (!this.validate()) return;
  await this.run("post", { id: this.$root.item.id });
}
```

До першої перевірки помилок не показуємо взагалі — порожня нова форма не
повинна зустрічати користувача червоним. Після неї помилки перераховуються на
кожен рендер, тож зникають щойно поле заповнили, а не з наступним натисканням.

## Як це виглядає

`renderField` сам ставить `data-field`, клас `.field-invalid` на обгортку і
текст помилки під контролом.

Компонент із власним підписом (`<ui-picker label>`, `ui-date`, `ui-select`,
`ui-decimal`) у `renderField` не загортається, тому дві прив'язки пише форма:

```ts
<ui-picker
  .label=${this.t("invoice.counterparty")}
  ?required=${this.isRequired("counterparty")}
  .invalid=${this.fieldError("counterparty")}
  …
></ui-picker>
```

Підсвітка йде **успадкованою CSS-змінною** `--field-border`, а не селектором:
контроли ui-kit живуть у власних shadow root, куди селектор із форми не дістає,
а змінна — дістає. Тому `.field-invalid` (для обгортки) і
`:host([invalid]:not([invalid=""]))` (для компонента) роблять одне й те саме —
перевизначають одну змінну; рамку підхоплює будь-який `.input` усередині.

**Текст помилки не бере участі в потоці** — це плаваюча підказка під полем
(`position: absolute` від обгортки `.field-invalid`). Причина в двох речах:
поява й зникнення помилки інакше смикали б висоту всієї форми, а довге
повідомлення у вузькій колонці (`w-40` під ЄДРПОУ) розповзалося б на три-чотири
рядки. Плаваюча підказка натомість росте **вбік** до `max-width: 18rem` і лише
потім переносить рядок, тож від ширини поля не залежить.

Ціна рішення: підказка лягає поверх того, що йде нижче. Це свідомо — вона
живе рівно доти, доки поле не виправили, а користувач у цю мить дивиться саме
на це поле. Але писати романи в `check` не варто: повідомлення має бути
короткою вказівкою («РНОКПП — 10 цифр»), а не поясненням на абзац.

## Межі

- **Табличні частини не покриті.** Обов'язкові колонки `TabularSection`
  перевіряються тільки в БД. Це свідомо відкладено.
- **Сервер не знає про ці правила.** Клієнтська перевірка — зручність, а не
  захист: обмеження цілісності лишаються в SQL, і саме вони спрацюють для
  запиту в обхід UI.
