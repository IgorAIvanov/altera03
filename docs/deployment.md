# Розгортання застосунку

Шлях від порожньої машини до працюючої системи — і для щойно згенерованого застосунку,
і для цього репозиторію. Різниця між ними у двох рядках, вона позначена по ходу.

**Що перевірено, а що ні.** Кроки нижче пройдені на Windows проти PostgreSQL у Docker,
включно з першим входом і зміною пароля. **Не перевірялося**: робота за зворотним проксі з
TLS, супровід процесу (systemd/docker), резервне копіювання. Ці розділи позначені
«не перевірено» — там написано, що зробити, але не «як я це зробив».

---

## 1. Що потрібно на машині

- **Deno 2.9+** (у пресеті Vite використовується `@deno/vite-plugin`);
- **PostgreSQL 15+** — потрібен `nulls not distinct` в унікальних індексах меню;
- на машині складання — нічого більше: Node.js не потрібен, npm-залежності ставить Deno.

Окремий сервер БД піднімати не обов'язково: якщо PostgreSQL уже є, вистачить **окремої
бази** на ньому (`create database <ім'я> owner <роль>`).

---

## 2. Створити застосунок

```bash
deno run -A jsr:@altera/create my-erp
cd my-erp
```

> **Для цього репозиторію крок пропускається** — застосунок уже є, працюємо в його корені.

Що з'явиться: `deno.json` із задачами, `vite.config.ts` на два рядки, `app/` з обома
composition root і оболонкою, `docker-compose.yml`, `.env.example`, `tsconfig.json`.

**`tsconfig.json` видаляти не можна.** Його читає транспілятор усередині Vite (з Vite 8 це
Oxc, до того був esbuild) — `deno.json` для нього не існує. Без `experimentalDecorators`
застосунок збереться, пройде перевірку типів і відкриється **білою сторінкою**: декоратори
Lit падають у рантаймі.

---

## 3. База даних

```bash
cp .env.example .env
```

Заповнити підключення й `BLOB_TOKEN_SECRET` (згенерувати власний — з плейсхолдером
`change-me-in-production` продуктивний сервер не стартує). Далі або свій PostgreSQL,
або той, що в комплекті:

```bash
deno task startdb
```

`docker-compose.yml` бере облікові дані з того самого `.env` і публікує порт `${PGPORT}` —
якщо на машині вже щось слухає 5432, достатньо змінити `PGPORT`.

**Імена змінних підключення — libpq**: `PGHOST`, `PGPORT`, `PGDATABASE`, `PGUSER`,
`PGPASSWORD`, `PGSSLMODE`. Тобто ті самі, які й так розуміють `psql`, `pg_dump` і будь-яка
керована база, — з тим самим `.env` вони йдуть туди ж, куди застосунок, і параметри не
доводиться перепечатувати (це знадобиться в розділі 9). Керована база зазвичай дає натомість
`DATABASE_URL`; заданий, він перекриває `PG*` **цілком** — джерело береться все, а не по
полях, інакше вийшла б химера з хостом з одного місця й паролем з іншого.

> **Одна пастка від libpq-імен.** `--env-file` **не перекриває** вже задані змінні оточення.
> `DB_HOST` ніхто глобально не експортує, а от `PGHOST` під власний `psql` — цілком: тоді він
> мовчки переможе проектний `.env`. Куди застосунок пішов насправді, видно в рядку старту
> `✅ PostgreSQL <host>:<port>/<база> відповідає` — з нього й починати, якщо база «не та».

## 4. Залежності — ДО збірки

```bash
deno install
```

Це не формальність. У `deno.json` стоїть `"vendor": true`: пресет Vite і Tailwind читають
вихідники фреймворку **з диска** (аліас `@client`, директива `@source`), а кеш JSR — це
файли з іменами-хешами, по яких сканувати нічого. `deno install` матеріалізує їх у
`vendor/`.

Якщо пропустити: збірка впаде на `Could not load .../vendor/jsr.io/@altera/client/...`.
Гірший варіант — коли застосунок імпортує фреймворк не через `@client/`, а через ім'я
пакета: тоді модулі приїдуть із кешу, збірка пройде, і **мовчки зникнуть стилі
фреймворку**. Тому в згенерованому застосунку всі імпорти йдуть через `@client/`.

> **Свіжий реліз фреймворку.** Deno не бере версію, опубліковану менш ніж 24 години тому:
> `error: Could not find version ... A newer matching version was found, but it was newer
> than the specified minimum dependency date`. Виглядає так, ніби пакета немає. Обхід —
> `deno install --min-dep-age=0`.

## 5. Схема бази

```bash
deno task sql:registry
deno task sql:assemble
deno task sql:publish
```

- `sql:registry` — реєстр моделей, маршрути, манифест в'ю з `manifest.json` моделей;
- `sql:assemble` — збирає SQL-пакет із ядра (`@core/*`) і моделей застосунку;
- `sql:publish` — виконує його в базі: структура → міграції → функції → дані.

Публікація ідемпотентна: повторний запуск нічого не ламає, сіди йдуть із
`on conflict do nothing`.

**Після кожного оновлення пакетів фреймворку** цю трійку треба повторити **до** запуску
сервера. Рантайм може почати вимагати нових функцій ядра, і на неопублікованій базі впаде
не одна команда, а всі — з повідомленням про ту модель, яку відкрили.

`sql:publish` відмовиться працювати, якщо хост БД (`PGHOST` або той, що в `DATABASE_URL`)
не локальний або оточення позначене як
`production`/`prod`/`staging`: це дев-інструмент, і промах у `.env` не має коштувати чужих
даних. Для продуктивної бази — розділ 8.

## 6. Перший запуск і перший адміністратор

```bash
deno task dev
```

Піднімає бекенд (`:3000`) і Vite (`:5173`). **Інтерфейс відкривати на адресі Vite** — з
непорожнім `VITE_DEV_URL` порт 3000 віддає лише `/api`, а в'ю приходять із Vite.

Хто такий перший користувач — залежить від `.env`, і шляхи два.

**Пароль у налаштуваннях.** Заповнені `BOOTSTRAP_LOGIN` і `BOOTSTRAP_PASSWORD` → екран
входу підставляє логін, користувач створюється **на першому успішному вході** (не при
старті сервера) і одразу потрапляє до групи `admin`.

Такий пароль позначається як тимчасовий: він лежить відкритим текстом у `.env`. Доки його
не змінено, сервер **не виконує жодної команди моделі**, а застосунок замість оболонки
показує екран зміни. Пропустити не можна — і це навмисно.

**Пароль у формі.** `BOOTSTRAP_PASSWORD` порожній (так поставляється шаблон) → екран входу
переходить у режим «Перший запуск: створіть адміністратора», логін і пароль вводить людина.
Прапорця тимчасовості тут немає — пароль вибрала не машина.

Обидва шляхи працюють **тільки поки в базі немає жодного користувача**. Забутий
`BOOTSTRAP_PASSWORD` у `.env` — разовий ключ, а не постійний чорний хід.

Змінити пароль потім — меню користувача в шапці → «Змінити пароль». У згенерованому
застосунку шапка мінімальна й такого пункту не має: додати його або лишити тільки
обов'язкову зміну — рішення застосунку.

---

## 7. Продуктивна збірка

```bash
deno task build:front
```

Кладе `dist/`. Далі сервер віддає фронтенд сам, і Vite більше не потрібен — **приберіть
`VITE_DEV_URL` з `.env`**, інакше сервер шукатиме в'ю у Vite, якого немає: сторінка
підніметься, жодна вкладка не відкриється.

```bash
deno run --allow-net --allow-read --allow-env --env-file ./app/server.ts
```

Перевірка, що все на місці: `GET /` віддає 200 і сторінку входу, `POST /api/auth/login`
пускає, будь-яка команда моделі відповідає конвертом.

## 8. Кілька екземплярів на одній машині

Два застосунки (або дві бази — робоча й навчальна) на одному хості живуть кожен у своєму
каталозі зі своїм `.env`. Задачі передають `--env-file` без шляху, тобто беруть `./.env`
відносно каталогу, з якого запущені, — розділення каталогами вже все, що потрібно від
процесу. Розійтися має п'ять значень:

| Змінна | Чому окрема |
|---|---|
| `PORT` | порт бекенда; його ж читає `vite.config.ts` для проксі `/api` |
| `VITE_PORT` + `VITE_DEV_URL` | порт Vite; тільки для режиму розробки |
| `AUTH_COOKIE_NAME` | **cookie не розрізняють порт** — див. нижче |
| `PGDATABASE` (або `PGPORT`) | своя база: одна на одному сервері чи окремий контейнер |
| `BLOB_TOKEN_SECRET` | інакше посилання на вкладення одного застосунку приймає інший |

**Про cookie — головне.** Для браузера `localhost:3000` і `localhost:3001` це один хост і
одна банка cookie: порт у їх область видимості не входить взагалі. Обидва екземпляри
пишуть cookie сесії з `path=/`, тож з однаковим іменем вхід у другий застосунок затирає
сесію першого. Виглядає це як випадкові розлогінення, а не як конфлікт налаштувань, —
і поки не знаєш причини, шукається довго. Те саме за зворотним проксі на спільному імені
хоста (`example.com/erp1`, `/erp2`), де порту немає й поготів.

Ім'я cookie береться з `AUTH_COOKIE_NAME` (порожньо → `altera_session`); у щойно
згенерованому застосунку там уже стоїть `<ім'я застосунку>_session`, тобто окремим воно
виходить само.

**Контейнер БД.** `docker-compose.yml` бере ім'я з `DB_CONTAINER_NAME`: імена контейнерів
глобальні на демон, тож два клони з однаковим іменем разом не піднімуться навіть на різних
`PGPORT`. Том цього не потребує — його compose префіксує іменем проєкту (за замовчуванням
це ім'я каталогу).

**Зайнятий порт Vite — помилка.** `strictPort` увімкнено навмисно: без нього другий Vite
мовчки переїхав би на 5174, а `VITE_DEV_URL` бекенда й далі вказував би на 5173 — сторінка
відкрилася б із чужого фронта. Краще не піднятися голосно.

## 9. Продуктивне оточення (не перевірено)

Тут написано, що зробити; жоден із пунктів у цьому репозиторії не проходили.

**Позначити оточення.** `NODE_ENV=production` (або `APP_ENV`/`DENO_ENV`). Це вмикає дві
речі: `AUTH_COOKIE_SECURE` за замовчуванням і заборону `DEV_AUTH_BYPASS` — з ним сервер
просто не стартує. Дев-інструменти (`sql:publish`, `api`, `passwd`) у такому оточенні теж
відмовляються працювати, тож схему на продуктив накочують інакше: зібраний
`app/_sqlpackage/*.sql` виконують звичайним `psql` — з тим самим `.env`, бо імена змінних
у нас libpq-ові, він піде рівно в ту базу. Тимчасове зняття позначки на час міграції теж
спрацює, але лише коли база локальна для машини, з якої публікують: перевірку хоста воно
не вимикає.

На Deno Deploy позначка не потрібна: платформа виставляє `DENO_DEPLOY` сама, і фреймворк
рахує її нарівні з `NODE_ENV=production`. Це навмисно — забути змінну в панелі легко, а
ціна забуття (cookie без `Secure`, дозволений `DEV_AUTH_BYPASS`) не видна ніде.

**TLS обов'язковий** — і до браузера, і до бази. Cookie сесії має `SameSite=Strict` і
`Secure` у продуктиві: по HTTP браузер її просто не збереже, і вхід виглядатиме як «пароль
не підходить». До бази TLS вмикається `PGSSLMODE` (`require` або `verify-full`) чи
параметром `sslmode` у `DATABASE_URL` — керована база без нього не пустить, а незнайоме
значення валить старт замість того, щоб мовчки піти відкритим з'єднанням.

**За зворотним проксі** задати `AUTH_PUBLIC_BASE_URL` — інакше redirect_uri зовнішніх
провідників входу будується з походження запиту (`http://localhost:3000`), а не з публічної
адреси.

**Секрети.** `BLOB_TOKEN_SECRET` — обов'язково свій: ним підписуються посилання на
вкладення, і з загальновідомим плейсхолдером `change-me-in-production` (або без секрета
взагалі) продуктивний сервер не стартує. `JWT_SECRET` читається як legacy-фолбек.
`.env` у `.gitignore` — так і має лишитися.

**Резервні копії** — звичайний `pg_dump`: усі дані, включно з вкладеннями (вони лежать у
`app.attachment` як `bytea`, зовнішнього сховища немає).

## 10. Оновлення фреймворку

```bash
# у deno.json підняти версії @altera/*
deno install
deno task sql:assemble && deno task sql:publish   # ДО запуску сервера
deno task build:front
```

Порядок принциповий — див. застереження в розділі 5.

## 11. Що йде не так найчастіше

| Симптом | Причина |
|---|---|
| Біла сторінка, у консолі порожньо | Немає `tsconfig.json` з `experimentalDecorators` |
| `Could not load .../vendor/...` | Не виконано `deno install` перед збіркою |
| Стилі поїхали, кнопки без оформлення | Те саме, але імпорти йдуть повз `@client/` |
| `Команду «X/list» не реалізовано` на всіх моделях | Не опубліковано SQL після оновлення пакетів |
| `Could not find version ... minimum dependency date` | Реліз молодший за 24 години → `--min-dep-age=0` |
| Порожня сторінка на `:3000` у dev | Інтерфейс відкривають на `:5173`, поки заданий `VITE_DEV_URL` |
| Вхід не спрацьовує, помилок немає | `Secure`-cookie по HTTP: або TLS, або зняти позначку продуктиву |
| Розлогінює при роботі з двома застосунками на машині | Спільне `AUTH_COOKIE_NAME`: cookie не розрізняють порт (розділ 8) |
| `Port 5173 is already in use` замість переїзду на 5174 | Так і задумано (`strictPort`) — задай свій `VITE_PORT` + `VITE_DEV_URL` |
