# Екран звіту: тулбар, друк, Excel

Звіт — це третій тип екрана поряд зі списком і формою редагування. У нього
завжди є три дії: **сформувати заново**, **надрукувати** і **вивантажити в
Excel**. Усі три живуть у базовому класі
[`ReportBase`](../client/ui-kit/base/report-base.ts) — новий звіт отримує їх
самим фактом наслідування, без жодного налаштування.

## Що дає база

| Дає база | Лишається звіту |
| --- | --- |
| закріплений тулбар «Оновити / Друк / Excel» | фільтри (`renderFilters()`) |
| банер помилок і «запис не знайдено» | запит (`buildReport()`) |
| шапка «назва · організація · період» для паперу й файлу | таблиця (`renderBody()`) |
| друк і експорт — без опису колонок | назва звіту (`reportTitle`) |

Тулбар **липкий**: прокручується панель вкладки, а блок з кнопками й фільтрами
лишається вгорі. Це `position: sticky` — контейнер прокрутки належить оболонці
(`.panel` у `tab-controller`), тож окремої «висоти 100%» звіту не потрібно.

## Мінімальний звіт

```ts
@customElement("my-report")
export class MyReport extends ReportBase<MyRoot> {
  protected model = "my_report";
  protected reportTitle = "myReport.title";       // ключ локалізації

  constructor() { super(MyRootSchema); }

  protected override get canRun(): boolean {
    return !this.busy && !!this.$root.$query.organizationId;
  }

  protected override async buildReport() {
    await this.loadInto("index", { ...this.$root.$query });
  }

  protected override printSubtitle(): string {
    return `${this.$root.$query.organization?.name} · ${period}`;
  }

  protected override renderFilters() { return html`…ui-picker, ui-date…`; }
  protected override renderBody()    { return html`<table class="table table-sm w-full">…</table>`; }
}
```

Кнопки «Сформувати» в тулбарі немає навмисно: «Оновити» — це вона і є. Друк і
Excel вимикаються, поки `rows` порожні.

## Друк

Друкує браузер — те, що на екрані. Серверного рендеру для звітів немає свідомо:
колонки в них з'являються за наявністю даних (валюта, кількість), а шаблон
описав би фіксований набір — екран і папір розійшлися б на першому такому звіті.
Друковані форми документів — інша річ, вони шаблонні: див.
[`print-subsystem.md`](print-subsystem.md).

Правила `@media print` розкидані по трьох рівнях, бо кожен володіє своєю
частиною розкладки:

| Рівень | Файл | Що робить |
| --- | --- | --- |
| документ | [`client/ui-kit/report/print.ts`](../client/ui-kit/report/print.ts) | розтискає `html/body/#app` з висоти 100%, ландшафтна орієнтація, поля |
| оболонка | [`client/tabs/tab-controller.ts`](../client/tabs/tab-controller.ts) | ховає меню, шапку й смугу вкладок; робить панель вкладки потоковою |
| компонент | [`client/styles/theme.css`](../client/styles/theme.css) | `.no-print` / `.print-only`, компактна таблиця, посилання звичайним текстом |

Рівень оболонки — не косметика: на екрані панель вкладки абсолютна і має власну
прокрутку, і якби вона такою лишилась, на папір потрапив би рівно один екран
замість усього звіту.

Два класи, які потрібно знати, пишучи звіт:

- `no-print` — елемент лише для екрана (підказки, кнопка «відкрити документ»);
- `print-only` — елемент лише для паперу; шапку звіту база малює сама.

## Excel

Кнопка збирає справжній `.xlsx` **у браузері** — без запиту на сервер і без
залежностей: [`xlsx.ts`](../client/ui-kit/report/xlsx.ts) пише zip методом
`store` і стільки OOXML, скільки треба аркушу (числа числами, формат `#,##0.00`,
жирна шапка з фоном, об'єднані комірки, закріплення шапки, ширини колонок).

Джерело даних — **сама намальована таблиця**
([`table-model.ts`](../client/ui-kit/report/table-model.ts)), а не окремий опис
колонок. (У списку навпаки: колонки оголошені, а в DOM лежить лише поточна
сторінка, тому там аркуш будується з даних — див.
[`ui-list-form.md`](ui-list-form.md).) Інакше кожен звіт описував би розкладку двічі, і розходження між
екраном і файлом виявлялося б уже після того, як бухгалтер відкрив вивантаження.

Читач спирається на три сигнали розмітки — усі три й так стоять для екрана:

| Розмітка | Що означає в файлі |
| --- | --- |
| `<th>` | шапка або підсумок: жирний шрифт, фон, рамка |
| `tabular-nums` | комірка числова: «1 234,56» розбирається назад у 1234.56 |
| `text-right` / `text-center` | вирівнювання комірки |
| `colspan` / `rowspan` | об'єднані комірки аркуша |

Звідси правило: **суму в звіті ставимо з `tabular-nums`**. Без цього класу число
приїде в Excel текстом, і колонка не додасться. Код рахунку, навпаки, цього
класу мати не повинен — інакше «0631» стане числом 631.

Порожня числова комірка лишається порожньою, а не нулем: у звітах нуль
відсутнього обороту і справжній нуль — різні речі.

Четвертий сигнал — `no-export`: «цей вузол не належить аркушу». Про нього —
нижче, разом із графіками, бо саме там він і потрібен.

## Графік у звіті

**Бібліотеку графіків фреймворк не постачає і не вибирає.** Жоден контракт у
неї не впирається: маніфест графік не оголошує, SQL про нього не знає, ядро його
не рендерить. Тому беріть що завгодно — chart.js, свій SVG, будь-що, — і кладіть
у власний компонент звіту.

Закриті **стики**, а не сама бібліотека: тулбар звіту має дві кнопки, які
працюють із уже намальованим DOM, і графік ламає обидві, якщо його поставити
абияк.

**Куди класти.** У контейнер `.report-chart` (клас живе в темі,
[`theme.css`](../client/styles/theme.css)):

```html
<div class="report-chart">
  <canvas ...></canvas>
</div>
```

Це вмикає три правила `@media print`, кожне проти окремої біди: графік не
розсікається межею сторінки, вписується в поля зі збереженням пропорцій
(`max-width`, а не `width` — вужчий за сторінку графік розтягувати не треба,
полотно від цього тільки замилюється) і друкується **із заливками**: без
`print-color-adjust` браузер їх викидає, і стовпчикова діаграма виходить із
самих контурів.

Правила навмисно на класі, а не на `canvas, svg` взагалі: під `svg` потрапили б
іконки в комірках таблиці.

**Excel графіка не побачить** — аркуш читається з `<table>`, а графік не
таблиця. Спеціально нічого робити не треба. Але два випадки потребують
позначки `no-export`:

| Де стоїть `no-export` | Що робить читач |
| --- | --- |
| на `<table>` | пропускає цю таблицю, шукаючи основну — потрібно, коли на екрані є легенда графіка чи довідкова врізка, намальована таблицею **раніше** за звіт |
| на `<tr>` | викидає рядок цілком — для рядка з графіком на всю ширину або з кнопками дій |
| на `<td>` / `<th>` | лишає комірку на місці, але порожньою — забрати її не можна, бо сітка поїде й наступні колонки стануть не під своїми заголовками |

Це аналог `.no-print` у темі, тільки читає його не браузер, а обхід DOM у
[`table-model.ts`](../client/ui-kit/report/table-model.ts).

І окремо: **комірці з графіком не можна давати `tabular-nums`**. Клас означає
«розбери текст як число», і спарклайн у комірці перетворив би вивантаження на
сміття.

## Перевірка вивантаження

`buildXlsx` не залежить від DOM (від нього залежить лише читач таблиці), тому
файл збирається тим самим модулем і в Deno — перевірити вивантаження можна без
браузера й без Excel. Разова проба: скрипт, що імпортує `buildXlsx`, будує
модель аркуша з рукописною сіткою (обов'язково з `rowspan` — саме на ньому
ламалася розкладка) і пише файл; далі його читає будь-який справжній споживач
OOXML — `openpyxl` у Python або `System.IO.Compression` у PowerShell. Обидва
звіряють CRC і розбирають XML, тож бита структура спливає одразу:

```python
import openpyxl
ws = openpyxl.load_workbook("probe.xlsx").active
print(ws.dimensions, ws.freeze_panes, sorted(str(m) for m in ws.merged_cells.ranges))
```

Саме так знайшлося з'їжджання другого рядка шапки під вертикально об'єднані
колонки: XML був валідний, а «Дебет» стояв у `A4` замість `C4`.
