# Розгортання на Deno Deploy

Шлях від репозиторію до працюючого застосунку на Deno Deploy. На відміну від розділу 9
[`deployment.md`](deployment.md), тут написано **те, що робилося**, а не те, що варто
зробити: усе нижче пройдено, включно з першим адміністратором і пересозданням бази.

Йдеться про **новий** Deploy: Deploy Classic вимкнено 20 липня 2026, і `deployctl` разом
із ним. Загальний порядок (база, схема, продуктивне оточення) — у `deployment.md`; тут
лише те, що специфічне для платформи.

---

## 1. Що бере на себе платформа

Три речі, які деінде довелося б налаштовувати руками:

- **PostgreSQL.** Provision із самої панелі (рушій — Prisma Postgres). Учасні дані
  підставляються в рантайм самі: `DATABASE_URL`, `PGHOST`, `PGPORT`, `PGDATABASE`,
  `PGUSER`, `PGPASSWORD`. Оскільки імена змінних у фреймворку — libpq, застосунок читає
  їх без жодного перехідника.
- **TLS і позначка продуктиву.** HTTPS назовні платформа дає сама, а `DENO_DEPLOY` вона
  виставляє як власну змінну — фреймворк рахує це продуктивом, тож `NODE_ENV=production`
  задавати не треба (і забути його теж не можна).
- **Порт.** Слухає платформа. `Deno.serve` у застосунку бере `PORT` або 3000, але в логах
  видно `Listening on http://0.0.0.0:8000/` — запитаний порт ігнорується. Задавати `PORT`
  у змінних не потрібно.

## 2. Конфігурація — у `deno.json`

Блок `deploy` перекриває налаштування панелі цілком, тож розклад видно в дифі й він їде
разом з кодом:

```json
"deploy": {
  "install": "deno install",
  "build": "deno task sql:assemble && deno task build:front",
  "predeploy": "deno run -A ./scripts/sql-deploy.ts ./app --yes --no-assemble --verbose",
  "runtime": { "type": "dynamic", "entrypoint": "./app/server.ts" }
}
```

**Чому схема публікується в `predeploy`, а не в `build`.** `build` виконується на кожну
збірку, зокрема на ту, що нікуди не поїде; `predeploy` — рівно перед тим, як ревізія
почне приймати трафік, і з тими самими змінними, що отримує застосунок. Тобто пароль не
покидає панель, а кожен контекст (прев'ю, продуктив) мігрує **свою** базу.

Звідси й розподіл кроків: пакет **збирається** в `build` (`_sqlpackage/*.sql` у git не
лежить), а **публікується** в `predeploy` з `--no-assemble`. Файли зі збірки там доступні
— у логах видно `/app/src/app/_sqlpackage/*.sql`.

`--yes` стоїть саме в конфігурації, а не в задачі `sql:deploy`: так його не можна зачепити
випадково з машини розробника. Ціна рішення свідома — DDL накочується автоматично;
публікація ідемпотентна (структура → міграції → функції → сіди з `on conflict do nothing`).

## 3. Змінні оточення

Задаються в панелі, окремо для кожного контексту (Production, Development для прев'ю та
гілок, Build для збірки — між ними сувора ізоляція).

| Змінна | Значення | Навіщо |
|---|---|---|
| `BLOB_TOKEN_SECRET` | свій випадковий | з плейсхолдером сервер не стартує взагалі |
| `DB_POOL_SIZE` | `3` | ізолятів багато, у кожного свій пул — керована база скінчиться раніше за застосунок |
| `BOOTSTRAP_LOGIN` / `BOOTSTRAP_PASSWORD` | для першого входу | разовий ключ: працює, лише поки в базі немає жодного користувача |
| `AUTH_PUBLIC_BASE_URL` | адреса застосунку | лише якщо потрібен зовнішній вхід (redirect_uri) |
| `VITE_DEV_URL` | **не задавати** | інакше сервер шукатиме в'ю у Vite, якого там немає |

Не потрібні: `PG*` (підставляє платформа), `PORT`, `PGSSLMODE` (виводиться з хоста —
локальна база без TLS, будь-яка інша `require`), `NODE_ENV` (є `DENO_DEPLOY`).

Секрет підпису вкладень зручно згенерувати так:

```bash
deno eval "console.log(crypto.getRandomValues(new Uint8Array(32)).reduce((s,b)=>s+b.toString(16).padStart(2,'0'),''))"
```

## 4. Порядок першого запуску

1. **console.deno.com** → організація → створити застосунок із GitHub-репозиторію.
   Налаштування збірки підхопляться з `deno.json`.
2. **Databases → Provision Database**, прив'язати до застосунку.
3. Задати змінні з таблиці вище в контексті Production.
4. Зібрати. Схему накотить `predeploy` — у логах ревізії, розділ Deployment, з'явиться
   рядок `→ публікую SQL у <хост>:5432/<база>` і чотири `Published SQL section`.
5. Відкрити застосунок. З заповненим `BOOTSTRAP_PASSWORD` вхід одразу вимагає змінити
   пароль: він лежить відкритим текстом у панелі, і доки прапорець стоїть, сервер не
   виконує жодної команди моделі.

## 5. Що з'ясувалося на практиці

**Збірка може впасти з гонки в Tailwind.** `Failed to unwrap exclusive reference of
BindingCallableBuiltinPlugin type from napi value` у `@tailwindcss/vite:generate:build` —
конфлікт запозичення в napi-біндингу rolldown. Версії ні до чого: локально й у CI ті самі
збираються, а тут це залежить від середовища збірки. **Лікується повторним запуском** —
перевірено, друга спроба проходить. Обхідний шлях через `@tailwindcss/postcss` у нас не
працює: PostCSS отримує шлях разом із запитом і робить `stat` по `tailwind.css?inline`.

**Тунель веде не в ту базу.** `deno run --tunnel` підставляє змінні контексту **Local** —
це окрема база, не продуктивна. Для локальної розробки проти хмарної бази зручно, для
публікації схеми в продуктив — ні.

**`predeploy` ініціалізує весь npm-граф** (~75 пакетів, дев'ять секунд): vite, rolldown,
lightningcss — усе, що до публікації SQL стосунку не має. Наслідок `nodeModulesDir: auto`
на весь проєкт. На час розгортання не впливає.

**Кожен push — це збірка, і платять саме за неї.** Прив'язана до Git інтеграція
запускає розгортання на кожен пуш у відстежувану гілку, а наша збірка не з дешевих:
`build:front` плюс `predeploy`, який ще й піднімає весь npm-граф. Десяток пушів за
день роботи — десяток повних збірок, з яких потрібна остання. Мережевого трафіку
тут немає взагалі, тож шукати «зайві запити» марно: вичерпується ліміт **збірок**.

**Прийнятий порядок — за кількістю розробників, і міняється він лише разом з нею.**

Поки працює одна машина, гілок не заводимо: досить **пушити рідше**, накопичуючи
коміти локально. Розгортання при цьому одне на пуш, і цього достатньо — зайва
гілка коштувала б дисципліни щодня, а економила б лише тоді, коли пушать часто.

Коли розробників стане кілька, з'явиться **`dev`**: усі зливають туди, а
відстежувана гілка лишається `master`, і публікація йде з пушу в неї. Тобто
проміжні стани більше не бачить ані платформа, ані той, хто в цей час перевіряє
рішення, — а це друга причина такого поділу, не менш важлива за рахунок:
перевіряльник не має отримувати наполовину зроблену правку посеред своєї роботи.

Що при цьому лишається платним і про що легко забути: **пуші в бічні гілки дають
прев'ю-розгортання, і їх теж рахують**. Зовсім безкоштовно бічна робота виходить
лише з вимкненими прев'ю.

**Ротації пароля бази в панелі немає.** Варіанти два: `Claim Instance` (інстанс переходить
під ваш акаунт Prisma, де є «Generate new connection string», — дія **незворотна**) або
видалити базу й провіженити нову. Друге дешеве саме завдяки `predeploy`: прив'язали нову,
перезібрали — схема накотиться сама, адміністратор створиться з `BOOTSTRAP_*`. Перевірено.

## 6. Типові збої

| Симптом | Причина |
|---|---|
| `Failed to unwrap exclusive reference … napi` у збірці | гонка в rolldown/Tailwind — просто перезапустити збірку |
| `relation "app.users" does not exist` | схема не опублікована: подивитися крок Deployment у логах ревізії |
| `DATABASE_URL не містить імені бази` | стара версія `@altera/server` (до 0.6.1) |
| `модуль … не експортує tagName` на кожній вкладці | стара версія `@altera/client` (до 0.6.2) |
| База даних недоступна на екрані входу | базу не прив'язано до застосунку або не задано змінні |
| Порожня сторінка | заданий `VITE_DEV_URL` — прибрати |
