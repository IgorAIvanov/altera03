# Права доступа: как это работает и как объявлять

Руководство для разработчика: из чего состоит право, как рантайм его проверяет
и что нужно написать, чтобы новая команда не осталась без защиты — или, наоборот,
не перестала работать.

> Это документация для человека. Параллельный инструктаж для AI-агента — в skill
> [`model-command-access`](../.github/skills/model-command-access/SKILL.md).
> Держите оба в синхроне.

---

## Модель прав

Право — тройка **группа → модель → действие**.

- **Группа** — `app.user_group`. Пользователь входит в группы (`app.user_group_member`),
  прав лично у него не бывает.
- **Модель** — имя из `manifest.json`, то же самое, что приходит в
  `ModelRuntimeService.execute(model, command, …)`. Значение `*` покрывает все модели.
- **Действие** — `view`, `create`, `edit`, `delete` для любой модели; `post` и `unpost`
  дополнительно для документов.

Отсутствие записи — запрет. Проверка: `app.access_can(user_id, model, action)`.

Структуры и функции живут в ядре (`server/sql/access/`, пакет `@core/access`), экраны
управления — в приложении (`app/admin/user`, `app/admin/user_group`).

## Как проверяется в рантайме

Проверка включена **для всех команд всех моделей**, включая модели ядра без манифеста
(`attachment`). Она вложена в тот же `select`, что вызывает команду:

```sql
select case when app.access_can($uid, 'bank', 'view')
            then app.bank_list($uid, $payload)
            else app.access_denied('bank', 'view')
       end as result
```

Один round-trip, кеша нет — значит, и инвалидации нет, права всегда свежие. При отказе
команда **не выполняется**: `CASE` не вычисляет невыбранную ветку, а свернуть её в
константу планировщик не может — аргументы параметризованы.

TS-команду вложить некуда, она выполняется в Deno, поэтому для неё делается один
дополнительный запрос, возвращающий строкой и `access_can`, и готовый `access_denied` —
чтобы текст отказа остался в одном месте.

**Отказ приходит обычным конвертом** `{ ok: false, messages: ["Немає права «create» на
модель «menu»"] }`, а не HTTP-статусом: это тот же контракт, что у всего остального API.
Заодно это отличает «нет права» от «нет такой команды» — последнее остаётся исключением
404/501.

**Порядок:** сначала резолвится команда, потом право. Обратный превращал бы опечатку в
имени команды в «нет доступа», и искали бы её не там.

## Стандартные команды: объявлять нечего

Действие выводится из имени:

| Команда | Действие |
|---|---|
| `list`, `get`, `lookup` | `view` |
| `save` | `create`, если `payload.item.id` пуст; иначе `edit` |
| `delete` | `delete` |
| `post`, `unpost` | `post`, `unpost` (только у моделей `type: "document"`) |

Разделение `save` на `create`/`edit` не косметика: без него право `create` не имело бы
смысла — любой с `edit` создавал бы записи.

---

## Нестандартные команды: объявление обязательно

Нестандартная — любая, которой нет в таблице выше: `printData`, `index` отчётов,
`menu/current`, `user/setPassword`, любая TS-команда. Такая команда обязана объявить
нужное право в блоке `commands.access` манифеста:

```json
{
  "model": "menu",
  "commands": {
    "sql": { "current": "menu_current", "copy": "menu_copy" },
    "access": { "current": "authenticated", "copy": "create" }
  }
}
```

Блок общий для SQL- и TS-команд: объявление идёт по имени команды, а не по способу её
реализации.

Значение — либо действие (`view` / `create` / `edit` / `delete` / `post` / `unpost`),
либо `"authenticated"`.

После правки — `deno task sql:registry`. Объявление попадает в
`app/_generated/model-registry.generated.ts`:

```ts
"menu": {
  sqlCommands: { "copy": "menu_copy", "current": "menu_current" },
  access:      { "copy": "create",    "current": "authenticated" }
}
```

### `"authenticated"` — и когда он уместен

Означает «достаточно быть авторизованным»: право модели не проверяется.

Это не лазейка для ленивых объявлений, а необходимость для команд «о себе». Пример —
`menu/current`: её зовёт каждый вход, и требовать на неё `view` на модель `menu`
означало бы, что пользователь без доступа к администрированию меню остаётся вообще без
меню.

Правило выбора: если команда возвращает данные, зависящие от того, **кто** спрашивает,
и не даёт ничего сверх того, что человеку и так положено, — `authenticated`. Во всех
остальных случаях — конкретное действие.

### Если объявление забыли

Команда не выполнится вообще:

```
501  Команда «bank/ping» не оголошує потрібного права.
     Додайте її в commands.access у manifest.json моделі й виконайте sql:registry.
```

Это сознательно **fail-closed**: забытое объявление видно на первом же вызове, а
молчаливое разрешение не видно никогда.

### Что выводится само

`printPdf` объявлять не нужно — генератор выводит её из непустого блока `prints` так же,
как и сам обработчик, и назначает `view`: печать это просмотр. Явное объявление
перекрывает вывод.

Объявление всегда сильнее вывода из имени. Написав `"access": { "list": "edit" }`, вы
получите `list`, требующий `edit`. Нужно это редко, но возможность есть.

## Как выбрать действие

| Что делает команда | Действие |
|---|---|
| Читает и отдаёт данные модели (отчёт, выборка, данные для печати) | `view` |
| Создаёт новую запись (копирование, импорт) | `create` |
| Меняет существующую (пересчёт, смена пароля, перепроведение) | `edit` |
| Удаляет | `delete` |
| Проводит / отменяет проведение документа | `post` / `unpost` |
| Отдаёт что-то «про себя» вызывающему | `authenticated` |

Сомневаетесь между `view` и `edit` — берите `edit`. Ошибка в сторону строгости даёт
внятную жалобу пользователя, ошибка в другую сторону не даёт ничего.

## dev-bypass

Отдельной ветки для него нет и не должно быть: `DEV_AUTH_BYPASS` отключает
**аутентификацию**, а не авторизацию. Поэтому `DEV_AUTH_USER_ID` должен указывать на
реального пользователя в нужной группе — иначе dev-режим расходится с продуктивным
именно там, где это дороже всего.

**Обход подставляет пользователя только там, где учётных данных нет.** Запрос с
`Authorization: Bearer`, который не подошёл — испорченный токен, отозванный,
просроченный, владелец деактивирован, — получает 401 даже при включённом обходе, и
до подстановки не доходит (server 0.18.1).

Причина в том, чего это стоило раньше. Такой запрос тихо становился запросом
пользователя по умолчанию: сломанный токен выглядел рабочим, а отозванный —
действующим, и увидеть это можно было только на чужой базе, где обхода нет. То есть
режим, в котором разработчик и работает каждый день, был единственным, где проверить
токен нечем. Сессионная cookie сюда не входит намеренно: просроченная сессия в
разработке должна вести к обычной работе, а не к 401 на каждый клик.

## Отладка

| Симптом | Причина |
|---|---|
| `501 … не оголошує потрібного права` | нестандартная команда без `commands.access`; добавить и выполнить `sql:registry` |
| `ok:false`, «Немає права «X» на модель «Y»» | права действительно нет — проверьте группы пользователя и `app.access_effective` |
| Команда работала, после добавления в манифест перестала | объявили действие строже, чем есть у группы |
| `404 … не налаштовано` | это не про права: команды нет ни в `commands.sql`, ни в `commands.ts`. Чаще всего команда объявлена на уровень выше — `"commands": { "fill": … }`; такую форму генератор реестра не читает и с tools 0.13.26 отвергает при генерации |
| Всё запрещено под dev-bypass | `DEV_AUTH_USER_ID` указывает на несуществующего или бесправного пользователя |
| `401 Токен доступу недійсний або відкликаний` | токен не подошёл; обход его не подменяет — проверьте `app.access_token` (`revoked_at`, `expires_at`, активность владельца) |

Посмотреть эффективные права пользователя:

```bash
deno task api user_group get '{"id":"2"}'
```

```sql
select * from jsonb_array_elements(app.access_effective(1, '{}'::jsonb) -> 'data' -> 'rows');
```

## Чек-лист: новая нестандартная команда

1. Реализовать: SQL-функция `{schema}.{model}_{command}(bigint, jsonb)` или TS-модуль.
2. Объявить в `commands.sql` или `commands.ts` манифеста.
3. **Объявить право в `commands.access`.**
4. `deno task sql:registry`.
5. Убедиться, что нужное действие есть у групп, которым команда предназначена.
6. Проверить вызовом от непривилегированного пользователя:
   `deno task api <model> <command> --user <id>`.
