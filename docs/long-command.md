# Довга команда: виконання у фоні

Команда моделі живе рівно стільки, скільки живе HTTP-запит, і для переважної
більшості команд це правильно. Але є роботи, які на реальній базі йдуть
хвилинами — перенесення даних із зовнішньої системи, закриття місяця,
перепроведення періоду, масове формування звітності. Для них прив'язка до запиту
ламається одразу трьома способами: бухгалтер закриває вкладку, проксі розриває
з'єднання, браузер показує помилку там, де робота насправді доробила.

Механізм у ядрі один: модель оголошує команду довгою, рантайм кладе її в
`app.job`, одразу віддає завдання і доробляє роботу поза запитом.

## Як оголосити

У `manifest.json` моделі:

```jsonc
"commands": {
  "ts": { "load": { "module": "./db/import.commands.ts" } },
  "access": { "load": "create" },
  "long": ["load"]
}
```

Потім `deno task sql:registry`.

Три речі, які варто знати одразу:

- **довгою є КОМАНДА, а не модель.** У тій самій моделі поруч живуть `load` на
  двадцять хвилин і `get` на мілісекунду;
- **оголошення в манифесті, а не в коді хендлера** — навмисно: довгою команду
  робить не реалізація, а розмір бази. Те саме перенесення в демо-наборі йде
  секунду, а в клієнта — двадцять хвилин;
- **ім'я мусить бути справжнім.** Команду, якої модель ніде не оголошує,
  `sql:registry` відхиляє. Інакше промах у слові давав би команду, що
  виконується звичайним шляхом — усередині запиту, який вона й не мала
  пережити, — і на малій базі це навіть працює.

Довгою може бути і SQL-команда: прогресу вона не звітує, але все інше (черга,
стан, результат) працює однаково.

## Що бачить викликач

Замість результату команди приходить **завдання** — у тому самому конверті:

```jsonc
{ "ok": true, "data": { "item": {
  "id": "42", "model": "import", "command": "load",
  "state": "queued", "progress": {}, "result": null
} } }
```

Далі стан питають командою `job/get`:

```bash
deno task api job get '{"id":"42"}'
```

Коли `state` стає `done`, у `result` лежить **конверт самої команди** — рівно
те, що прийшло б від звичайного виклику. Тобто клієнтського коду на два випадки
не потрібно: дочекався й читай як завжди.

Стани: `queued` → `running` → `done` | `failed` | `cancelled`.

## Прогрес

TS-хендлер дістає ручки завдання через контекст:

```ts
export default async function load(payload, ctx) {
  for (const [index, section] of sections.entries()) {
    if (await ctx.job?.isCancelled()) break;
    await ctx.job?.progress({ section: section.name, index, of: sections.length });
    await convert(section, ctx.db);
  }
  return ok({ … });
}
```

- **форму об'єкта обирає команда.** «Розділ 7 із 16» і «оброблено 12 400 рядків»
  — різні речі, спільного набору колонок під них немає;
- **`ctx.job` може не бути.** Та сама команда викликається й прямо — у пробі, на
  малій базі, з `deno task api`. Тому `ctx.job?.progress(...)`, а не
  обов'язковий крок;
- **прогрес пишеться ІНШИМ з'єднанням**, поза транзакцією роботи. Це не
  оптимізація: усе, записане всередині транзакції, видно лише після коміту —
  тобто прогрес було б видно рівно тоді, коли він уже не потрібен.

## Зняття

`job/cancel` — це **прохання**, а не вбивство. Рядок позначається, а зупиняється
команда сама, між кроками, там, де зупинка не лишає половини роботи. Ядро не
перериває чужу транзакцію ззовні: «зняв» означало б тоді «відкотив половину
невідомо чого».

Завдання в стані `queued` знімається одразу — чекати нема на кого.

Зняти може той, хто запустив, і той, кому видали `job:view`. Токену «тільки
читання» це доступне свідомо: зупинити роботу, яку ти ж і почав, — не зміна
даних, а відмова від дії. Агентові `cancel` при цьому не видно взагалі (див.
нижче).

## Що тримає систему чесною

**Одне активне завдання на пару (модель, команда).** Другий запуск, поки перший
працює, — відмова. Тримає це унікальний індекс `uq_job_active`, а не перевірка
перед вставкою: перевірити й вставити — гонка, і програє вона рівно там, де ціна
найвища (два однакові перенесення в одну базу).

**Покинуті завдання прибирає сторож.** Виконавець стукає в `heartbeat_at` раз на
15 секунд; завдання, що мовчить понад хвилину, стає `failed` з
`@[core.jobRunnerLost]`. Без цього одне падіння сервера посеред роботи робило б
команду недоступною **назавжди**: рядок лишався б у `running`, а унікальний
індекс не дав би запустити її вдруге. Зворотний бік того самого: після падіння
команда справді недоступна — але до хвилини, а не довіку.

Сторож дивиться на стук, а не на «чий процес»: на одній машині екземплярів
буває кілька, і прибирати чужі завдання при своєму старті — той самий збій,
тільки навпаки.

**Права ті самі.** Завдання не має власних прав: щоб запустити довгу команду,
потрібне право на саму команду, і воно перевіряється двічі — до постановки в
чергу (інакше відмова прилітала б не у відповідь на запуск, а хвилиною пізніше,
у стані завдання, де на неї ніхто не дивиться) і ще раз усередині самої роботи.

**Видимість.** Своє завдання бачить той, хто його запустив; чужі — той, кому
видали право `job:view` (питання експлуатаційне, і відповідь на нього має бути в
кого одного). «Немає» і «не твоє» відповідають однаково, щоб перебором id не
можна було дізнатися, що ганяють інші.

## Агент

Зовнішній агент бачить `job/list` і `job/get` — інакше довга команда, запущена
від його імені, була б беззмістовною: у відповідь він дістає id завдання, а
спитати про нього не мав би чим. `cancel` йому не видно: зупинити роботу —
дія людини, що бачить екран, а не крок, зроблений «щоб подивитися».

## Чого тут немає і чому

**WebSocket.** Доставка прогресу — окрема задача від виконання, і базово вона
розв'язується опитуванням: агент через MCP і скрипт по HTTP працюють «запит —
відповідь» і інакше не вміють, тож читання стану потрібне в будь-якому разі. Раз
воно є, екрану вистачає його ж раз на дві секунди. WebSocket був би покращенням
екрана, не механізму.

**Deno Deploy.** Безсерверна платформа не обіцяє, що процес доживе після
відповіді на запит. Тому там фонове виконання **відмовляється** —
`@[core.jobNotSupportedHere]` при спробі запуску. Рішення приймає
`configFromEnv()` (єдине місце, яке має право дивитися на оточення) і передає
полем `jobs.background`; застосунок може перекрити його явно, і це свідома
заява, що він бере на себе те, чого платформа не обіцяє.

Мовчання було б гіршим за відмову: робота, обірвана на середині, не лишає сліду
ніде, крім наполовину перенесених даних.

Точності заради: неможлива саме робота, що **переживає відповідь**. Виконання,
не прив'язане до HTTP, на платформі є — `Deno.cron`. Чому ми ним не
користуємося, написано нижче окремо: причина не технічна, а грошова.

**Черга з кількома виконавцями.** Завдання виконує той самий процес, який його
прийняв. Черги в сенсі «взяв наступне з черги» тут немає: одне активне завдання
на команду й так, а розподіляти роботу між екземплярами нема чого.

## `Deno.cron` на Deploy: чому його тут немає

Панель Cron у Deploy наводить на очевидну думку — хай крона щохвилини бере
завдання з черги. Думка правильна технічно й дорога насправді.

Що крона дає (перевірено, не з голови): та сама крона **не виконується
паралельно** — черговий запуск пропускається, якщо попередній ще йде;
гранулярність — **одна хвилина**; реєстрація — **лише на верхньому рівні
модуля, до `Deno.serve()`**, бо платформа витягує крони статичним аналізом при
деплої (отже рядок мусить стояти в `app/server.ts` — ядро зареєструвати крону за
застосунок не може); **максимальна тривалість обробника ніде не документована**.
Локально `Deno.cron` без `--unstable-cron` не існує взагалі.

Чого вона коштує. Deploy бере гроші за активний CPU і за **пам'ять-час** (768 МБ,
поки застосунок завантажений; простій вимикає його за 20–30 с). Крона раз на
хвилину не дає застосунку заснути ніколи:

| | раз на хвилину | раз на 15 хвилин |
|---|---|---|
| запусків на добу | 1440 | 96 |
| завантажений | ~12 год/добу | ~48 хв/добу |
| пам'ять-час за місяць | ≈270 GiB-год | ≈18 GiB-год |
| CPU за місяць | ≈3.6 год | ≈0.25 год |

Безплатний тариф — 150 GiB-год і 10 год CPU. Щохвилинна крона з'їдає майже вдвічі
більше пам'яті-часу, ніж увесь безплатний тариф, заради `select` по порожній
таблиці. Плюс кожен холодний ізолят відкриває нове з'єднання до бази.

**Форма, що там справді працює, інша: двигуном є той, хто чекає.** Екран і так
опитує стан завдання кожні дві секунди — це потік запитів, який тримає ізолят
живим. Довга команда, **відновлювана по шматках**, просувається на крок з
кожним таким запитом: ніхто не чекає — не коштує нічого. Крона лишається
добавкою «довести до кінця без мене», яку застосунок вмикає окремою ревізією на
час міграції й потім прибирає.

Ціна цієї форми названа наперед: команда мусить уміти зупинитися посеред і
продовжити. Для перенесення даних це природно (сировина й карта ключів роблять
повтор безпечним за побудовою); для «закрити місяць» — ні, і там на Deploy
відповідь лишається чесним «ні».

Шматкового виконавця в ядрі немає, поки Deploy не став метою: це було б рішення
без випадку.

## Транзакція прогону — не одна на все

Спокуса «весь прогін в одній транзакції, щоб не лишилося наполовину» —
зрозуміла й дорога. Десятки тисяч `_save`/`_post` в одній транзакції дають
величезний write-set, довгі блокування й розпухання, а точка збереження на
кожен об'єкт коштує окремо.

Ядро транзакцією прогону не керує: її межі обирає сама команда через `ctx.db`.
Рекомендація — транзакція **на партію** плюс відновлюваний прогін.

## Таблиця

`app.job` (пакет ядра `@core/job`): `model`, `command`, `params`, `state`,
`progress`, `result`, `error`, `started_by`, `runner_id`, `heartbeat_at`,
`cancel_requested` і три позначки часу.

`params` тут зберігаються, хоча `app.audit_log` payload свідомо **не** зберігає.
Різниця не в недбалості: журнал накриває кожну команду, включно зі зміною
пароля, тож payload там — ризик без потреби; параметри довгої команди і є зміст
запуску, без них рядок не пояснює нічого. Звідси вимога до того, хто оголошує
команду довгою: **її payload не має нести таємниць**.
