## server 0.23.0 · tools 0.13.24 · skills 0.1.36 · create 0.7.35

Вертикаль бланка більше не треба вгадувати. Блок може стати ПОТОКОМ — під
попереднім, хай де той скінчився, — а `yPercent` тепер означає ВЕРХ блока в усіх
типів однаково. Обидва записи ваші: і той, де підпис поруч із клітинками
підганяли на око, і той, де висоту таблиці доводилось передбачати числом.

### Потребує дії

**Передивіться бланки — текст з'їде вниз на висоту літери** (0.75 кегля: 6 pt
при кеглі 8). Там, де текст стоїть сам по собі — заголовок, реквізити,
підписи, — це непомітно й правити нічого не треба.

**Правити доведеться там, де підпис вирівнювали ДО ЧУЖОЇ РАМКИ** — до поля по
клітинках, до картинки, до таблиці. Така підгонка робилася на око саме тому, що
блоки стояли по різні боки однієї координати; тепер вона зайва:

```json
{ "key": "date_caption", "type": "text",       "placement": { "yPercent": "18.4"  } }
{ "key": "date_cells",   "type": "char-cells", "placement": { "yPercent": "16.78" } }
```

стає двома однаковими `yPercent` — блоки, які мусять стояти поруч, тепер несуть
ОДНЕ число:

```json
{ "key": "date_caption", "type": "text",       "placement": { "yPercent": "16.78" } }
{ "key": "date_cells",   "type": "char-cells", "placement": { "yPercent": "16.78" } }
```

**Шаблон, збережений у редакторі, лежить у базі — файл його не замінить.** Сід
іде `on conflict do nothing`, тож правити такі бланки треба в редакторі шаблонів
(вкладка PDF тепер показує те саме, що полотно). Файли в `prints/**` правляться
як звичайно.

### Змінилося саме

#### Розкладка потоком

```json
{ "key": "section_b_caption", "type": "text", "value": "Розділ Б",
  "placement": { "mode": "flow", "gapPt": "10", "xPercent": "0", "widthPercent": "100" } }
{ "key": "section_b", "type": "table",
  "placement": { "mode": "flow", "gapPt": "4", "xPercent": "0", "widthPercent": "100" } }
```

`mode: "flow"` ставить блок під ПОПЕРЕДНІМ У СПИСКУ `blocks`, хай де той
скінчився. Змішувати з координатами можна й треба: шапка відповідає затвердженій
формі до міліметра й лишається абсолютною, а все від першої таблиці й нижче йде
стосом. Абсолютний блок теж рухає курсор, тож стос законно починається під
шапкою.

- **Блок, який не влазить, іде на наступну сторінку цілим.** `keepTogether` («не
  відривати від наступного») тримає на одній сторінці цілу групу — цим
  виражається «підпис не відривати від твердження», замість порога в 64 pt, який
  вгадував те саме по відстані між блоками. Таблиця ознаки не слухає: вона
  розривається сама, по записах.
- **`yPercent` у потоці лишається й нічого не вирішує на папері** — це місце
  рамки на полотні редактора, і поле там так і підписане.
- **Досить одного блока з `flow`, щоб евристика підвалу вимкнулась на ВСЬОМУ
  бланку.** Це те правило, через яке підпис між двома таблицями їхав на другий
  аркуш разом із підвалом: усе, що нижче ПЕРШОЇ таблиці, вважалося підвалом.
  Бланк без жодного `flow` працює як працював — щоб наявні шаблони не поїхали.

#### Куди що стало

```ts
import { renderPrintPdfWithLayout } from "@altera/server/print/render";

const { bytes, layout } = await renderPrintPdfWithLayout(template, data);
layout.filter((block) => block.overflow);            // що не влізло
layout.find((block) => block.key === "section_b");   // де саме стала таблиця
```

Ключ, тип, сторінка початку й кінця, `topPt`/`bottomPt` (координати PDF — вісь y
росте вгору) і `overflow`. Ядро знало це в момент малювання й доти викидало, а
ви з'ясовували своє місце розпакуванням потоку готового PDF. `renderPrintPdf`
лишився як був — віддає самі байти.

#### Координати блока

**`yPercent` — верх блока, для всіх типів.** Вміст стоїть під цією межею:
рамка з клітинок висить під нею, картинка й таблиця починаються з неї, текст
відсунутий від неї вниз на висоту літери. Доти в `text` і `field-list` `y`
означала базову лінію ПЕРШОГО РЯДКА, тобто літери стирчали над рамкою, — два
блоки з однаковою `yPercent` опинялися по різні боки координати, на цілу висоту
блока. Полотно редактора при цьому малювало текст УСЕРЕДИНІ рамки, тобто
показувало не те, що піде на папір; тепер вони збіглися.

**Порожня висота в полі по клітинках означає КВАДРАТ** — клітинку заввишки в
саму себе завширшки (було: кегль × 1.8, не менше 14 pt). Це не зручність:
відсотки по двох осях беруться від різних сторін аркуша, тож той самий квадратик
записується двома різними числами (13 pt — 2.52 % завширшки й 1.71 % заввишки),
і виходило, що квадратик доводилось рахувати. Рамку розміряють від клітинки —
`widthPercent = count × розмір ÷ 5.1528`, звідки 12 клітинок по 13 pt — 30.3 %.
Задана висота сильніша: клітинка затвердженої форми буває й видовженою.

#### Замір бланка

**`printContentHeight()` — друга сторона області друку** в
`@altera/server/print/metrics`, поруч із `printContentWidth()`. Потрібна саме
через різні знаменники: розмір, однаковий по обох осях, у розкладці
записується двома різними числами, і пробі бланка треба вміти порахувати обидва.

**Невідома орієнтація тепер валить замір, а не мовчить.** Обидві функції
приймають рівно `"portrait"` / `"landscape"`; зайвий аргумент
(`printContentWidth("A4", "landscape")`) доти означав книжкову — 515.28 замість
761.89, — і неправильними ставали всі ширини, пораховані від цього числа, без
жодної ознаки, крім паперу.

## server 0.22.1 · tools 0.13.23 · skills 0.1.35 · create 0.7.34

Індексний вхід у `acc_entries` нарешті вмикається там, де ви його кличете. Ви
заміряли проведення після 0.21.3 і сказали, що воно не впало — це виправлення
саме про це.

### Потребує дії

**Опублікуйте SQL — зміна цілком у функціях ядра:**

```bash
deno task sql:assemble && deno task sql:publish
```

Пакет оновиться, а база лишиться зі старими функціями, і мовчки: жодної помилки,
просто колишня швидкодія.

**Заміряйте свій найдорожчий виклик ще раз.** Ми міряли обгорткою, яка повторює
ваш `inventory_balance`; у вас на місці й партійний облік, і документи, яких на
стенді немає. Якщо час проведення знову не впав — це знову до нас, і знову з
планом.

### Змінилося саме

**Мертва гілка `union all` більше не псує оцінку.** Індексний вхід (0.21.2) у
плані був і виконувався, але поруч лишалася гілка «без відбору»: вона
відсікалася на ВИКОНАННІ одноразовим фільтром, а на ПЛАНУВАННІ входила в
`Append` усіма своїми рядками. Планувальник бачив джерело на 160 тис. рядків
там, де фактично 88, — і брав хеш-з'єднання з повним скануванням журналу.

Згорталася вона лише тоді, коли `p_dims` — константа. У застосунку він не
константа ніколи: відбір збирається виразом
(`jsonb_build_object('nomenclature', …) || case when … end`). Тому наш стенд,
який кликав шар літералами, виграш бачив, а ваш живий шлях — ні.

Тепер тіло винесено в `app.acc_entries_impl(…, p_by_dims boolean)`, а
`app.acc_entries` розгортає його двічі — з `false` і з `true`. Літерал
вбудовується разом із тілом, мертва гілка згортається на плануванні, і кожна
половина дістає свій правильний план. Те саме в `acc_journal`.

**Сигнатури, форма результату й семантика `@>` не змінилися** — у ваших
викликах не міняється нічого. Рівність перевірена на 14 випадках стенда,
біт-у-біт.

Числа з нашого стенда (80 тис. проводок, чергування старої й нової функції в
одній сесії, медіана):

| Випадок | До | Після |
|---|---:|---:|
| живий виклик, один вимір (~90 рухів) | 45.6 мс | **10.6 мс** |
| живий виклик, два виміри | 58 мс | **30 мс** |
| повний журнал без відбору (контроль) | 335 мс | 349 мс |

Два виміри виграють менше, бо маловибірковий вимір (склад — половина журналу)
багато читає й індексом; контрольний рядок без відбору лишається в межах
розкиду.

**Дві нові функції в схемі — `acc_entries_impl` і `acc_journal_impl`.** Це
внутрішні тіла, кличте як і раніше `acc_entries` / `acc_journal`: у них
`p_by_dims` мусить збігатися з `p_dims`, інакше функція просто віддасть не те.

**Ціна рішення, названа чесно:** у плані тепер видно обидві половини (друга —
`never executed`), планування трохи дорожче, а сумарна оцінка рядків завищена на
мертву половину. На вибір шляху всередині це не впливає, і всі споживачі шару
над результатом лише агрегують. Якщо ви ЗʼЄДНУЄТЕ результат `acc_entries` з
чимось іще, а не агрегуєте, — скажіть, це єдине місце, де завищена оцінка може
вилізти.

## server 0.22.0 · tools 0.13.22 · skills 0.1.34 · create 0.7.33

Друк на регламентованих формах: поле по клітинках і вертикальний текст. Обидві
речі — властивості рендерера, і обійти їх із боку застосунку не виходило ніяк.

### Потребує дії

**Якщо у вас є СВОЯ копія редактора шаблонів друку** (`app/admin/print_template/`)
— вона перестане проходити `deno task check`, і це навмисно. У форматі
з'явилися два обов'язкові поля, і мовчки не показаний орган керування був би
гіршим за помилку типів: шаблон би зберігся без повороту, а причини не знав би
ніхто.

Дві правки в чужому коді на два рядки:

```ts
// app/admin/print_template/printTemplate.grid.ts → createCell()
    color: "",
    textOrientation: "0",          // ← додати

// app/admin/print_template/printTemplate.blocks.ts → createBlock("text") і createDefaultBlocks()
      format: "",
      textOrientation: "0",        // ← додати
```

Після цього збірка зелена, а шаблони друкуються як друкувалися. Щоб дістати самі
органи керування (поворот у властивостях блока й комірки, новий тип блока в
переліку), візьміть екран із репозиторію фреймворку — він там оновлений цілком.

**Шаблони мігрувати не треба.** Порожній `textOrientation` означає `"0"`, тож
усі наявні бланки чинні як є.

### Змінилося саме

**Блок `char-cells` — поле, розкладене ПО КЛІТИНКАХ.** Одна літера — одна рамка:
так друкуються ІПН і ЄДРПОУ, РНОКПП, дата складання, порядковий номер
декларації. Раніше це виражалося тільки рядком, і бланк формально не збігався із
затвердженим; таблиця не годилася — там рядки ДАНИХ, а тут одне значення,
розрізане на символи, посеред шапки.

```json
{ "type": "char-cells", "path": "doc.sellerTaxNumber", "count": "12",
  "placement": { "mode": "absolute", "xPercent": "22", "yPercent": "14", "widthPercent": "36", "heightPercent": "3" } }
```

`count` беріть із ЗАТВЕРДЖЕНОЇ форми, а не з довжини значення: порожні клітинки
на бланку лишаються порожніми, і це його нормальний вигляд.

**Ріже рендерер, форматує команда даних** — правило «рендерер не форматує»
винятку не дістало. `22.06.2026` у восьми клітинках дасть `2 2 . 0 6 . 2 0`:
крапки теж символи. Дату під клітинки віддавайте окремим полем
(`to_char(d, 'DDMMYYYY')`). Це найдорожча пастка тут, бо бланк при цьому
виглядає заповненим.

**`"textOrientation": "90"` — текст знизу вгору**, у блоці `text` і в комірці
таблиці. Заголовок авансового звіту вздовж лівого краю аркуша, заголовки вузьких
колонок інвентаризаційного опису, таблиці ЄСВ — усе це в затверджених формах
повернуте, і горизонтально його нема куди подіти. Кут рівно один: у 1590 макетах
джерела інших значень, крім 0 і 90, немає.

Дві речі, які з цього випливають і які видно лише на папері:

- у **повернутого блока висота рамки починає діяти на друк** — вона стає
  довжиною, на якій рядок переноситься (не задана — текст іде одним рядком на
  всю довжину);
- **повернута комірка не переноситься по словах** — довжина її напису стає
  висотою рядка таблиці.

**`@altera/server/print/render` — рендерер назовні.** Тепер бланк можна зібрати
в пробі, не заходячи в застосунок: `renderPrintPdf(templateItem, printData)`.
Раніше «чи влізе» рахувало ядро (`/print/metrics`, 0.17.1), а «як воно
виглядає» проба однаково діставала імпортом із `vendor/` і запуском із
`--no-config`. Шаблон, прочитаний з диска, спершу проженіть через
`normalizePrintTemplateSchema` — файл у `prints/` через нормалізацію не
проходив, і саме там береться `Cannot read properties of undefined`.

## server 0.21.3 · client 0.12.5 · tools 0.13.21 · skills 0.1.33 · create 0.7.32

### Потребує дії

**Опублікуйте SQL** — зміна знову цілком у базі:

```bash
deno task sql:assemble && deno task sql:publish
```

Міграція перебудує один індекс (`ix_journal_entry_analytic_value`); на великому
журналі це помітна пауза один раз, далі публікації його не чіпають.

### Змінилося саме

**Індекс аналітики дістав `journal_entry_id` і `side` у ключ.** Індексний вхід
за субконто (0.21.2) читає з індексу рівно ці дві колонки, а їх там не було —
тобто за кожним знайденим рухом ішов похід у купу. Тепер вхід index-only:
на журналі, що не вміщається в кеш, зникають тисячі випадкових читань диска на
виклик — а виклик стоїть у проведенні на кожен рядок документа. Префікс
`(dimension_code, value_id)` збережено: усі ваші запити по цьому індексу
працюють як працювали.

**Збірка більше не падає на ключах-коментарях у `manifest.json`.** Домовленість
`"//board": "чому це окрема в'ю"` знав генератор реєстру, але не сканер збірки
Vite: той діставав рядок замість опису в'ю, і `deno task build:front` помирав з
`The "path" argument must be of type string` — після зелених `sql:registry` і
`check`, не називаючи ні файлу, ні ключа. Тепер сканер пропускає такі ключі так
само, як реєстр.

**Нові гліфи `chevronLeft` / `chevronRight`** — крок до сусідньої колонки, та
сама пара, що `moveUp`/`moveDown` по вертикалі. Дошка (kanban) малює перенесення
картки ними, а не рукописним svg, який випав би з набору й `--icon-size`.

## server 0.21.2 · tools 0.13.20 · skills 0.1.32 · create 0.7.31

### Потребує дії

**Опублікуйте SQL — інакше нічого не зміниться:**

```bash
deno task sql:assemble && deno task sql:publish
```

Виправлення цілком усередині функцій ядра, а вони потрапляють у базу лише
публікацією. Пакет оновиться, а база лишиться зі старими функціями — і мовчки:
жодної помилки, просто колишня швидкодія.

**Заміряйте час проведення багаторядкового документа.** Ми заміряли прямі
виклики шару, а найдорожчий шлях у вас інший — добір собівартості кличе
`acc_entries` з plpgsql з обчисленим відбором, на кожен рядок. Правильність
такого виклику перевірена, а швидкодія саме його — ні (очікуємо, що виграш там
теж є, але це міркування, не замір). Якщо час проведення не впав — напишіть у
канал зворотного зв'язку, доробимо вхід під цей шлях.

### Змінилося саме

**Відбір за субконто входить у вибірку через індекс.** Доти `p_dims` фільтрував
уже побудовані рядки: `acc_entries` перебирала весь журнал організації,
розгортала на два боки, рахувала аналітику в jsonb на кожен рядок — і лише в
кінці застосовувала `@>`. Ціна виклику не залежала від вибірковості: залишок

## server 0.21.0 · tools 0.13.16 · skills 0.1.28 · create 0.7.27

### Потребує дії

**`app.acc_journal` віддає кількість і валюту по боках** — замість `quantity`,
`currency_code`, `currency_amount` тепер `quantity_debit`/`quantity_credit`,
`currency_code_debit`+`currency_amount_debit` /
`currency_code_credit`+`currency_amount_credit`. Звіт, який читає журнал проводок
(рухи документа), мусить перейти на нові імена; еталон
`app/report/document_movements` уже переведений — колонка малюється, лише коли її
бік є в даних. Функції сальдо-й-оборотів форми не міняли; `acc_entries` теж ні —
але його `currency_debit`/`currency_credit` тепер заповнюються ЛИШЕ на боці, що
веде валюту: доти сума діставалася обом бокам без огляду на `is_currency`, і
картка гривневого рахунку в проводці «Дт 312 Кт 311» показувала валютну суму.

**Позначка на видалення документа = скасування проведення — перегенеруйте SQL
документів.** Позначений документ більше не тримає проводок: `delete`
проведеного спершу знімає проведення (разом із вашим `_unpost_records`), потім
ставить позначку — тож заборона закритого періоду діє й на видалення
проведеного. **Зняття позначки проведення не повертає**: документ стає
непроведеним, провести треба заново, свідомо. Доти «правду» про позначений
документ виражав фільтр читання — проводки лежали, звіти їх не бачили, а
«Відновити» мовчки повертало рухи в баланс. Наявні позначені проведені документи
приводить до інваріанта міграція при `sql:publish` (видимих чисел вона не міняє
— їхні рухи й так були виключені з кожного звіту); ті, що прослизнуть повз неї,
доліковує `undelete`.

**Згенерований `save` відмовляє на проведеному документі — перегенеруйте SQL
документів.** Форма й так відкриває проведений документ лише на читання, але
підказка клієнта — не захист: через API чи агентом реквізити переписувалися без
жодної відмови, а рухи в регістрі лишалися від старих даних. Розходження, якого
не видно, доки хтось не звірить документ зі звітом. Тепер відмовляє сервер;
розпровів — редагуй — проведи, як і малювалося.

**Міграція `app.journal_entry` при `sql:publish`**: `quantity` розкладається на
`quantity_debit`/`quantity_credit`, а пара `currency_id`+`currency_amount` — на
бічні четвірки, обидві за ознакою рахунку (значення дістає бік, що веде вимір —
те саме правило, яким їх доти роздавав `acc_entries`); старі колонки зникають.
Прямий запит у регістр повз шар, якщо він у вас є, перестане компілюватися — це
навмисно голосно, бо мовчки він почав би брехати.

### Змінилося саме

**Складна проводка виражається регістром: кількість зберігається ПО БОКАХ.**
Комплектація — 2 комплекти з 6 корпусів і 2 матриць — це тепер два звичайні
рядки однієї кореспонденції:

```sql
perform app.doc_entry_add(doc_id, 1, '281', '281', 600.00, null, 'корпуси',
  dims_kit, dims_case, null, null, '{"debit": 2, "credit": 6}'::jsonb);
perform app.doc_entry_add(doc_id, 2, '281', '281', 600.02, null, 'матриці',
  dims_kit, dims_matrix, null, null, '{"credit": 2}'::jsonb);
```

Кількість — небалансовий вимір, як у джерелі цієї моделі: сума одна на проводку
(це і є подвійний запис), а кількості боків незалежні, бо шість корпусів дають
два комплекти — нерівність тут зміст операції. Кількість головного боку пишеться
один раз, на одному з рядків; підсумки по рахунку складаються самі, а в розрізі
номенклатури комплект дістає +2, кожен компонент іде в нуль.

**Новий параметр — вираження наміру.** `p_quantity` працює як працював: одне
число на обидва кількісні боки, і забути його так само не можна. `p_quantities`
(`{"debit": 2, "credit": 6}`) задає боки окремо, і перелік тут і є захистом:
кількісний бік, відсутній в об'єкті, лишається порожнім ЗАКОННО — голова
складної проводки живе на сусідньому рядку. Порожній об'єкт `{}` — переоцінка:
сума без кількості на кількісному рахунку, що доти не виражалася нічим.

**Механізму «групи» проводок немає навмисно.** Сховище групи однаково тримало б
кількість голови на одному рядку з N, а сверяти при «закритті групи» нема чого —
сума головної частини дорівнює сумі частин за побудовою. Якщо колись друкованій
формі знадобиться показувати складну проводку деревом, ознака групи додається
аддитивно; протокол із трьох функцій — ні.

**Валюта — по боках тим самим махом, і в парі з сумою.** Конвертація
«Дт 312 USD Кт 314 EUR» — дві різні валюти в одній проводці:

```sql
perform app.doc_entry_add(doc_id, 1, '312', '314', 4100.00, null, 'конвертація',
  dims_312, dims_314, null, null, null,
  '{"debit": {"id": 3, "amount": 100.00}, "credit": {"id": 4, "amount": 92.00}}'::jsonb);
```

Доти вона виражалася лише через рахунки «в дорозі» (333/334) — той обхід
методологічно законний і лишається законним, але був ЄДИНИМ способом, а став
вибором. Legacy-пара `p_currency_id`+`p_currency_amount` діє як діяла: одна
валюта й сума на кожен валютний бік (переказ усередині валюти). Перелічений у
`p_currencies` бік мусить бути повним — `id` без `amount` це помилка, а не намір;
ЦІЛА порожня пара (`"debit": null`) — законний намір «без валютної суми», як у
кількості.

**Чотири дірки формування проводок закриті заразом:**

- **сума, що округлюється в нуль** (`0.004`), проходила перевірку «не нуль» і
  лягала в регістр нулем — numeric(18,2) округлює мовчки; тепер нуль
  перевіряється після округлення. Від'ємна сума лишається законною навмисно —
  це сторно, коригування на тій самій кореспонденції;
- **подвійне задання виміру** (`p_quantity` разом із `p_quantities`, або
  legacy-валюта разом із `p_currencies`) відмовляє замість мовчазної переваги
  одного зі способів: котрий мав на увазі документ — звідси не видно;
- **паралельне проведення того самого документа** серіалізується
  (`for update` у `doc_post_begin`): доти двоє встигали знести старі проводки й
  писати нові, і другий падав на унікальності номера рядка — помилкою за два
  кроки від причини;
- **`save` на проведеному документі** — див. «Потребує дії».

## tools 0.13.12 · skills 0.1.23 · create 0.7.22

### Потребує дії

**Ключ-коментар у манифесті більше не валить генерацію — але перевірте, що він у
вас не став командою.** `"//picker": "…"` у блоці `views` падав із `Path must be
a string, received "undefined"`, і це було видно. Гірше було там, де видно не
було: той самий коментар у `commands.sql` чи `commands.access` тихо ставав
записом реєстру з іменем «//…». У цьому репозиторії таких набралося чотири. Тепер
ключі з `//` прибираються при читанні манифеста — на всіх рівнях. Перегенеруйте
(`deno task sql:registry`) і подивіться в дифф `model-registry.generated.ts`.

Заразом генератор більше не пише НІЧОГО, доки не зібрав усе: помилка в одному
манифесті лишала застосунок із частково оновленою генерацією — реєстр,
ts-commands і agent-routes уже на диску, view-manifest ні, — і виглядало це як
зламаний застосунок, а не як помилка в манифесті.

**`sql:gen` тепер відмовляє на ссылочному фільтрі звіту, чий підпис розходиться з
поданням цілі.** Якщо генерація впала з таким текстом — це не регрес, а мовчазна
помилка на екрані, яку нарешті видно:

```
stock_balance: фільтр «warehouse» оголошений як { id, name }, а подання моделі
warehouse — колонка «code» (перше поле з x-lookup). Додайте display: "name" в
x-ref або оголосіть фільтр як { id, code }
```

Эхо обгортки бере ключ підпису з першого поля цілі з `x-lookup` — у більшості
довідників це `name`, а в складі, одиниці виміру й банківському рахунку `code`, —
і приходить першим у `v_filters || …`, тобто ЗАТИРАЄ підпис, покладений формою.
Відбір діє, числа правильні, а пікер у панелі порожній; схема при цьому валідна,
SQL зелений, і причину йдуть шукати у форму й у пікер. Лікується одним словом —
`display` у `x-ref`. Оголошення без підпису (`{ id }`) проходить як і раніше.

### Змінилося саме

**У розпроведення з'явилася пара до `_post_entries` — необов'язковий
`app.<model>_unpost_records(user_id, document_id)`.** `doc_unpost` чистить
`app.journal_entry` і більше нічого: про рядок, покладений документом у ЧУЖУ
таблицю — періодичний реєстр цін, склад, ПДВ, — ядро не знає нічого. Без цього
ціни розпровединого документа далі діяли в накладних, а екран показував документ
непроведеним; дописати умову «лише проведений реєстратор» у читання чужого
реєстру теж нікуди, коли воно генерується (`periodic`).

```sql
create function app.price_setting_unpost_records(user_id bigint, document_id bigint)
returns void language plpgsql as $$
begin
  delete from app.nomenclature_price
  where document_id = price_setting_unpost_records.document_id;
end $$;
```

Вмикається СТВОРЕННЯМ функції — так само, як `app.doc_before_write`, — тож
документи, у яких рухи лише проводками, не міняються зовсім. Функція з тим самим
іменем і **іншим підписом** валить розпроведення: мовчазний пропуск тут гірший за
відмову, бо застосунок був би певен, що рухи зняті. Обхід — власний тригер на
`app.document` — можна знімати, і варто: на ту саму таблицю вішає тригери й ядро,
а порядок їхнього спрацювання ніде не записаний.

**Скіл `model-print-form` тепер каже, ЧИМ секції таблиці необов'язкові.** Він і
раніше обіцяв «Sections are optional», а в коді плановика видно зворотне — тож
шаблон без `footer` виглядав як міна, і його підпирали порожнім масивом у файлі.
Насправді відсутні секції складає `normalizePrintTemplateSchema`, через який
проходять обидва входи друку, тож збережений шаблон до плановика напівописаним не
доходить. Доходить той, який **читають самі** — вимірювач розкладки, міграція,
скрипт над `prints/*.template.json`; це єдиний спосіб зустріти `Cannot read
properties of undefined (reading 'filter')`, і лікується він викликом того самого
нормалізатора з `@altera/server/print`, а не правкою шаблону.

## tools 0.13.11 · skills 0.1.22 · create 0.7.21

### Змінилося саме

**`x-ref` на модель-ДОКУМЕНТ тепер працює.** Доти послатися на документ у схемі
моделі не можна було ні на який: генератор будував join за колонкою `id`, а в
таблиці документа її немає взагалі — первинний ключ там `document_id`, і саме
цю розкладку («шапка в ядрі, реквізити в таблиці моделі») задає сам фреймворк.
Публікація падала на `column r_shipment.id does not exist`, тобто за два кроки
від причини.

Оголошується як будь-яка інша ссылка — тип цілі генератор бере з її
`manifest.json`:

```ts
shipmentId: Type.Optional(Type.Union([Type.String(), Type.Null()], {
  title: "Документ відвантаження", "x-db-type": "bigint",
  "x-ref": { model: "goods_sale", as: "shipment" },
})),
```

**Подання за умовчанням — `presentation` шапки з падінням на номер**, тож у формі
поле це `<ui-picker display-field="presentation">`. Це та сама колонка, якою
підписаний рядок у журналі документів, і заповнює її **необов'язковий** хук
`app.<model>_denormalize` — документ, який його не має, показує номер, а не
порожній рядок. «№1 від 22.07.2026» генератор не складає навмисно: слово «від» —
це текст мовою, а сервер тексту не перекладає. Хочете саме такий підпис — складіть
його у своєму `_denormalize`.

`display` вибирає колонку явно й працює по обидва боки: `"number"` і `"doc_date"`
— шапка, будь-яка інша — власний реквізит документа. Ключ вкладеного об'єкта —
camelCase від колонки (`doc_date` → `docDate`). `searchable` дозволений лише по
текстовому поданню (`number`, `presentation`, `description`) — `ilike` по даті це
помилка типу, і без відмови на генерації вона вилізла б на першому наборі символів
у полі пошуку.

Те саме діє у **ссылочному фільтрі звіту**: інакше одна анотація працювала б у
формі й падала у фільтрі.

Обхід — «звичайна колонка `bigint` плюс добір номера окремим запитом у формі» —
можна прибирати: він коштує зайвого запиту на кожне відкриття документа, а ссылка
при ньому невидима для списку й для агента.

## server 0.19.0 · tools 0.13.9 · create 0.7.19

### Потребує дії

**Вхід агента перейменовано: `POST /api/agent/chat` → `POST /api/agent/call`.**
Старої адреси немає — 404. Тіло й відповідь ті самі (`{model, command,
payload}`), змінилося ім'я: чату там ніколи не було, а пара з
`GET /api/agent/tools` тепер читається як у MCP — перелік інструментів і виклик
інструмента.

**Перегенеруй опис інструментів** — `deno task sql:registry`. Без цього агент не
побачить звітів (див. нижче): `agent-tools.generated.ts` — закомічений вихідник,
а не продукт збірки.

**`GET /api/agent/tools` без параметрів віддає тепер КАТАЛОГ, а не схеми.**

```
GET /api/agent/tools                          → [{model, type, route, aliases, priority, commands}]
GET /api/agent/tools?model=bank,invoice       → [{model, command, input}] — схеми названих моделей
GET /api/agent/tools?model=bank&command=save  → одна команда
```

Хто читав плаский перелік `{model, command, input}`, має або спитати схеми
поіменно, або пройти каталогом і добрати потрібне. Кілька моделей — через кому,
одним запитом. Названа модель, якої немає, — відмова, а не порожній список, і в
списку відмовляє будь-яка невідома: віддати решту мовчки означало б дати агенту
вважати, що він отримав усе, що просив.

**`uiActions` замінені на `route`.** Дії для екрана (`openRoute`, `showToast`)
наказували щось зробити оболонці, яка їх не слухала, і будувалися на кожен
виклик; до того ж `openRoute` віддавав `/catalog/bank/edit?id=5`, тоді як
вкладку відкриває `/catalog/bank/edit/5`. Тепер у результаті лежить готове
посилання на вкладку:

```json
{ "ok": true, "result": { "model": "invoice", "id": "42",
  "route": "/document/invoice/edit/42" }, "messages": [] }
```

Відповідь тепер `{ok, result, messages}`. Посилання є лише на успіху; відборів
воно не несе, тож звіт відкриється порожнім.

### Змінилося саме

**Агент бачить звіти.** Оборотно-сальдова відомість, картка рахунку, рухи
документа — команда `index` із схемою фільтрів. Доти агент умів створити й
провести документ, але не міг подивитися оборотку, тобто мав рівно протилежний
до потрібного набір: звірка починається з читання регістру, а не з запису.

Право звітної команди береться **з оголошеного** (`commands.access` у
манифесті), а не виводиться з імені. Вивід знає лише вісім стандартних дій —
через нього нестандартні команди були невидимі для агента, хоч і виконувані.

**Чому перелік розділили.** Двадцять моделей дають 65 інструментів і 26 КБ;
повне рішення — сотню моделей, тобто 400–600 інструментів і близько 200 КБ в
одній відповіді, причому нелінійно (`save` документа з табличною частиною важить
у рази більше за `lookup` довідника). Каталог від цього не росте так само:
заміряно 127 байтів на модель, тобто ~13 КБ на сотню, — його можна тримати
цілком, а схему брати тоді, коли справді збираєшся викликати.

**У каталозі з'явилися назви й синоніми.** `titles` — назва моделі мовами
застосунку (`{"uk": "Банки", "en": "Banks"}`), взята з `titleKey` списку при
генерації; `aliases` і `priority` з `manifest.agent` генерувалися в маршрути, але
агенту не показувалися взагалі. Технічне ім'я `nomenclature` не каже нічого тому,
хто цієї бази не бачив, — а на сотні моделей вибирати доводиться саме за назвою.
Назви беруться зі **зібраних** локалей: без `deno task locales:build` їх просто
не буде.

**Ім'я моделі має бути унікальним на весь застосунок — тепер це перевіряється.**
`sql:registry` відмовляє й називає обидва манифести. Доти другий `model` із тим
самим іменем мовчки перемагав у реєстрі, а зіткнення вилазило аж при публікації
SQL. Префікса родини в імені немає й не буде: під ним лежать SQL-функції однієї
схеми, рядки прав і аудит, тож ім'я мусить пережити переїзд моделі з довідників
у регістри — родина їде окремим полем (`type`, `route`).

**Білий список диспетчера — це той самий перелік інструментів.** Раніше
`/api/agent/chat` мав власний набір із п'яти імен, і саме через нього звіт не
викликався б: перелік показував би `index`, а диспетчер відмовляв. Тепер
дозволене — рівно те, що агент прочитав у `/api/agent/tools`, тобто зібране з
манифестів (`agent.allow`, `agent.allowCommands`). Двох списків, які тихо
розходяться, більше немає.

## server 0.17.6 · tools 0.13.6 · create 0.7.16

### Змінилося саме

**Запобіжники запису для агента.** Обидва діють ЛИШЕ на виклики персональним
токеном — на застосунок у браузері не впливає нічого.

**Токен «тільки читання»** (`isReadOnly` при видачі) відмовляє будь-якій
команді, що змінює дані, незалежно від прав користувача. Це не заміна правам:
право відмовляє тому, кому не можна взагалі, а прапорець — тому, кому можна,
але не на цій задачі. Такий токен ще й **не бачить інструментів запису** в
`/api/agent/tools`: вони йому однаково відмовлять, а показані виглядають як

```json

```

Людини це не стосується — вона підтвердила натисканням кнопки. Агент мусить
сказати це словом: провести документ «щоб подивитися» не можна.

Вимога стоїть **у схемі інструмента**, а не лише в перевірці: `confirm`
з'являється в `required` із `const: true`. Інакше агент дізнавався б про неї
відмовою — тобто витрачав крок і міг би вважати відмову випадковою.

Перевірка живе в `ModelRuntimeService.execute`, у тій самій точці, де рахується
право, тож обійти її іншим входом не виходить.

**`GET /api/agent/tools` — що агент уміє робити в цій базі.** Віддає

  `app.document`. Без цього агент не побачив би дати;
- **екранні анотації не йдуть у контекст** (`x-form`, `x-list`, `x-lookup`,
  `x-search`, `x-db-type`, `x-filter`) — вони коштують місця й нічого агенту не
  кажуть. `x-ref` лишається;
- **перелік звужується правами користувача**. Це не захист (він нижче, у
  рантаймі, і fail-closed), а чесність опису: інакше агент витрачав би крок на
  команду, яка йому відмовить.

Описи будуються лише для типів зі стандартним CRUD (`catalog`, `document`,
`register`). Звіт має свій `index`, admin-екран — рукописний набір; показати їм
п'ятірку означало б дати агенту інструменти, що повертають 501.

**Метрику тексту бланка можна отримати назовні — тепер верстку друку перевіряють
пробою, а не поглядом на папір.**

Бланк псується мовчки: число, ширше за комірку, ламається на два рядки, а

```ts
import {
  createPrintTextMeasurer,
  PRINT_CELL_PADDING,
  printContentWidth,
} from "@altera/server/print/metrics";

const measure = await createPrintTextMeasurer();          // ОДИН раз на прогін
const usable = printContentWidth() * 0.10 - PRINT_CELL_PADDING * 2;   // колонка 10 %

measure("1 234 567.89", 9) <= usable;
caption.split(/\s+/).every((word) => measure(word, 9, true) <= usable);
```

## client 0.12.2 · skills 0.1.16 · create 0.7.9

### Потребує дії

**`<ui-select>` показував ПЕРШИЙ пункт замість збереженого. Перевір свої
`<select>` — найпевніше в тебе те саме.**

Виглядало це не як «показано не те», а як «**не збереглося**»: після вибору
контрол тримає вибране, і різниця вилазить аж після перезаходу. Шукати йдуть у
права доступу, payload і SQL — усе справне.

Причина в лита, і вона стосується будь-якого `<select>`, не лише компонента
ядра: прив'язки елемента комітяться раніше, ніж додаються його діти, тож
`.value=${…}` присвоюється, коли жодного `<option>` ще немає. Браузер таке
значення відкидає, а щойно пункти з'являються — стає на перший. Далі лит
`.value` не чіпає: воно дорівнює тому, що він сам поставив минулого разу.

```ts
// Неправильно — мовчки показує перший пункт
html`<select .value=${this.accountType} @change=${…}>
  <option value="active">Активний</option>
  <option value="passive">Пасивний</option>
</select>`

// Правильно — вибране на самому пункті, від порядку не залежить
html`<select @change=${…}>
  <option value="active"  ?selected=${this.accountType === "active"}>Активний</option>
  <option value="passive" ?selected=${this.accountType === "passive"}>Пасивний</option>
</select>`
```

Помилка видна ЛИШЕ коли збережене значення не збігається з першим пунктом, а в
половини списків перший пункт — найчастіший («20%», «покупка», «активний»). Тому
шукати варто не там, де щось не працює, а в **кожному** своєму `<select>`: у нас
із трьох знайдених місць запис знав про одне.

Порядок властивостей у ВИКЛИКУ (`.options` перед `.value`) не рятує — значення
виставляє сам компонент у своєму шаблоні.

У власному компоненті, де значення міняється ще й програмно (кнопка очищення,
перезавантаження запису), `?selected` мало: атрибут діє, лише доки в `<option>`
не зведено прапорець «брудності», а взаємодія його зводить. Там значення
доставляють властивістю після рендера — так тепер зроблено в `ui-select`:

```ts
protected override updated(changed: Map<string, unknown>) {
  super.updated?.(changed);
  const select = this.renderRoot.querySelector("select");
  if (select && select.value !== this.value) select.value = this.value;
}
```

Правило дописане в скіл `lit` — проби на нього немає й бути не може, це
поведінка DOM, тож єдине, що тримає його від повторення, це записаний текст.

## server 0.17.0 · client 0.12.1 · tools 0.13.0 · skills 0.1.15 · create 0.7.8

### Потребує дії

**Журнал документів дістав відбір за організацією — одним рядком.**

```ts
// у журналі документів
protected override organizationFilter = true;
```

Доти журнал фільтрувався за періодом і проведенням «задарма», а за організацією
— ніяк: колонка `organization_id` живе в `app.document`, тобто в ядрі, і
застосунку не було куди повісити `x-filter`. Поки організація в базі одна,
цього не видно; на другій журнал перетворюється на суміш двох обліків, і
відсіяти чужий нічим.

База дає три поведінки, і кожну варто знати: **умовчання — поточна
організація** (сіється до першого завантаження, зайвого запиту немає); це
**умовчання, а не заборона** — «усі організації» у списку й «Скинути» його
знімають; **при одній організації відбору немає взагалі**.

**Щоб це працювало, застосунок мусить зареєструвати контекст** — інакше
фреймворк поводиться так, наче організація одна, і відбір не з'явиться:

```ts
// app/main.ts, після відновлення сесії
import { setOrganizationContext } from "@client/shared/organization-context.ts";

setOrganizationContext({ current: () => currentOrg(), list: () => knownOrgs() });
```

Свого поняття організації фреймворк не заводить навмисно: «поточна організація»
це облікова політика застосунку — його шапка її показує, його сховище зберігає.
Тому вона приходить ЗЗОВНІ, тим самим прийомом, яким `bootstrap()` отримує все
на сервері. Обидва методи читаються на кожен рендер, тож перемикання
організації в шапці доходить саме собою — якщо за ними стоять сигнали.

`list()` у нас віддає перелік, завантажений один раз при вході. Якщо в тебе він
лежить у стані компонента шапки (а спершу так і було), його доведеться підняти
в спільний модуль — інакше фреймворк не має звідки дізнатися, скільки
організацій, і відбір не з'явиться, доки не відкрити меню вибору.

**Логічне поле без `default` у схемі більше не стає `true` у згенерованому
SQL.** Перегенеруй моделі (`deno task sql:gen`) і подивись у дифф.

Умовчання для `coalesce` генератор бере зі схеми, і все, крім явного `false`,
ставало `true` — `undefined` теж. Поле, якого немає в payload (а його не буде в
кожного клієнта, що шле лише заповнене), мовчки ставало «так»:
`amountIncludesVat` без ключа перетворював рахунок на «ціни з ПДВ», тобто з
іншою сумою до сплати. Нічого цього не ловило — SQL валідний, тип правильний,
проба на документі з явним ключем проходить.

Тепер `false`, і це не «краще значення», а єдине, яке не вигадує факт: «нема
ключа» означає «не сказано», а не «так». Хто хоче «так» — оголошує
`default: true` у схемі. У нашому дереві перегенерація дала **нульовий** дифф
(усі Item-схеми умовчання вже оголошують), тож найпевніше зміниться й у тебе
нічого — але подивитися варто саме там, де умовчання не оголошене.

**Текстовий блок бланка навчився прив'язки — і твої шаблони, найпевніше, уже її
пишуть.** Перевір бланки на прочерк там, де має бути значення.

Доти `text` умів лише статику, а `field-list` завжди друкував «підпис:
значення». Разом це означало, що ДИНАМІЧНИЙ рядок без підпису надрукувати не
було чим: заголовок бланка («Рахунок на оплату № 12 від 02.02.2026 р.»),
підсумок, «Надруковано …», реквізити сторони — усе це значення без підпису.

Гірше було те, що межа мовчала: шаблон писав `path` у текстовий блок, наче він
працює, нормалізація його викидала, і на бланку лишався **«-»**. Тобто
відсутність механізму виглядала як заповнений бланк, і побачити це можна було
лише поглядом на папір. У самому scaffold так друкувалася «Картка контрагента»
— рядок «Надруковано» стояв прочерком із першого дня.

Тепер працює і те, і те:

```json
{ "type": "text", "path": "document.title" }
{ "type": "text", "path": "document.total", "format": "amountInWords" }
{ "type": "field-list", "items": [{ "key": "org", "label": "", "path": "org.name" }] }
```

Порожній `label` друкує саме значення — без нього рядок починався з двокрапки.
Статичний `value` перекриває прив'язку: одне правило на весь формат, те саме, що
в комірці таблиці й у штрих-коді.

Міграції шаблонів **не треба** — навпаки, ті, що вже писали `path`, почнуть
друкувати значення замість прочерку. Що варто зробити руками: пройтися бланками
й зняти обхід, якщо в команді даних з'явилися шматки фраз (`titleTail`,
`itemsSummary` — підпис, дописаний до значення заради `field-list`). Такі поля
тепер зайві, а команда даних перестане бути описом розкладки.

**Умовна видимість у шаблоні: `visibleWhen`.** Бланк більше не треба звужувати
до спільного знаменника й не треба множити на комбінації.

```json
{ "type": "field-list", "visibleWhen": "invoice.hasVat", "items": [ … ] }
{ "key": "c_vat",  "widthPercent": "10", "visibleWhen": "invoice.hasVat" }
{ "key": "r_note", "cells": [ … ],       "visibleWhen": "note" }
{ "key": "vat", "label": "У т.ч. ПДВ", "path": "vat", "visibleWhen": "hasVat" }
```

Поле лежить на **всіх** рівнях: блок будь-якого типу (лінії, картинка й
штрих-код включно), колонка таблиці, рядок будь-якої секції, рядок списку
полів. «Включно з лініями» — не для повноти: підвал із факсиміле це картинка
ПЛЮС риска, і сховати з них частину означало б лишити висячу лінію.

Корінь шляху — той самий, що в `path` поруч: дані друку для блоків, колонок,
рядків шапки й підвалу — і **запис** для рядка секції `row`.

Прапорець рахує КОМАНДА ДАНИХ (`total_vat > 0 as "hasVat"`), бо умова це шлях,
а не вираз: шаблон редагує бухгалтер, і мова всередині форми там зайва.
Рішення лишається в SQL, бланк лише показує, чим воно керує.

Хиба — `false`, `0`, `""`, `[]`, `null`, відсутнє поле, **і рядки `"false"` /
`"0"`**: команда даних, що віддає все текстом, інакше показувала б блок завжди,
а побачити це можна було б лише на папері.

Порожня умова = «видно завжди», тож наявні шаблони чинні **без міграції**.

Дві речі, які не треба компенсувати руками: схована колонка віддає ширину
сусідам сама, а комірка, об'єднана через неї, звужується (`colSpan: 3` → `2`), а
не зникає. Рядок, від якого не лишилося комірок, не друкується; таблиця без
жодної видимої колонки не друкується зовсім.

**Порожнє значення тепер друкується порожнім, а не прочерком.** Це помітно на
кожному бланку, тож варто подивитися на папір.

Раніше `stringifyPrintTemplateValue` віддавав «-» на `null`/`''`, і це було
втручанням ядра в бланк: «нічого» на регламентованій формі виглядає по-різному —
десь порожньо, десь прочерк, десь «б/н», — і вирішує це той, хто форму робить.
Найвидніше було в таблиці: у рядка-послуги немає одиниці виміру, і колонка «Од.»
друкувалася прочерком на кожному такому рядку.

Кому прочерк потрібен — ставить його **в команді даних**, де відомо, чи поле «не
заповнене», чи «не застосовне»:

```sql
coalesce(nullif(u.short_name, ''), '-') as "unit"
```

Непридатне значення (об'єкт, масив у скалярній прив'язці) теж дає порожнє:
позначкою прочерк однаково не був — помилку прив'язки видно з того, що на папері
немає значення.

**Картинка теж дістала прив'язку — логотип, печатка й факсимільний підпис
нарешті можливі.**

```json
{ "key": "stamp", "type": "image", "path": "invoice.sellerStamp", "alt": "Печатка" }
```

Робиться це разом із текстом навмисно: після цих двох у форматі не лишилося
блоків, які «майже вміють» брати значення з даних. Причина не в симетрії —
логотип і печатка належать ОРГАНІЗАЦІЇ, від імені якої друкують, а організацій
у базі кілька; статичний `src` означав би одну печатку на всі, тобто не
спрощений документ, а неправильний. Команда даних віддає `data:`-URI рядком.
Порожня прив'язка дає порожній `src`, а не «-»: прочерк тут був би зламаною
картинкою замість відсутньої.

**У типах формату з'явилися нові ОБОВ'ЯЗКОВІ поля.** Якщо в тебе є свій редактор
шаблонів (екран `admin/print_template` scaffold не везе, тож це копія), фабрики
блоків перестануть компілюватися:

| тип | нові поля |
|---|---|
| `PrintTemplateBlockBase` (усі блоки) | `visibleWhen` |
| `PrintTemplateTextBlock` | `path`, `format` |
| `PrintTemplateImageBlock` | `path` |
| `PrintTemplateTableColumn` | `visibleWhen` |
| `PrintTemplateTableRow` | `visibleWhen` |
| `PrintTemplateFieldListItem` | `visibleWhen` |

```ts
// app/admin/print_template/printTemplate.blocks.ts
{ key: newKey(), type: "text", style: "body", value: "Текст",
  path: "", format: "", visibleWhen: "",     // ← додати
  placement: …, text: … }

{ key: newKey(), type: "image", src: "", path: "", visibleWhen: "", alt: "", … }
{ key: newKey(), widthPercent: "20", visibleWhen: "" }              // колонка
{ key: newKey(), label: …, path: "", format: "", visibleWhen: "" }  // поле списку
{ key: newKey(), cells: [ … ], visibleWhen: "" }                    // рядок секції
```

Дві пастки в перебудові сітки, які легко пропустити: `gridToRows()` збирає
рядки заново — умову треба **перенести з вихідного рядка**
(`visibleWhen: sourceRows[rowIndex]?.visibleWhen ?? ""`), інакше об'єднання
комірок її мовчки стирає; те саме в `cloneBlock()` (`{ ...row, key: newKey() }`
замість перелічення полів).

У панелі властивостей додай «Показувати, коли» на чотирьох рівнях (блок, поле
списку, колонка, рядок секції) і прив'язку для тексту й картинки — усе це вже є
поруч у блоці штрих-коду й копіюється рядок у рядок. Для картинки додай ще й
кнопку «прибрати файл»: доки `src` непорожній, він перекриває прив'язку, а зняти
його не було чим.

`isPrintTemplateElementVisible` експортується з `@altera/server/print` — клич
його з полотна замість власної копії правила істинності. Полотно, яке рахує
«видно» інакше, ніж рендерер, обіцяє те, чого на папері не буде.

Далі — дві дрібниці, що вилізли на вкладках із попереднього релізу. Обидві —
вигляд, не дані; обидві прибирають обхід, який довелося написати.

**Панель дій табличної частини перемальовується сама, коли міняється `readonly`.**
Прибери обхід після `post`/`unpost`, якщо писав:

```ts
// більше не потрібно
for (const section of this.sections()) section.refresh();
```

Було так: `section.readonly` — це функція форми (`() => this.readonlyMode`), а та
читає сигнали (право на запис і `$root.item.isPosted`). Форма перемальовувалася
одразу, а `<ui-tabular-toolbar>` — ні: його власна властивість `section`
лишалася тим самим об'єктом, і lit не мав про що дізнатися. Тому після
«Розпровести» кнопки лишалися вимкненими, доки не перемкнеш вкладку — стан у
формі вже правильний, неправильне лише те, що видно. Тепер тулбар слухає сигнали
так само, як `<ui-tabular-table>` із самого початку.

`section.refresh()` нікуди не подівся — він і далі потрібен для стану ПОЗА
`$root` (кеш конфігурації, який сигналами не трекається).

**Зазор між панеллю дій і таблицею у вкладці ставить тема.** Прибери своє
правило, якщо додавав:

```css
/* більше не потрібно */
.form-tab-panel ui-tabular-toolbar { margin-bottom: 6px; }
```

Доти цей зазор давала розмітка форми — обгортка `<div class="… mb-1">` навколо
тулбара. Коли панель поїхала у `<ui-form-tabs>`, обгортка пішла разом із нею, а
відступ за собою не забрала: над кнопками 6px, під ними 0, і рамка таблиці
сходилася зі смугою дій в одну лінію. Тепер це `.form-tab-panel >
ui-tabular-toolbar { margin-bottom: 6px }` у темі. Величина та сама, що
`padding` панелі, і саме `margin`, а не `gap`: маргін із твоїм правилом не
складеться, `gap` склався б і дав подвійний зазор.

Форми БЕЗ вкладок це не зачіпає — там тулбар і таблицю ставить розмітка
застосунку, і зазор лишається її справою.

### Змінилося саме

**Зірочка обов'язковості стоїть удвічі ближче до підпису — 4px замість 8.**
Робити нічого не треба: і `renderField()`, і підписи компонентів (`ui-picker`,
`ui-date`, `ui-decimal`, `ui-select`, `ui-image`) малюють її самі.

Вісім пікселів набігали з двох джерел і жодне з них не було наміром: `.label` у
daisyUI 5 — це `inline-flex` із `gap: .375rem`, а розмітка додавала зверху ще
`ml-0.5`. На вузькому контролі підпис із позначкою заходив на сусідній —
`.label` несе `white-space: nowrap`, тож зайве не переноситься, а вилазить.

Заразом позначка дістала СВІЙ клас — `<span class="field-required">*</span>`
замість `text-error ml-0.5`, розсипаного по десятьох місцях; вигляд тепер у
темі (`.field-required` і `gap` підпису). Якщо десь малюєш зірочку своїми
руками, став цей клас — інакше поле лишиться зі старим зазором і поїде повз
решту форми:

```ts
${required ? html`<span class="field-required">*</span>` : ""}
```

## client 0.12.0 · tools 0.12.1 · skills 0.1.14 · create 0.7.7

### Потребує дії

**Смуга вкладок для кількох табличних частин — у ядрі: `<ui-form-tabs>`.**
Прибери свою, якщо писав.

```ts
import "@client/ui-kit/tabular/ui-form-tabs.ts";

html`<ui-form-tabs .tabs=${[
  { key: "goods",    titleKey: "supplierInvoice.goods",    section: this.goods },
  { key: "services", titleKey: "supplierInvoice.services", section: this.services },
  { key: "extra",    titleKey: "common.extra",             content: () => this.renderExtra() },
]}></ui-form-tabs>`
```

Вкладка з `section` малюється цілком — панель дій, таблиця, кількість рядків,
позначка помилки; `content` лишається для вкладки, у якій не таблиця, а звичайні
поля. Малюється тільки активна панель (рядки живуть у `$root`, тож сховане нічого
не губить).

Дві речі компонент бере на себе, і саме через них це місце ядра:

- **вкладка з помилкою вмикається сама.** `BaseUI` перевіряє ВСІ секції з
  `sections()`, включно зі схованими, тож банер казав «Рядок 2, «Сума»…», коли
  рядка на екрані немає. Ловиться це наявним сигналом (`pendingFocus`, який база
  ставить першій секції з помилкою), а не звіркою `errorCount`: інакше
  користувача тягло б назад щоразу, коли він пішов подивитися сусідню частину;
- **вкладка знову може бути `<button>`.** Своя смуга в розмітці форми лежить
  усередині `fieldset[disabled]` з `renderFields()`, і каскад гасить усі нативні
  контроли — проведений документ переставав гортатися. Каскад не перетинає межу
  тіньового кореня, тож усередині компонента кнопка працює, а з нею клавіатура й
  доступність.

Забирай і свої класи `.form-tab*` зі збірки Tailwind — вони тепер у темі
фреймворку (`.form-tabs`, `.form-tab`, `.form-tab-count`, `.form-tab-error`,
`.form-tab-panel`).

**Панель дій табличної частини в режимі перегляду більше не зникає — вона
вимкнена.** Те саме з колонкою кошика в рядку. Зникнення читалося як поламка:
вимкнена кнопка каже «дія тут є, зараз не можна», відсутня — «дії тут немає
ніколи», а для щойно проведеного документа правильне саме перше. Плюс проведення
не перезавантажує форму, тож смуга з'являлася й зникала під курсором, зсуваючи
таблицю. Кому потрібне саме зникнення — той не ставить `<ui-tabular-toolbar>`
(компонент незалежний) або віддає секції `rowDelete: false`.

### Змінилося саме

**Об'єкт-ссылка в схемі більше не вимагає `x-transient`.** Поле
`nomenclature: { id, name }` поруч із `nomenclatureId`, що несе `x-ref`,
генератор тепер упізнає сам і колонки під нього не шукає. Доти воно розбиралося
як звичайне поле, і публікація падала аж на `create function`:

```
column l.nomenclature does not exist
```

— причому `sql:gen` і `deno check` перед цим були зелені. Анотацію лишай, де
вона вже стоїть: вона й далі каже читачеві «це не колонка».

**Скіли: домовленості про документи**, кожна з яких коштувала переробки на
першому прикладному рішенні —

- `post` — це СТАН, а не тільки рухи: документ без жодної проводки (рахунок на
  оплату, платіжне доручення) усе одно проводиться, а `post_entries` у нього
  не відмовляє, а перевіряє;
- табличних частин стільки, скільки їх у предметній області: вони окремі не
  тому, що їх не можна звести в одну, а тому, що так зручніше заповнювати людині;
- зміна складу табличних частин — це міграція (публікація SQL нічого не зносить);
- колонку `not null default` треба передавати явно: у `MERGE` відсутній ключ
  приходить явним `null`, і умовчання колонки не спрацьовує.

## server 0.16.0 · tools 0.12.0 · skills 0.1.13 · create 0.7.6

### Потребує дії

**Сума прописом — у ядрі, форматом поля шаблону друку.**

```json
{ "schemaVersion": 2, "locale": "uk", "currency": "UAH", "blocks": [
  { "type": "field-list", "items": [
    { "key": "sum", "label": "Сума словами", "path": "document.total", "format": "amountInWords" }
  ]}
]}
```

`format` працює на елементі `field-list` і на комірці таблиці; мова й валюта —
у корені шаблону (умовчання `uk`/`UAH`, тож наявні шаблони чинні без міграції).
Мови: `uk`, `ru`, `en`.

**Прибери свою функцію**, якщо писав: правило належить мові, а не застосунку, і
помиляються в ньому однаково — рід належить розряду («дві тисячі», але «два
мільйони»), форму вибирають дві останні цифри (111 — «гривень»), порожній
розряд усе одно називається. На 1234,56 не видно жодної з цих помилок.

Рахувати суму словами в команді даних більше не треба: прив'яжи число, а як його
надрукувати, каже шаблон — те саме поле можна вивести і цифрами, і прописом.
Валюта з неоголошеними формами **відхиляється** й друкується числом (як помилкове
значення штрих-кода), тож перевіряй надрукований результат, а не факт виклику.

**Тим, хто конструює блоки шаблону в TypeScript**, доведеться поправити типи:
`PrintTemplateFieldListItem` і `PrintTemplateTableCell` дістали обов'язкове поле
`format` (порожній рядок — без формату). Саме через це сервер іде мінором.

**`x-ref` бачить моделі, чий SQL не генерується.** Карта посилань будувалася з
`app/sql.json`, тобто з переліку тих, хто везе СВІЙ SQL, — і посилання на
`user` чи `user_group` падало з «модель не знайдена». «Мій SQL пишуть інші» та
«на мене не можна посилатися» — різні речі.

Тепер карта будується з манифестів усього дерева (той самий обхід, що й у
реєстру рантайму). Плюс манифест приймає ім'я таблиці, коли воно не збігається з
ключем моделі:

```json
{ "model": "user", "table": "users" }
```

**Перевір імена файлів схем:** генератор шукає `<model>.schema.ts` і мовчки
пропускав модель, якщо файл названо інакше (`userGroup.schema.ts`). Тепер пропуск
друкується рядком у `--verbose`, але сама вимога не змінилася — модель зі схемою
під іншим іменем у карту посилань не потрапляє.

### Тільки для нових застосунків

**Піни `@altera/tools` у `Dockerfile` і `docker-compose.yml` шаблону підняті до
поточних.** Вони застрягли на `^0.5.x` при `0.11.x`: каретка на `0.x` не пускає
далі наступного мінора, тож контейнерний `solution:update` ішов інструментом
піврічної давнини проти свіжого сервера — та сама розбіжність версій, через яку
вже був фікс-реліз, лише в місці, куди ніхто не дивився.

Наявних застосунків це не стосується — шаблон їде тільки в нові. **Якщо ти
розгортаєш у контейнері**, поправ у себе ці два рядки руками; шукати їх за
`jsr:@altera/tools@`.

Проба пінів тепер читає й ці два файли — вона сканує їх текстом, тож формат
значення не має. Доти перевірялися лише `deno.json`, і саме тому дрейф не було
видно.

## server 0.15.0 · client 0.11.1 · tools 0.11.0 · skills 0.1.11 · create 0.7.4

### Потребує дії

**З'явилося спільне місце для налаштувань — пакет ядра `@core/setting`.** Додайте
його в `app/sql.json` (одразу за `@core/audit` — залежить лише від `app.users`),
інакше публікація впаде на відсутній `app.setting_value`.

Одна таблиця на обидві області: `user_id is null` — значення установки, інакше —
значення людини. Порядок накладання названий один раз (`app.setting_read`):
значення користувача сильніше за значення установки. Користувацька область поки
не ввімкнена, але колонка є від першого дня — додавати її потім означало б міняти
ключ уже наповненої таблиці.

**Що можна налаштувати, каже застосунок:** рядки сіє його `db/data.sql` через
`on conflict do nothing`, а значення після першого сіву належить адміністратору й
перевикочування його не затирає — той самий поділ, що в нумераторах, шаблонах
друку й рівнях журналу. Зворотний бік той самий: змінене в сіді умовчання на вже
налаштованій базі **не застосується**.

Читати з SQL — `app.setting_read(user_id, key)`; усе одразу мапою —
`app.setting_effective`. Екран у застосунку робиться звичайною admin-моделлю; у
цьому репозиторії еталон — `app/admin/setting/`.

**Розріз за субконто більше не губить рухів без цього субконто — і числа у
звітах зміняться.** `app.acc_balance_turnover_by_dim` відбирав значення виміру
через `cross join lateral`, тобто рух, у якого цього субконто немає, зникав із
результату **цілком** — не ставав рядком із порожнім значенням, а зникав.

Помилка мовчить уся: функція не падає, кожен рядок окремо правильний,
неправильна лише їхня СУМА — величина, якої ніхто не звіряє з рахунком. На
даних altera-buh рахунок 311 давав 117 500 через `acc_balance_turnover` і 5 500
у розрізі статті руху коштів; різниця — початкові залишки, де статті руху немає
й бути не може.

Суть у тому, що субконто веде не рахунок, а ПРОВОДКА, і ядро саме це допускає:
`chart_of_account_analytic.is_required` дозволяє необов'язковий слот. Тобто шар
читання суперечив власному правилу схеми.

Тепер рух без виміру приходить окремим рядком із `value_id is null` — останнім
(`null` в ASC сортується в кінець). **Перевірте свої звіти, що беруть розріз:**
сума рядків тепер дорівнює сальдо рахунку, тож підсумки зростуть, а в аркуші
з'явиться рядок без значення виміру. Назвати його «&lt;не вказано&gt;», згорнути чи
відсіяти — вирішує звіт: шар віддає рух, а не подання.

Повернутися це не може — інваріант «сума розрізу = підсумок рахунку» тепер під
пробою (`deno task smoke`, крок «регістр: розріз за субконто не губить рухів без
нього»).

**Підбір можна звузити відбором — і невідомий ключ він тепер ВІДХИЛЯЄ.**
Половина механізму була давно: `<ui-picker>` слав параметри в payload. Другої не
було — генератор складав фільтри лише для `_list`, тож у `_lookup` вони мовчки
ігнорувалися, і на екрані це виглядало як «відбір не працює», а не «відбору
немає».

Тепер `_lookup` бере ті самі оголошення `x-filter`, що й `_list`, а пікер веде
відбір однією властивістю в обидва шляхи вибору — випадний список і діалог:

```html
<ui-picker url="catalog/bank_account"
  .filters=${{ organizationId: item.organizationId }}
  .value=${item.bankAccount ?? null}
  @value-changed=${(e) => this.setRef("bankAccount", e.detail.value)}
></ui-picker>
```

**Перегенеруйте моделі, чий підбір має звужуватися** (`deno task sql:gen
<family>/<model>`), і оголосіть потрібні поля `x-filter` у схемі, якщо їх там ще
немає.

**Що може зламатися на місці:** якщо ваша форма вже слала в підбір параметри —
через `fetch-params` або `picker-params`, — і серед них є ключ, якого модель не
оголошує, підбір тепер **відмовляє**. Доти він мовчки віддавав повний перелік.
Це навмисно: форма, яка звузила підбір, вважає, що звузила його, а друкарська
помилка в імені фільтра не лишала жодного сліду. Модель, яка фільтрів не
оголошує, відмовляє на будь-якому наборі — з тієї самої причини.

Відбір підбору **не є** фільтром списку, хоч і користується тим самим
оголошенням: у списку його задає користувач панеллю й може зняти, тут — форма, і
зняти його не можна. Рахунок своєї організації в полі «рахунок платника» — не
звужений вибір, а помилка вводу.

### Змінилося саме

**Розміщення випадного вікна доступне застосунку — `@altera/client/ui-kit/popover.ts`.**
Модуль був у пакеті й робив рівно потрібне (`computePlacement` + `placePopover`:
відкриття вгору, коли внизу не влазить, і притискання до краю вікна), ним
користуються `ui-picker`, `ui-date` і `ui-period` — але в карті експортів його не
було, і своє меню застосунок розміщував власною математикою. Тобто виправлення,
зроблене саме тому, що троє контролів рахували позицію кожен по-своєму й однаково
неповно, було сховане від четвертого охочого.

Разом із розрахунком їде `POPOVER_ANCHORED_STYLE` — скид, без якого браузер
центрує `[popover]` у в'юпорті власними `inset: 0` + `margin: auto`, і задані
`top`/`left` не діють узагалі:

```ts
import { placePopover, POPOVER_ANCHORED_STYLE } from "@altera/client/ui-kit/popover.ts";

html`<div popover="manual" style=${`${POPOVER_ANCHORED_STYLE} width:20rem;`}>…</div>`
// показати, і ТІЛЬКИ ПОТІМ розміщувати: у схованого вікна немає розмірів
popover.showPopover();
placePopover(popover, anchor, { desiredHeight: 320 });
```

Доти цей рядок стилю був переписаний слово в слово в трьох контролах фреймворку;
тепер він один, і застосунок бере той самий.

**Типи документів і правила нумерації тепер сіються ПЕРЕД сідами застосунку.**
Доти згенеровані секції йшли в самий кінець секції даних, тож сід, який заводить
документ викликом `<model>_save` — саме так, як радить документація, — падав на
порожній базі:

```
Тип документа «expense_report» не зареєстровано в app.document_type
```

Гірше за саму помилку було те, що вона **самозакривалася**: публікація
зупинялася до реєстрації типів, тож наступна впиралася в те саме, і вийти з кола
можна було лише правкою сіду або ручним `insert`. На чистій установці (перший
`sql:publish` у замовника) у це впирався б кожен, чий сід заводить документ.

Дорогою з'ясувалося, що сід нумератора робив **дві різні речі одним блоком**, і
місця в пакеті в них протилежні: оголошення правила потрібне ДО сідів (сід бере
з нього номер), а `numerator_reseed` — ПІСЛЯ них (він підтягує лічильник під
рядки, які сід вставив прямим `insert` із власним кодом). Тому в зібраному
пакеті тепер дві секції замість однієї — `_generated/numerators.data.sql` на
початку й `_generated/numerators-reseed.data.sql` наприкінці.

Робити нічого не треба — досить перезібрати пакет (`deno task sql:assemble`).
Порядок під пробою: `tools/assemble-sql-package_test.ts`.

**Закрита вкладка повертає в ту, з якої її відкрили.** Нова вкладка стає
останньою в смузі, тож сусід ліворуч від неї — це те, що відкривали перед нею, а
не те, куди користувач збирається повернутися: відкривши об'єкт зі списку
посеред смуги, після закриття він опинявся у випадковій чужій вкладці, а не в
своєму списку з відбором і позицією курсора. Тепер вкладка пам'ятає, з якої
народилася, і закриття веде туди; позиційний вибір лишається запасним — для
вкладки, чий «батько» уже закритий, і для відновлених після перезавантаження
(id там генеруються заново, тож зв'язок було б вигадано). Робити нічого не
треба.

**Смуга вкладок більше не прокручується — те, що не вміщається, іде під кнопку
історії** в правому кінці смуги. Доти зайві ярлики виїжджали за екран і
з'являлася горизонтальна прокрутка; разом зі зникненням кнопки «Закрити» у формі
це означало, що таку вкладку не закрити взагалі, доки не докрутиш до неї.

Ховається найдавніше вживана — той самий порядок, що й у витісненні, тож вкладка
спершу зникає зі смуги й лише потім, дійшовши до ліміту в 30 відкритих,
закривається насправді. Активна не ховається ніколи. Приховані лишаються ЖИВИМИ:
дані завантажені, стан форми на місці — по кліку в переліку вкладка просто
повертається у смугу. Там же її можна й закрити, не відкриваючи; якщо серед
прихованих є незбережена, на кнопці стоїть «*». Робити нічого не треба.

## server 0.13.0 · client 0.11.0 · tools 0.10.0 · skills 0.1.9 · create 0.7.2

### Потребує дії

**`<ui-picker>` приймає ссылку ОБ'ЄКТОМ — контракт замінено, старий прибрано.**
Значення тепер одне (`value`), а не пара «id окремо, підпис окремо», і подія
одна (`value-changed`) — та сама, що в `ui-date` і `ui-decimal`:

```html
<!-- було -->
<ui-picker url="catalog/counterparty" fetch="lookup"
  .selectedId=${item.counterpartyId ?? ""}
  .displayValue=${item.counterparty?.name ?? ""}
  @item-selected=${(e) => { … два записи … }}
  @item-cleared=${() => { … ще два … }}
></ui-picker>

<!-- стало -->
<ui-picker url="catalog/counterparty"
  .value=${item.counterparty ?? null}
  @value-changed=${(e) => this.setRef("counterparty", e.detail.value)}
></ui-picker>
```

Прибрано: `selectedId`, `displayValue`, `item-selected`, `item-cleared`,
`fetch`. Забутий пікер тепер **ламається голосно** (властивості немає, подія не
слухається), а не показує порожнє поле — саме заради цього старе прибрано, а не
лишено «поки що працюючим».

Чому об'єкт: підпис і так завжди приїжджав у відповіді — `x-ref` кладе вкладений
`{ id, name }` у `get`, у рядок списку, в эхо фільтра й у `lookup`. Пікер тепер
бере його як є, замість того щоб форма розбирала його на дві прив'язки й
збирала назад.

Що допомагає при переході:

- **`BaseUI.setRef(key, value)`** пише і сам об'єкт, і `<name>Id` — розсинхронити
  їх нема як. Ім'я id-поля виводиться як `<key>Id`, інакше третім аргументом;
- **`save` приймає обидва вигляди** — `counterpartyId` як раніше або
  `counterparty: {id}`. Тобто форма може тримати лише об'єкт;
- **у фільтрах змін майже немає**: значення ссылочного фільтра вже об'єкт, тож
  `.value=${this.filterValue("counterparty") ?? null}` і
  `@value-changed=${(e) => this.setFilter("counterparty", e.detail.value)}`;
- **у табличній частині — нічого**: колонку `picker` перевела сама база
  (`fetchCommand` з опцій колонки прибрано за непотрібністю).

Тип події експортується: `import type { PickerChangeEvent } from
"@client/ui-kit/components/ui-picker.ts"` — локальні `type PickEvent = …` у
формах більше не потрібні.

**Періодичні дані генеруються з оголошення.** Ключ, дата, значення — четвертий
типовий вид моделі після довідника, документа й регістру, і однаковий скрізь.
Тепер він оголошується в манифесті регістру:

```jsonc
"periodic": { "key": ["currencyId"], "period": "period" }
```

і `sql:gen` дає до звичайного CRUD ще три команди — `at` (зріз останнього на
дату), `history`, `set` (перезапис значення на дату, `merge` за природним
ключем) — плюс **унікальний індекс `(ключ…, період desc)`**. Індекс кладе сам
генератор: унікальність тримає `set`, а напрямок — те, що зріз стає пошуком, а
не скануванням. У `struc.sql` його писати не треба.

Права трьох команд виводяться звідти ж (`at`/`history` — `view`, `set` —
`edit`), і рантайм маршрутизує їх без запису в `commands.sql`.

Що це прибирає: перший такий регістр коштував ≈130 рядків рукописного SQL, і
кожен наступний коштував би стільки ж — зі своїм шансом розійтися з контрактом.
Еталон — `app/data/currency_rate/` у монорепозиторії.

**Проводка може мати порожній бік — але тільки на забалансовому рахунку.**
Забалансовий облік у плані рахунків України однобічний за визначенням: «Дт 021
Устаткування, прийняте для монтажу» не кореспондує ні з чим. Виразити це було
нічим — обидві колонки `app.journal_entry` були `not null`, а обхід (парна
проводка через допоміжний рахунок) псує самі дані: у регістрі з'являється
кореспонденція, якої в обліку немає, і звіт по кореспонденціях починає показувати
неіснуючі зв'язки.

Тепер `debit_account` і `credit_account` нульові, а зводить їх обмеження
`ck_journal_entry_sides` (хоча б один бік). `doc_entry_add` приймає порожній бік
і вимагає, щоб рахунок був `is_off_balance`: на балансовому рахунку однобічна
проводка — не задум, а недописаний рядок, і мовчки прийняти його не можна.

**Перевірте власні звіти по регістру.** Запит виду

```sql
select debit_account as account, amount from app.journal_entry
union all
select credit_account, amount from app.journal_entry
```

тепер збирає порожній бік в окремий рахунок «null» — з сумою, яка робить
підсумки «зведеними». Додайте `where … is not null` у кожен бік (в оборотці
цього репозиторію це зроблено). Заразом варто вирішити, що робити із
забалансовими рахунками в підсумку: тут вони лишилися рядком, але з суми
вилучені — інакше «баланс зійшовся» перестає щось означати.

Своєму документу, який веде забалансовий облік, лишається передати `null` одним
боком у `doc_entry_add`. У ручній операції це вже так: порожній один бік

## server 0.12.0 · client 0.10.0 · tools 0.9.1 · skills 0.1.8 · create 0.7.1

### Потребує дії

**Документні моделі нарешті генеруються поза монорепозиторієм.** `sql:gen`
шукав схему спільної шапки за шляхом `app/../client/shared/schema.ts` — тобто за
розкладкою МОНОРЕПОЗИТОРІЮ, зашитою в інструмент, який роздається з JSR. У
встановленому застосунку каталогу `client/` немає й бути не може (фреймворк
лежить у `vendor/`, а `@client/` — аліас карти імпортів), тож `type: "document"`
не генерувався взагалі:

```
✗ operation/manual_entry: Module not found "file:///…/client/shared/schema.ts"
```

Тепер шапка береться звідти ж, звідки її бере сам застосунок — з його карти
імпортів (`@client/`, а без аліаса — `@altera/client`), тобто **версію називає
застосунок**, а не інструмент. Це навмисно не залежність `tools` від
`@altera/client`: інакше в застосунку опинилися б дві версії клієнта — та сама
пастка, що вже стріляла з `@altera/server`.

Що це означає на місці: документи, які доводилося заводити в монорепозиторії
фреймворку й копіювати `.gen.sql` руками, тепер генеруються у себе. Прогоніть
`deno task sql:gen <family>/<model>` по своїх документах — і звіряйте вихід із
тим, що лежить: копія могла відстати від схеми.

Якщо карти імпортів немає взагалі, відмова тепер називає причину замість
`Module not found`.

**Ядро більше не сіє виміри субконто й прив'язки до рахунків.** У
`@core/document_core` лежали ПРИКЛАДНІ дані: описи довідників застосунку
(`counterparty`, `bank` — з іменами його таблиць) і прив'язки до рахунків
українського плану (311–314, 361, 631…), причому з `on conflict … do update`.
Тобто ядро лишалося власником слота назавжди: застосунок, що ставив на 311 свій
вимір, після кожного `sql:publish` мовчки отримував назад ядровий — без помилки,
без сліду, помітно аж у проводці через місяць.

Тепер це оголошує застосунок, і в двох місцях за змістом:

```sql
-- app/catalog/bank/db/data.sql — вимір оголошує модель, чий довідник ним працює
insert into app.analytic_dimension (code, name, entity_kind, model_key,
  target_table, id_column, code_column, name_column, is_active) values
  ('bank', 'Банк', 'catalog', 'bank', 'app.bank', 'id', 'mfo', 'name', true)
on conflict (code) do nothing;

-- app/catalog/chart_of_account/db/data.sql — прив'язку до рахунків веде план
insert into app.chart_of_account_analytic (account_code, slot_no, dimension_code, is_required)
values ('311', 1, 'bank', true), …
on conflict (account_code, slot_no) do nothing;
```

**Наявні бази від оновлення нічого не втрачають** — рядки вже стоять, а `do
nothing` їх не чіпає. Але після оновлення **чиста** база отримає лише те, що
оголосив застосунок: якщо ви покладалися на сід ядра, перенесіть ці рядки до
себе, інакше проведення впаде на «рахунок веде субконто, якого немає».

**Порядок у `sql.json` став значущим:** модель, що оголошує вимір
(`catalog/bank`, `catalog/counterparty`), стоїть **вище** за план рахунків.
Нижче — і прив'язка не знайде виміру; зовнішній ключ зробить це помилкою
публікації, а не тихим пропуском.

Туди ж переїхало виправлення `code_column` виміру «Банк» (`bank` → `mfo`) — у
`app/catalog/bank/db/migration.sql`. У пакеті ядра імені прикладної таблиці
більше немає ніде.

**Гак «перед записом документа».** Заборона закритого періоду й будь-яка
перевірка «чи можна чіпати цей документ» тепер має одну точку: ядро кличе
`app.doc_before_write(p_user_id, p_op, p_doc, p_prev)` зі свого тригера на
`app.document`. Вмикається створенням функції — реєструвати нічого не треба:

```sql
create function app.doc_before_write(
  p_user_id bigint, p_op text, p_doc jsonb, p_prev jsonb
) returns void language plpgsql as $$
begin
  if p_op in ('insert', 'update', 'post', 'unpost')
     and (p_doc->>'doc_date')::date <= app.period_lock_date(p_user_id) then
    raise exception '@[app.periodLocked]%',
      jsonb_build_object('date', p_doc->>'doc_date')::text;
  end if;
end $$;
```

`p_op` називає дію словом застосунку: `insert`, `update`, `post`, `unpost`,
`delete` (позначка), `undelete`, `purge`. З `TG_OP` цього не видно — і
проведення, і позначка на видалення там `update`, — тому називає ядро.

**Свій тригер на `app.document` після цього можна прибрати.** Заразом зникає
пастка, на якій такі сторожі мовчки не спрацьовують: `new is not null` істинне
лише коли непорожні ВСІ поля рядка, а в шапці є nullable-колонки — тригер стоїть,
увімкнений, і не робить нічого.

Функція з іншим підписом валить запис із підказкою про очікуваний: мовчазний
пропуск тут гірший за відсутність гака — застосунок вважав би, що заборона діє.

**Порожній звіт малює база — своє «немає даних» у `<tbody>` більше не
показується.** `ReportBase` кличе `renderBody()` лише коли є дані, інакше малює
порожній стан сам і називає причину: звіт ще не формували («натисніть
„Оновити“») чи сформували й порожньо («немає даних **за відбором:** ТОВ «Демо» ·
Липень 2026»). Рядок відбору дає `emptyHint()` з умовчанням `printSubtitle()` —
той самий підпис, що вже йде на папір.

Приберіть із звітів рядки виду:

```ts
${rows.length === 0 ? html`<tr><td colspan="8">${t("common.noData")}</td></tr>` : ""}
```

**Перевірте `hasData` там, де порожній перелік рядків — це ще не порожній
звіт.** База вважає даними непорожній `$root.rows`; картка рахунку з вхідним
сальдо й без оборотів за період під це не підпадає, а відповідь у неї є. Тоді
`hasData` перекривається — заразом це вмикає кнопки друку й експорту:

```ts
protected override get hasData(): boolean {
  if (super.hasData) return true;
  const { openingDebit, openingCredit } = this.$root.totals;
  return Number(openingDebit) !== 0 || Number(openingCredit) !== 0;
}
```

## client 0.9.1 · tools 0.9.0 · skills 0.1.7 · create 0.7.0

### Потребує дії

**`lookup` навчився ссылкам — моделі з ссылкою в пікері треба перегенерувати.**
Раніше `<Model>LookupRowSchema` із вкладеним об'єктом (`counterparty`) давав
зламану функцію: генератор виводив `r_counterparty.name`, а `left join`, що
створює цей аліас, ставив тільки в `list`. `create function` тіла не перевіряє,
тож генерація й публікація були зелені, а пікер падав на першому відкритті:

```
ERROR: column t.counterparty does not exist
```

Тепер `lookup` бере ті самі join-и, що й `list`. Ссылка називається **ключем
вкладеного об'єкта**, а `x-ref` лишається на полі `<name>Id` в `ItemSchema` —
дублювати анотацію не треба й не можна:

```ts
export const InvoiceLookupRowSchema = Type.Object({
  id:           Type.String({ "x-db-type": "bigint" }),
  number:       Type.Optional(Type.String()),
  counterparty: Type.Object({ id: Type.String(), name: Type.String() }),
});
```

Прогоніть `deno task sql:gen <family>/<model>` для моделей, чий пікер показує
ссылку, і опублікуйте. Рукописний обхід (копія `_lookup` з дописаним join) після
цього можна викидати цілком.

**Пошук у пікері тепер шукає й по ссылках** — там, де в схемі стоїть
`searchable: true`. Доти та сама анотація діяла в списку й мовчки не діяла в
підборі. Якщо шукати по назві контрагента в пікері не треба — заберіть
`searchable` (він і в списку тоді зникне) або приберіть ссылку з
`LookupRowSchema`.

### Змінилося саме

**Esc над відкритим `<dialog>` більше не закриває вкладку під ним.** Оболонка
слухає клавіатуру на `window` і, впізнавши Esc, кликала `preventDefault()` —
тобто скасовувала закриття самого діалогу й закривала вкладку замість нього.
Виглядало це як «вікно не реагує на Esc», а справжня втрата була поруч: під ним
зникала вкладка з незбереженою формою. Правило «обробив — познач» тут не
працювало ніколи: нативне вікно закриває себе браузером, і позначати подію нема
кому. Тепер оболонка впізнає відкрите `<dialog>` у `composedPath()` сама —
власним діалогам застосунку робити для цього нічого не треба.

## client 0.9.0 · server 0.11.1 · tools 0.8.0 · skills 0.1.6 · create 0.6.1

### Потребує дії

**Звіти: команда `index` тепер генерується.** `sql:gen` складає обгортку
`app.<report>_index` у `db/_generated/<report>.index.gen.sql` — розбір
`payload.filters`, відмову при незаповненому обов'язковому фільтрі, эхо
`$filters` і конверт. Рукописним лишається запит.

Наявні звіти **не ламаються**: збирач кладе ваш `db/<report>.sql` після
згенерованого файлу, тож ваш `_index` його перекриває. Але з'являється мертвий
згенерований файл і рядок `⚠` про відсутню `<Pascal>FiltersSchema`. Щоб перейти
на новий механізм:

1. оголосити походження ссылочних фільтрів — `x-ref` у схемі фільтрів;
2. звести обов'язковість: те, без чого звіт не будується, — без `Type.Optional`;
3. перейменувати `app.<report>_index(user_id, payload)` на
   `app.<report>_data(user_id, filters)` — фільтри приходять уже розібраними
   (ссылка згорнута до id: `organization` → `organizationId`);
4. прибрати з нього конверт, эхо `$filters` і перевірки обов'язкових — це тепер
   робить обгортка; повертати лише `{rows, totals, extra}`.

Подробиці — скіл `model-report-form`.

**`<ui-picker>`: умовчання `fetch` стало `lookup`** (було `fetch`). Явний
атрибут працює як раніше. Умовчання доти не працювало ні в кого — команди
`{model}_fetch` немає в жодної моделі, — тож ламається лише той випадок, де
команда справді зветься `fetch`: назвіть її явно.

**`@source`, що не веде в наявний каталог, валить збірку** — з іменем файлу,
номером рядка й підказкою. Раніше це мовчало, і класи, вжиті лише всередині
фреймворку, просто не потрапляли в CSS: кожен його екран виглядав не так, при
зеленій збірці. Найчастіша причина — перенесення рішення між деревами; у
встановленому застосунку правильний шлях:

```css
@source "../../vendor/jsr.io/@altera";
```

**`x-db-type` перевіряється за списком.** `numeric(10,2)` тепер помилка
генерації, а не мовчазний текстовий fallback, який падав аж на першому `save`.
Пишіть голий тип (`numeric`), точність задає DDL.

**Таблиця генерованої моделі мусить мати `created_at` і `updated_at`.** Це було
завжди — `save` пише `updated_at = now()` беззастережно, — але ніде не було
сказано; без них генерація й публікація зелені, а падає перший запис.

### Змінилося саме

**`type: register` отримує генерований CRUD** — `list`/`get`/`save`/`delete`, усе
як у довідника, але **без `lookup`** (на регістр ніхто не посилається), і
`<Model>LookupRowSchema` від нього не вимагається. Позначки на видалення
генератор не додає, якщо в схемі немає поля `isDeleted`, — для регістра це
правильно: позначений рядок мовчки псував би «зріз останнього». Власне читання
регістру (`_at`, `_history`, `_set`) лишається рукописним.

**Виміри субконто.** Опис довідника (`target_table`, `code_column`,
`name_column`) більше не переписується при кожній публікації — сід дає лише
умовчання, далі опис належить установці. Неіснуюча колонка в описі тепер
відхиляється тригером при записі, а не вилазить при проведенні документа
(`ERROR: column "code" does not exist`). Сід ставить лише ті виміри й аналітики
рахунків, чиї таблиці й рахунки в установці справді є. На базах, де вимір «Банк»
описаний колонкою `code`, якої в `app.bank` немає, міграція виправляє його на
`mfo` — але тільки якщо колонки `code` справді немає, а `mfo` є.

**Звіт відмовляє замість порожнього аркуша**, коли не заповнений обов'язковий
фільтр: конверт `ok:false` з прив'язкою до поля.

**`<ui-picker>` попереджає в консолі**, коли заданий `selected-id` без
`display-value` — це завжди означає, що форма не додала підпису, а на екрані
виглядає як «дані не прийшли».
