# {{name}} — застосунок на фреймворку Altera

> Цей файл твій. Scaffold поклав його один раз і більше не чіпає — дописуй сюди правила
> свого проєкту (доменні домовленості, схему рахунків, порядок проведення документів).
> Знання про сам фреймворк живе не тут, а в `.claude/skills/` — воно оновлюється разом
> з пакетами (`deno task skills:sync`).

Deno + Lit Web Components + Vite + Tailwind CSS v4 + daisyUI v5 на фронтенді, Danet на
бекенді, PostgreSQL як база. Фреймворк приходить пакетами `@altera/client`,
`@altera/server`, `@altera/tools` — його вихідники лежать у `vendor/` і **не редагуються**.
Тут живе тільки застосунок: моделі, їх SQL і оболонка.

## Головне правило роботи тут

**Це застосунок НА ФРЕЙМВОРКУ, а не самостійний проєкт.** Список, форма, діалог вибору,
звіт, друкована форма, права, вкладення, таблична частина документа — усе це фреймворк уже
вміє, і задача полягає в тому, щоб **оголосити** потрібне, а не написати його.

Порядок для будь-якої моделі чи екрана — один і той самий:

1. **Взяти скіл.** `.claude/skills/` — не довідка «якщо раптом», а перший крок:
   `model-feature-architecture` (структура моделі), `typebox-model-schema` (схема),
   `model-list-form` / `model-form-root` / `model-picker-form` / `model-report-form`
   (екрани), `screen-design-rules` (оформлення), `db-function-contract` (SQL),
   `model-command-access` (права нестандартної команди).
2. **Робити засобами фреймворку** — базові класи, компоненти `ui-kit`, згенерований CRUD.
   Приклади в застосунку дивитися **після** скіла, а не замість: з коду видно *як*
   зроблено і не видно *чому*, а скіл називає саме інваріант.
3. **Не вистачило можливостей фреймворку — спинитися і спитати.** Не «обійти й записати», а
   саме спинитися: обхід не пишеться, доки на нього не дано явної вказівки, і в
   автоматичному режимі теж. Більшість «фреймворк цього не вміє» виявляється невідомим гаком
   або неправильно поставленою задачею, і з'ясувати це коштує одного речення, а не сотні
   рядків, які потім доведеться зносити. Подробиці — розділ
   [«Якщо фреймворку бракує функціональності»](#якщо-фреймворку-бракує-функціональності).

Ознаки того, що робота пішла не туди: у формі з'явилася рукописна таблиця з пагінацією;
компонент `ui-kit` скопійовано в `app/`; у файлі моделі — власний `fetch` до `/api`;
базовий клас підмінено своїм. Кожне з цього означає, що крок 1 пропущено.

## Команди

```bash
deno task dev              # frontend + backend разом
deno task dev:server       # тільки backend (--watch)
deno task dev:front        # тільки Vite
deno task sql:gen <family>/<model>   # згенерувати CRUD-SQL ОДНІЄЇ моделі зі схеми
deno task sql:registry     # перегенерувати app/_generated/** з manifest.json
deno task locales:build    # зібрати app/_locales/*.json із _locales/ поряд із кодом
deno task sql:assemble     # зібрати SQL-пакет з db/ файлів моделей
deno task sql:publish      # опублікувати SQL у PostgreSQL
deno task check            # типи ВСЬОГО app/ — екрани вантажаться динамічно, вхід їх не бачить
deno task skills:sync      # оновити .claude/skills + FRAMEWORK-CHANGELOG.md з @altera/skills
deno task startdb          # docker compose up -d (PostgreSQL)
deno task build:front      # продуктивна збірка
deno task solution:export  # вивантажити рішення (app/) у переносимий пакет
deno task solution:status  # чи чіпали app/ після поставки (на підтримці / знято)
deno task solution:update -- <пакет.tar.gz> [--check] [--force]   # оновити рішення
```

## Перенесення рішення

Прикладне рішення — це каталог `app/` цілком: моделі, локалі, стилі, оболонка,
обидва composition root. Усе решта в корені (`deno.json`, `vite.config.ts`,
`scripts/`, `tsconfig.json`) належить **каркасу** — його дає scaffold, і пакет
рішення його не везе.

Тому `app/` мусить лишатися переносимим: у фреймворк він ходить **тільки** через
`@client/…` і `@altera/server`, ніколи відносним шляхом. У монорепо фреймворку
такий шлях компілюється, тут — ні: фреймворк лежить у `vendor/` і видний лише
через експорт-мапу пакета.

Що станеться з наявним `app/` при завантаженні, вирішує **стан підтримки** —
див. наступний розділ. `solution:import` кладе лише файли; увесь ланцюжок після
них робить `solution:update`.

Карту імпортів інструмент не редагує: якщо рішення користується пакетом, якого
тут немає, він друкує готовий рядок для `imports` — версії, на яких стоїть
застосунок, чужа рука міняти не повинна.

## Оновлення

**Установка сама знає, чи ти чіпав `app/` після поставки** — манифест
`app/.solution.json` несе контрольну суму кожного файлу:

```bash
deno task solution:status                              # на підтримці / знято / невідомо
deno task solution:update -- ./erp-1.2.0.tar.gz --check
deno task solution:update -- ./erp-1.2.0.tar.gz
```

Не чіпав — оновлення заміняє `app/` автоматично. Чіпав — `app/` **не
чіпається**: пакет лягає в `app.incoming/`, і друкується, чого торкнулися
обидві сторони. Оголошувати нічого не треба, `--force` затирає свідомо.

`solution:update` робить увесь ланцюжок (розпакування → `sql:registry` →
`sql:deploy --yes` → `build:front`), після чого застосунок треба
**перезапустити**. Окремою командою, а не кнопкою: той, кого заміняють, не має
заміняти себе сам — і серверу тоді не потрібні ані `--allow-write`, ані
`--allow-run`.

Перед оновленням — дамп бази: міграції ходять тільки вперед. І тримай у дереві
`deno.lock` (`deno install`) — без нього щойно опублікована версія фреймворку не
резолвиться в рантаймі.

**Фреймворк** оновлюється окремо: піни живуть у `deno.json` у двох місцях — в
`imports` і в рядках задач (`sql:registry`, `sql:gen`, `solution:*`,
`skills:sync`), другі править тільки рука. Версію називає рішення: пакет несе
піни, під якими зібраний, і оновлення зупиниться, якщо тут стоїть старіше.

**У контейнері** образ несе фреймворк, а `app/` і `dist/` — том:

```bash
docker compose --profile prod build
docker compose --profile prod run --rm update ./erp-1.2.0.tar.gz
docker compose --profile prod restart app
```

Нове рішення — на том, образ той самий; новий фреймворк — новий образ, том той
самий. **Після заміни образу обов'язково перезібрати**: на томі лишаються
`dist/` і `_sqlpackage/` від попередньої версії.

**Якщо `app/` змінюєш і код у Git:** тримай гілку `vendor` із незміненим
рішенням (заведи її до першої правки). Кожна поставка: імпорт `--force` у
`vendor` → коміт → `git merge` у робочу гілку. Конфлікти — список місць, які
треба звести свідомо.

**На Deno Deploy** контейнер і `solution:update` не працюють (файлова система
лише для читання): імпорт локально → commit → push, решту зробить платформа.

**Прибирання за собою — твоя робота, не інструмента.** Публікація SQL додає й
змінює, але нічого не зносить: прибрана модель лишає в базі свої таблиці,
функції й пункти меню. Тому, коли прибираєш модель, пиши `drop ... if exists` і
видалення пункту меню **в міграцію**. Дві пастки:

- клади цю міграцію в модель, яка **лишається** в `app/sql.json`. Збирач бере
  `<model>/db/migration.sql` лише для перелічених там моделей, а відсутній файл
  мовчки пропускає — тож `drop` у міграції моделі, яку ти зі списку прибираєш,
  не збереться більше ніколи;
- пиши `if exists`: `migration.sql` виконується цілком при **кожній** публікації,
  журналу застосованого немає, і скрипт лишиться в обігу назавжди.

Після зміни моделі майже завжди потрібне одне й те саме:

```bash
deno task sql:registry && deno task sql:assemble && deno task sql:publish
```

## Структура

```
app/
  <family>/<model>/         # одна модель — один каталог
    manifest.json           # декларація: model, type, schema, views, commands, agent
    <model>.schema.ts       # TypeBox-схема — ЄДИНЕ джерело типів для форм і SQL
    <Model>List.ts          # список        (наслідує ModelListBase)
    <Model>Edit.ts          # форма         (наслідує BaseUI)
    <Model>Picker.ts        # діалог вибору (наслідує ModelPickerBase)
    _locales/               # рядки ЦІЄЇ моделі: en.json, uk.json
    db/
      struc.sql             # DDL таблиць
      _generated/*.crud.gen.sql   # згенерований CRUD — правити не тут
      <model>.custom.sql    # доробки поверх генерації: проведення, нестандартні команди
      migration.sql         # міграції
      data.sql              # seed-дані
    prints/                 # шаблони друкованих форм
  _generated/               # реєстр моделей, прив'язки TS-команд, маршрути агента, маніфест в'ю
                            #   model-registry — дані (їх читає й клієнт), ts-commands — статичні
                            #   import модулів команд, тому його імпортує ТІЛЬКИ app/server.ts
  shared/_locales/          # рядки, що не належать жодній моделі: common.*, document.*
  _locales/                 # ЗІБРАНІ локалі — склейка всіх _locales/ дерева, віддається
                            #   браузеру; правити тут не можна, деталі нижче
  styles/tailwind.css       # ЄДИНИЙ вхід збірки Tailwind
  main.ts                   # composition root клієнта
  server.ts                 # composition root бекенду
  sql.json                  # порядок збірки SQL-пакета (важливий: за FK)
scripts/
  sql-assemble.ts           # обгортки над @altera/tools: передають усередину SQL ядра
  sql-publish.ts            #   зі СВОГО @altera/server, щоб схема й рантайм були однієї версії
```

## Демо-модель

`app/catalog/counterparty/` — довідник «Контрагенти», покладений scaffold'ом як
живий приклад повного контуру: манифест → TypeBox-схема → три екрани → `struc.sql`
→ згенерований CRUD → пункт меню → сід із трьома рядками. Читати його корисніше,
ніж опис: усе, що описано нижче, там уже зроблено.

Там же — **друкована форма** «Картка контрагента»: `prints/*.template.json`
(шаблон), `db/counterparty.custom.sql` (команда даних `counterparty_print_data`),
блок `prints` у манифесті й кнопка у формі. Клієнт нічого не рендерить: PDF
збирає ядро, а команду `printPdf` рантайм виводить із непорожнього `prints` сам —
оголошувати її не треба.

**Видаляється в чотири дії**, коли стане не потрібен:

1. прибрати каталог `app/catalog/counterparty/`;
2. прибрати `"catalog/counterparty"` з `app/sql.json` (а якщо друк більше ніде не
   використовується — і `"@core/print_template"`);
3. прибрати пункт меню з `app/admin/menu/db/data.sql` (і сам рядок з БД);
4. `deno task sql:registry` — щоб модель зникла з реєстру.

Ключі перекладу (`counterparty.*`) лежать там само, де модель, —
`app/catalog/counterparty/_locales/*.json`, тож прибираються разом із каталогом.

## Чого не чіпати

| Шлях | Чому | Як оновити |
|------|------|------------|
| `vendor/` | вихідники фреймворку з JSR | `deno install` |
| `app/_generated/**` | реєстр з манифестів | `deno task sql:registry` |
| `app/_locales/*.json` | склейка `_locales/` дерева | `deno task locales:build` |
| `app/_sqlpackage/**` | зібраний SQL | `deno task sql:assemble` |
| `db/_generated/*.crud.gen.sql` | CRUD зі схеми | `deno task sql:gen <family>/<model>` |
| `.claude/skills/**` | скіли з пакета | `deno task skills:sync` |
| `FRAMEWORK-CHANGELOG.md` | що змінилося у фреймворку — читати після оновлення | `deno task skills:sync` |

Згенерований CRUD **комітиться** — це вихідник, а не продукт збірки: він має потрапляти
в дифф рев'ю разом зі схемою, з якої зроблений. Правки поверх нього пишуться в
`db/<model>.custom.sql`, ніколи не в сам `.gen.sql`.

## Додати модель

Спершу застосуй skill `model-feature-architecture` — він описує структуру каталогу
й контракт SQL-функцій. Скіл кожного кроку читається **до** написання файлу, а не для
звірки після (див. [«Головне правило роботи тут»](#головне-правило-роботи-тут)). Далі за
кроками:

1. `manifest.json` — модель, тип (`catalog` / `document` / `register`), в'ю, команди.
2. `<model>.schema.ts` — TypeBox (skill `typebox-model-schema`).
3. UI: `<Model>List.ts` (skill `model-list-form`), `<Model>Edit.ts` (skill `model-form-root`),
   `<Model>Picker.ts` (skill `model-picker-form`).
4. `_locales/<код>.json` — рядки моделі (заголовки, підписи полів), потім
   `deno task locales:build`. Не в `app/_locales/*.json`: це склейка, і правку там зітре.
5. `db/struc.sql`, потім `deno task sql:gen <family>/<model>`.
6. Додати модель у `app/sql.json` — **порядок за зовнішніми ключами**.
7. `deno task sql:registry && deno task sql:assemble && deno task sql:publish`.

Тулбар, таблицю, пагінацію, сортування, пошук руками не писати — усе це в базових класах.
Форму, що не наслідує базовий клас, доводиться потім переписувати цілком.

## Якщо фреймворку бракує функціональності

Буває, що потрібного немає: компонента, гака в базовому класі, команди ядра.

> **СПИНИТИСЯ.** Обхід не пишеться, доки на нього не дано явної вказівки. Це правило
> діє і в автоматичному режимі: «спитати нема в кого» не означає «вирішувати самому» —
> означає зупинитися й винести питання нагору.

Порядок дій:

1. **Спинити роботу над цим місцем.** Усе, що від прогалини не залежить, доробляється до
   кінця — але сама вона обходом не закривається.
2. **Спитати.** Предметно: що будували, який саме гак чи компонент шукали, чим *можна було
   б* обійтися і скільки це коштує. Найчастіша відповідь — «такий гак є, зветься інакше»
   або «задачу не туди повернули», і з'ясовується це одним реченням.
3. **Дочекатися явної вказівки** — обходити, робити інакше, чи чекати на зміну фреймворку.
4. **Записати прогалину** у [`FRAMEWORK-GAPS.md`](FRAMEWORK-GAPS.md) у корені (формат у
   самому файлі), коли з відповіді підтвердилося, що можливості справді немає. Це єдиний
   канал, яким прогалина доходить до того, хто розвиває фреймворк.

Чому саме спинитися, а не «записати й іти далі»: обхід, зроблений без рішення, — це код,
якого ніхто не замовляв, і він **лишається назавжди**. Наступний, хто відкриє цей файл, не
відрізнить обхід від задуму й повторить його; а коли фреймворк нарешті навчиться потрібного,
обхід уже вросте так, що знімати його ніхто не піде. Ціну цього платить власник застосунку,
тож і рішення його, а не того, хто пише код.

Чого не робити натомість:

- **не правити `vendor/`** — наступний `deno install` затре зміну, і зникне вона мовчки;
- **не копіювати базовий клас фреймворку в `app/`**, щоб дописати один метод: копія
  перестане отримувати виправлення, а розійдеться з оригіналом на першому ж оновленні.
  Якщо гака справді немає — обхід у підкласі, а запис у `FRAMEWORK-GAPS.md`;
- **не залишати прогалину лише в голові чи в коментарі `// TODO`** — з коментаря вона не
  дійде до того, хто розвиває фреймворк.

Записувати варто саме випадок, а не побажання: що будували, що не вийшло, скільки коду
коштував обхід. Побажання без випадку неможливо ані оцінити, ані перевірити, коли його
закриють.

## Контракти, про які легко забути

- **Відповідь завжди конверт**: `{ ok, data: { item, rows, options, totals }, messages }`.
  Одиночний запис — в `item`, список — у `rows`, відмова — `ok: false` + `messages`.
- **Ім'я SQL-функції** виводиться з моделі: `{schema}.{model}_{command}(user_id bigint, payload jsonb)`.
- **Нестандартна команда мусить оголосити своє право** в `manifest.json` (`commands.access`),
  інакше рантайм її не виконає — 501, fail-closed (skill `model-command-access`).
- **Primary key** — `bigint` у базі, `string` у TypeScript і JSON (щоб не втратити точність).
- **Дати** — тільки через `<ui-date>`; у моделі значення завжди ISO.

## Оточення

`.env` у корені (шаблон — `.env.example`, він же годує docker-compose). Логін і пароль у
`BOOTSTRAP_LOGIN`/`BOOTSTRAP_PASSWORD` створюють адміністратора на старті; цей пароль
тимчасовий — до його зміни жодна команда моделі не виконується.

`PORT` і `VITE_PORT` читає ще й `vite.config.ts` — щоб порт бекенда й проксі `/api` не
